- 202a1fb (a change to `pipeline`, so its dependents' flow ran, not a fully warm run): runner wrote 1.5 GB (4e55c57: 6.6 GB), kernel I/O pressure peak 4%, CPU I/O wait peak 0%. - "Peak VM CPU under 60%" cannot hold while a run is CPU-bound and fast: both numbers above are 97% average, and the run is 4.7 min of flow tests. What a faster run changes is how long the CPU is busy. The budget gates the I/O wait and the duration, not the CPU peak.
- Ledger of run b4b490e (written by the job itself): crate-deploy:cargo-flow 248.7 s, crate-wf:cargo-flow 94.1 s, crate-pipeline:cargo-flow 38.7 s, crate-wf:cargo-e2e-smoke 19.8 s, wf cargo-unit 14.4 s, pipeline clippy 12.0 s, wf clippy 10.7 s, pipeline cargo-unit 7.6 s, deploy clippy 7.1 s, typecheck 1.4 s (all ran; 8 e2e tasks hit). Set for the whole CI workflow and for wf's own pnpm call; the same call is 0.30 s. Deploy scenario tests 82 s -> 62 s, 69 s -> 65 s. Tried and reverted: one `git cat-file --batch` reader (the flow tests' git stub only understands `show`), and a per-process `show` cache (160 spawns instead of 364, no measurable time).

Only `nx.rs`, `e2e_tests.rs`, `test_plan.rs`, `verify.rs`, the router and binaries, the contract's own tests and support, and manifests can move it, so it is now an allow-list (`outside_the_contract` in `test_plan.rs`); the weekly cold run plans every test and is the backstop.
