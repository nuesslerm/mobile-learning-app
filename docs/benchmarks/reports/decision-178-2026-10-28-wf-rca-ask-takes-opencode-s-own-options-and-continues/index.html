Reported observations and context
2026-10-29, the options of `wf rca ask` held to `opencode run`: the 24 options of `opencode run --help` (1.19.0) are recorded in `clis/rca/tests/flow/fixtures/opencode-run-options.json`, each `same`, `unsupported` or `not-applicable` with a reason. A flow journey runs every `same` option (long and short form) against a fake service and checks it reaches the request, refuses `--fork` with why, and checks every `not-applicable` option is rejected and sends nothing. It caught two differences, both fixed: `-p` was `--prompt` where opencode's is `--password` (now not accepted), and `--dir` did not resolve files against the directory the way `opencode run --dir` does. A by-hand test (`cargo test -p offload --test e2e -- --ignored`) compares the table with the installed opencode after an upgrade. Real-model checks: three e2e journeys of the CLI (`-c` continuing a session and `--format json`, read-only without `--auto` and editing with it plus `--variant`, a repository-defined agent) pass against the deployed service in 22 s from this sandbox, and the service's own deployed e2e (`e2e_deployed.rs`: session, read-only, changes, agent, usage) are written and run by the service-e2e stage, not from a sandbox that has no tailnet route for reqwest.
2026-10-29, integration tier for the rca service (`backend/remote-chat-agent/rs/tests/integration.rs`, `test:integration`): the built `rca-service` binary on a free port, a fake opencode (session, SSE events, prompt) and a fake ORDS table of the test, nine journeys over real HTTP, one per `wf rca ask` option as it reaches `POST /runs`: secret gate, `auto` false (edit and bash denied) and true (changes returned), `-m`/models, `--shape` ladder pick with pool, `-f` text and base64 files, path escapes refused, `--agent` plus `--variant` plus `--title`, `-s`/`-c` session continuation, `caller` in the run log. 9 pass in 0.7 s locally with no model call, so no benchmark was needed. It showed that the API's `auto` defaults to true when absent; the CLI always sends it. `wf rca ask` itself is covered by its flow journeys (fake service over HTTP, real binary) and by its e2e against the deployed service; it has no separate integration tier.
2026-10-29, `opencode run` against `wf rca ask` side by side (`clis/rca/tests/e2e/parity.rs`, on demand: `cargo test -p offload --test e2e parity -- --ignored`; needs the opencode binary, the vault key and the tailnet). Nine journeys, same pinned model (`opencode-go/deepseek-v4.1-flash`), same prompts in same-shaped checkouts: plain answer, `-f`, `-c`, `-s`, `--agent`, `--variant`, `--format json`, `--auto`, a refused option. All nine pass, about 55 s and a few cents. One real difference found: without `--auto`, `opencode run`'s build agent still edits files (`--auto` only approves what opencode would ask), while `ask` denies edits and commands (read-only). The test pins that as the known difference; the option table's note now says so. Whether `ask` should follow opencode here is open: the Gem draft and the cf researcher/reviewer agents rely on `--no-auto` being read-only. Also found: opencode resolves `-f` and `--agent` files against `$PWD`, not its working directory, so a harness must set `PWD` (the test does).
2026-10-30, `wf rca ask` made to behave as `opencode run` where a remote run can, after the parity e2e found where it did not. (1) `--auto`: opencode's build agent edits and runs commands with or without it; the flag only approves what opencode would ask (env files, other directories, repeated calls). The service now creates the session with those asks approved (`auto`) or rejected (not), a run's changes always come back, and `--no-auto` is refused with the way to a read-only run: `--agent read-only` (`.opencode/agents/read-only.md`, which the Gem draft and the visual judge use now). The default shape is `document`; `--shape implementer:unit` is explicit for the plan worker, the batch and `/cheap`. (2) Output: stdout is each finished text part and a newline, the header and tool trace (read, write, edit, bash, glob, grep as opencode prints them, byte for byte in a unit test) are on stderr, and `--format json` prints the turn's events one per line, built by the service from opencode's own parts. (3) `-f` also carries the file as a file part of the message (`attach`), so the model sees it without a tool call. Not matched: unknown-option exit code (wf's 2, opencode's 1) and the directory itself (the service has no checkout; `--files` names what a search may see). Evidence against a local service and opencode with the real model, 18 e2e tests of the CLI pass: 8 option journeys beside `opencode run` (plain, `-f`, `-c`, `-s`, `--agent`, `--variant`, JSON event shapes, tool sequences), the permission mapping (an outside file is refused without `--auto` and read with it, on both), a read-only agent, a three-turn session that writes, appends and counts a file, two interleaved sessions taken up by id, a file changed between turns, and a task that greps, writes and runs bash. Service integration 9, flow 24 and e2e_deployed (3 run locally) pass. Cost: about 190 s and a few cents a run of the suite.
2026-10-30, the capabilities of opencode's docs (config, rules, agents, commands, permissions, skills, tools, custom tools, plugins, MCP, formatters, models, sessions) put through `opencode run` and `wf rca ask` side by side, 62 e2e tests of the CLI in all (`clis/rca/tests/e2e/parity*.rs`, run by the cli-e2e job with opencode 1.19.0 installed) with a real model, plus 13 integration tests of the service binary and 14 flow tests of the CLI. They found and fixed: the service's session did not carry what `opencode run` creates it with (question, plan_enter and plan_exit denied) and answered nothing when opencode asked a permission, so a run that asked stalled to its idle limit (now `permission.asked` is replied: approved with `--auto`, rejected without); the project's `opencode.json`, `AGENTS.md`/`CLAUDE.md`, `.opencode` agents, commands, skills, plugins and tools, the skills of `.claude` and `.agents`, and the files they name were not sent (now sent, with the local MCP servers that install a package dropped); `--command` was not carried (now it is, through opencode's command endpoint); an unknown agent was an error, not a fallback; the first request to a directory with plugins timed out while opencode installed their dependencies (180 s now); `node_modules` and install files of that were returned as the run's changes and used up the reply budget before the real files (excluded, and pruned from the kept session directory); a file a background job made after a turn was never delivered (the next turn on the session returns it); `-c` with no earlier session errored (now starts one); the message words are quoted and joined, and a pipe appended, as opencode does; a failed run prints one error event in `--format json`. The server image is now opencode 1.19.0, the version the tests pin. Each paragraph of the docs that has a counterpart on the gateway has a test; what has none is listed in `docs/gaps/rca-runbook-and-remote-run-usage.md`. Cost: about 15 minutes and a few cents a full run of the suite.
2026-10-30, the CI budget (`wf ci budget`) and a preflight job (`wf ci preflight`). First version judged each job and the wall time against the 75th percentile of the last ten green `dev` runs with a 25 % + 60 s slack; replayed on the 58 real push runs (15 green) it flagged 5 of 11 judgeable green runs, because green wall times run from 2 minutes to 98 minutes with the cache (cold against replayed), so it was made report-only and replaced: each Nx task is now judged against itself in a ledger (HEALTH_RPT.CI_TASKS, CI_JOBS; Nx's own `run.json` gives task, hash, ran or replayed, ms). A task that ran although its hash was produced before (and the task has been replayed once, entry under 13 days old) fails the run; a hash that moved with no affected project, and the same work under one hash taking 50 % and 30 s longer, are reported. The time limits that do not depend on the cache were set from the same real runs (14 green runs: idle time between jobs 8 to 47 s except the 30 Oct stall at 590 s; runner wait not explained by another run's interval 2 to 526 s except the stall at 1489 s): idle at least 120 s and 5 %, wait over 600 s. Those two flag only the stall. `enforce` stays false for the soft checks until about 20 runs have filled the ledger; the cache-refused-write and should-have-hit checks fail the run from the start. Evidence: ledger round trip against the real database (`cargo test -p pipeline --lib live_ledger -- --ignored`), preflight run live from the sandbox (cache probe written and read back, database and tailnet services up, vault secrets usable; the sandbox's own full disk and missing docker were the failures it reported), 22 flow tests of the verbs against a fake GitHub API and a ledger file. Not yet seen: the budget and preflight jobs in a real CI run.
2026-10-31, the VM's memory and disk, measured (reporting-service samples in the Autonomous Database, `wf vm exec` into agent-shell, vm-ops-api `/stats`). Memory: 7.0 of 11.9 GB in use with nothing running but CI, of which `remote-chat-agent-opencode` held 4.3 to 4.8 GB: its history climbs from 0.35 GB after the 18:00 redeploy to 4.8 GB by 22:00 while CI's `cli-e2e-tests` ran 62 real-model sessions against it, and it gives none back (opencode keeps every session in memory; the container had no memory limit). Disk: 122 to 131 GB used of 145 to 150 GB (81 to 85 %), flat across the day rather than growing; the agent-shell workspace holds only 9.2 GB of it (6.9 GB of kept ask directories), `agent-shell-dind` has written 53 GB, and no compose file limited a container's log size, so the host's Docker data (images, build cache, json logs) is the rest; the host's Docker could not be listed from agent-shell. Changes: the opencode container is capped at 3 GB (the kernel restarts it, its sessions are on the workspace volume), the service deletes an ask session from opencode when its kept directory expires and keeps those directories 3 hours instead of 24 (`RCA_SESSION_TTL_HOURS`), every prod compose service rotates its log (3 x 20 MB), the redeploy script's prune at 70 % now also trims the build cache to 6 GB and removes stopped containers, and `wf ci tidy` frees the runner volume (rust incremental state, old wf installs, week-old cargo targets) above 70 % and prints the biggest directories into the job summary so the next full disk is explained by the data. Not measured yet: the split of the host's 112 GB outside the workspace; the runner volume's breakdown arrives with the next run's summary.
2026-10-31, the flow-tests job (21 minutes of a 25 minute run) measured test by test (`cargo test -p pipeline --test flow -- -Z unstable-options --report-time`, RUSTC_BOOTSTRAP=1). Of the pipeline crate's flow tests, ten are the Nx cache contract suite, which runs the real Nx (not the stubbed `nx` the other flow tests use) over a copy of the repository dozens of times each: 208, 168, 92, 77, 59, 56, 53, 32, 20 and 17 seconds, about 780 s of the suite; every other test in the file takes under 10 s. The suite was rerun on every change to the crate, including edits to the CI report that cannot touch the contract. It is now its own test binary (`tests/nx_contract.rs`) and its own Nx task (`cargo-contract`, inputs: the crate's sources and nx.json, tooling/nx, every project.json and package.json), and `wf test plan` selects it only when the plan is not a change, the crate is reached through a dependency or the Nx graph, or one of the crate's own changed files can move the contract (everything except `ci_*.rs`, `nx_ledger.rs`, the help texts and the report's flow test, so a new file runs it until it is classified). Expected effect: a change to the CI report runs the pipeline crate's flow tests in about a minute instead of fourteen; a change to the Nx modules, `nx.json`, `tooling/nx` or any manifest still runs the contract. The weekly cache audit and the forced cold run still run everything.
