Reported observations and context
The A1 VM (`main`: 2 OCPU, 12 GB, no swap) runs the backend, the deploy builds and the Android test device. Measured on 2026-10-14 (MemAvailable on the host):
- Two devices under test: 46 to 923 MB available.
- A deploy build alone: 281 to 503 MB available.
- One device under test uses about 1.2 to 1.4 GB.
- The buildx builder holds about 0.9 to 1.5 GB.
- One device idle with the builder running: 782 MB available.
On 2026-10-18 the VM had 10572 of 11927 MB in use before the device started; the device pushed it over, the dind stopped answering its health check and the watchdog recreated it, which killed the device mid-run and (before `--no-deps`) stranded the then self-hosted CI runner in a dead network (decision log, 18 Oct).
One device. It is up only for the post-deploy test step and down after (`docker stop -t 30`, then remove). A second device was tried and dropped. The Android job starts the device only when the VM has 2000 MB available (`wf vm ops stats`), and the browser job stops its daemon before the Android job runs.
The gap still holds structurally, but its trigger has narrowed. The VM is still 12 GB with no swap. The buildx builder has no memory cap. Nothing keeps the device job and a build apart. Since 17 Oct, the CI concurrency group serializes whole runs, so the next push's builds can no longer overlap the Android job. The one build that can still overlap it is the same run's registry cache export, which wf starts after each redeploy and does not wait for (deploy_run.rs:240-258). Android units since 19 Oct never fell below 2549 MB available. CI is green through the Android job.
- The path `.github/workflows/device-tests.yml` no longer exists. The device job is the `android-e2e-tests` job of `pipeline.yml`, which calls `.github/workflows/e2e-tests.yml`. The 2000 MB check is at e2e-tests.yml:145-149.
- The 14 Oct figures (46 to 923 MB available with two devices, 281 to 503 MB during a deploy build) describe the old two-device setup. Across 94 CI Android units since 19 Oct, the VM never dropped below 2549 MB available (min memAvailableMinMb in the run reports).
The shared Metro is gone (22 Oct, stages M1 to M3), so the 14 Oct figures that counted it are one resident process lighter and nothing else in this gap changed: the VM is still 12 GB with no swap, the buildx builder has no memory cap, and the Android job still starts its device only when 2000 MB are available. The CI export steps wait for 3000 MB of `MemAvailable` before they bundle (`e2e-tests.yml`, `pipeline.yml`); the figure stays until the freed memory is measured in CI.
