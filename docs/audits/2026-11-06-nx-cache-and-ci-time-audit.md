# Nx cache and CI time audit, 2026-11-06

Scope: why the sandbox-seeded Nx cache did not replay browser e2e in CI (run 42261055980, commit 4781bb6), why the drift check did not see it, and what else costs CI time. Read-only audit; every finding was re-checked by a second reader. Numbers come from CI logs, the Nx ledger and `wf test drift` tables as cited. Anything not verified is in section 5.

## 1. Why the drift check missed this

Four separate gaps, all proven from the code:

1. It sampled two tasks that do not have the faulty input. Until bed1de1a the table in `.github/workflows/deploy.yml:354-363` held only `@lib/hook-runtime:test:unit` and `crate-harness-core:cargo-unit`. Neither takes the `browser` named input (`nx.json:15-19`, added to every e2e-browser target at `tooling/nx/e2e-tests.js:88`). The NXHASH of run 42261055980 job 128041542587 has runtime keys node, pnpm, rustc and cargo-lock-slice, and no chromium key. Those two tasks were identical on both sides, so the check was right about what it measured.
2. It never compares anything. The step runs `wf test drift ... --save` and echoes `NXHASH <json>`. There is no `--against` call in `.github`, `clis/pipeline/src` or `lefthook.yml`. `--against` exists (`clis/pipeline/src/nx_drift.rs:3,18,42`) and returns exit 1 on drift, but only the manual procedure in `docs/audits/2026-11-04-platform-cache-tier.md:78-79` uses it.
3. The sandbox side is never produced automatically. The gate (`clis/pipeline/src/pushed.rs`) never calls `wf test drift --save` and never records which hashes it wrote. `seeding()` (lines 115-126) only looks for the stderr line "build cache reads only for this run" or a `degraded` flag. The message at `pushed.rs:219` ("passed here, so CI replays them") is never checked against CI's hashes. The doc comment in `nx_drift.rs:3-4` says CI writes its table "into the run bundle"; it does not. The table only goes to `$RUNNER_TEMP` and the log, and Better Stack keeps logs 3 days.
4. It cannot fail. `continue-on-error: true` (deploy.yml:355), a 3 minute timeout, and no verdict. Also the step runs in the typecheck job, whose environment has none of the `EXPO_PUBLIC_*` values the browser job exports (set in `e2e-tests.yml:222-239` and `pushed.rs:88-101`), so its export:web and e2e-browser rows are "env unset" hashes that no real run produces.

The unit test (`clis/pipeline/tests/flow/nx_cache.rs`, around 757-810) builds two fixture sites differing only in directory, HOME, PATH and browsers dir, with node/pnpm/rustc faked through `FX_*` shims. It cannot see a real installed-Chromium difference, real arch differences or the real env. It gave false assurance.

## 2. Proven causes of the cold CI export and e2e runs, ranked

1. Chromium build name in the e2e-browser hash (proven, about 12.5 min per run). The `browser` input ran `node tooling/nx/chromium-build.js`, which returned the newest installed `chromium-*` directory. Sandbox: `/opt/pw-browsers/chromium-1243` (Chrome 153). CI: `chromium-1234` (Chrome 151, the build Playwright 1.62.1 pins in browsers.json, installed by `e2e-tests.yml:134-140`). Evidence: a python diff of the sandbox and CI tables for `e2e-tamil-writing:e2e-browser` (1157 inputs each) shows exactly one differing input, `runtime:node tooling/nx/chromium-build.js` (hash 13543833548771094224 sandbox vs CI 5424851643987376542); with a fake `chromium-1234` dir the sandbox reproduced all four CI hashes of run 42261055980 (5424851643987376542, 17464960375432082196, 6536750114746833865, 3124469331648520142). CI probe: `build cache {hits:0,misses:4}`, `"ran":[app-routes,editor-typing,tamil-writing,voice-edit],"cached":[]`. The 15 minute timeout of run 42224720917 is assumed to be the same cause (not downloaded). Fix: already written as local commit e0474576 ("nx: a browser test hashes on the pinned Playwright, not the installed Chromium build"), one commit ahead of origin/dev and not an ancestor of 4781bb6. `chromium-build.js` now returns `playwright-core@1.62.1` from pnpm-lock.yaml (`WF_CHROMIUM` still overrides; installed build is only a fallback). Remaining work: push it and confirm. Caveat: the hash now names the Playwright version, not the browser binary. The sandbox still drives Chrome 153 and CI Chrome 151, so a sandbox pass counts for CI only through the goldens' 0.2% tolerance.
2. Node patch version in every `default`-input task (proven, about 3-4 min per run when it applies). `nx.json:7-14` hashes `node --version` and `pnpm --version`. This sandbox resolves node 22.23.4 (`/opt/node22/bin/node`), mise pins 22.22.0 (`mise.toml:13-14`), CI runs 22.22.0. `wf test drift --against` shows `mla-tamagui:export:web` and `@lib/hook-runtime:test:unit` drifting only on `runtime:node --version`. `wf test drift --pins` returns ok:false here. The wf-bucket shim refuses to write from an unpinned node (`clis/wf-bucket/src/cache.rs:57-64`), so the gate then fails loudly (`pushed.rs:211-213`) instead of seeding. Cause in `.agents/setup.sh` `step_mise` (line 42): it skips any tool already found by `command -v`, so the preinstalled node shadows the mise 22.22.0. Fix in section 6.
3. The export never goes through Nx (proven, 4.5 min per browser job with any miss). `wf test prepare --web` (`clis/pipeline/src/export_site.rs:137-139`) runs `pnpm --filter mla-tamagui run export:web` directly. The only `nx run mla-tamagui:export:web` is the benchmark step (deploy.yml:408-412). `export:web` is declared cacheable (`nx.json:88-104`) but no production path uses it, and the stamp (`wf-export.json` in one checkout's dist) is the only reuse. CI log: `reused:false`, `buildS:270.6`, step 274 s. Replaying e2e-browser skips the export step, so fixing cause 1 hides it; any real miss still pays it cold.
4. Test-only files are production inputs (strong, inferred, up to 22 min per affected push). `nx.json` `production` is `{projectRoot}/**/*` minus tests, `__tests__`, md and a few more; `.flow-goldens-baseline` is not excluded, and `e2e-tests.js:82-84` adds `^production` and `production` of mla-tamagui to every e2e target. Commit 6b791822 deleted three `tamil-strokes/*.html` goldens; the diff 26e3ca11..4781bb65 touches no other frontend, harness, lockfile or patch input. The earlier hash 16466064615058251317 hit in four runs and became 5424851643987376542 in 42261055980. Inferred, because no earlier input table was saved.

Related, not a cause today: the e2e-browser hash does not include the baked `EXPO_PUBLIC_*` values or the export (a deliberate owner decision, `e2e-tests.js:114`), so a replayed pass is only as good as the goldens and the services' own verification.

## 4. Refuted findings (do not re-raise)

- "Save the pnpm store is an unconditional upload that should compare the lockfile hash with the bucket" (F6, F11). The compare already exists (`clis/blob-cache/src/pnpm.rs:158-176`, plus `save_precheck`). The real defect is different: the pack happens before a put that is rejected, the sidecar is never written, so the skip never fires. See the first row of section 3. F11's claim that the cost is not shown on every run is also wrong; 8 of 8 sampled jobs show about 180-200 s.
- "Web export (274 s) and EAS publish (281 s) are two cold Metro bundles with no shared cache" (F4). Both use the metro blob kind (`wf cache restore/save metro` in `e2e-tests.yml` around lines 211 and 252 and in deploy.yml around lines 798 and 845, same app-build tarball). Why each is still slow was not examined.
- "Host-derived runtime inputs fall back silently to the installed tool" (S3). `build()` returns `pinned() ?? installed()` and the lockfile has `playwright-core@1.62.1`, so the fallback is dead here; nothing sets `WF_CHROMIUM`; the `platform` input applies only to opt-in platform-tier crates (`cargo-crates.js:83-84,180-182`), not to e2e-browser (`e2e-tests.js:88`).
