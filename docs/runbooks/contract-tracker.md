# contract-tracker

This page is the instruction file of the scheduled Claude session "contract tracker". The phone apps are conformed to two real servers: T3 (the npm package `t3`, pinned in `tooling/t3-conformance/t3-pin.json`) and Orca (the newest GitHub release of `stablyai/orca`, pinned in `tooling/orca-conformance/orca-pin.json`). When either publishes a new release, the cassettes recorded from the pinned server, the method lists and the coverage tables are of an older contract. The tracker finds that out, records the new contract on the VM and tells the session what differs from our adapters, so a drift is fixed in days and not found by a phone.

The run itself is native: `track-contracts.yml` has `schedule: 23 2 * * *` (UTC; an empty message means `[track t3 orca]`) on a GitHub-hosted runner, so no clock pushes a marker any more. The follow-up is a step of the nightly audit session: the "Nightly audit clock (daily)" tick fires into the persistent `session_01MdgrcdJGE5MkZS29xApR9c` (which has the repository, in `nuesslerm/mobile-learning-app`), and its standing steps (`docs/runbooks/nightly-audit.md`) end with this page's Steps. The owner session keeps #80 and `#78` in this repository; until they exist, record findings in the audit log. GitHub runs schedules only from `main`, hours late, so nothing is live until `dev` is merged to `main`, and a schedule-driven run tests `main` (which is `dev` merged), not `dev`; a tagged empty commit to `dev` still dispatches it by hand.

## The pieces

- `wf parity track check|bump|plan|report` (`wf parity track --help` has the schema of each; crate `clis/parity`). `check --app <t3|orca>` prints `{app, pinned, latest, drifted}`; `bump` rewrites the pin to the newest release and lists what is stale (`rerecord`, `stale`, `review`); `plan` reads the marker of a commit message and checks each app it names; `report` folds a run into one drift report. The newest release is read from npm and the GitHub API (`GITHUB_TOKEN` lifts the API's rate limit; `WF_TRACK_NPM`, `WF_TRACK_GITHUB_API` and `WF_TRACK_GITHUB_WEB` name other services).
- `.github/workflows/track-contracts.yml`, on a GitHub-hosted runner (only the plan job joins the tailnet; the capture legs get `wf` as an artifact and the vault token only after the record). Marker, on a line of its own that begins with `[`: `[track t3]`, `[track orca]` or `[track t3 orca]`, optionally `chunk=<minutes>` (1 to 60, default 10) and `fresh` (drop the checkpoint of an earlier run). The commit must change no file (the gate of `tag-gate.yml`), so `deploy.yml` starts no CI run.
- Per app that is behind, the legs of the record machinery of `docs/runbooks/record-reference-servers-on-the-vm.md` (`wf mimic trigger|provision|job`): the pin is bumped in the runner's checkout only, each cassette set whose `mimic.toml` takes the app's provision file is provisioned at the new commit and recorded in resumable chunks, and the new set is replayed against its candidate. Nothing is committed by CI.
- The last job (`report`) bumps the pin again in its own checkout, fetches `references/<app>` at the new commit, rebuilds the methods list and coverage table (`wf parity coverage --app <app>`), and publishes `track-contracts`: the drift report, the new pins, the new methods lists and tables and the new cassette sets, as a workflow artifact (14 days) and, without the cassettes, as a run bundle under `verification/test-runs/<runId>/` (the cassettes are in the bucket as the set run of `wf mimic publish`).

## Inputs of the session

1. The last verdict. Preferably from the bucket, which an agent session reaches when its proxy refuses the Actions API: `wf test results --query "track-contracts" --json` lists the bundles (suite `track-contracts`); the bundle's `drift-report.json` is the verdict. From Actions: `gh run list --workflow track-contracts.yml --limit 3`, then `gh run download <id> -n track-contracts`.
2. `wf parity track check --app t3` and `--app orca` yourself, whatever the last run says: it is two requests.
3. `docs/plans/rca-parity/plan.md` (the coverage tables and the pin-bump rule), `docs/runbooks/record-reference-servers-on-the-vm.md` (sections 5 to 7: replaying and re-deriving the known gaps) and `docs/known-gaps.md`.
4. Issue #80, section "H. Owner" (the findings inbox; #79 is closed) and `#78` (the planned work).

## Steps

1. **Check the daily run happened.** The newest `track-contracts` verdict must be under 24 h old and the last scheduled run (`gh run list --workflow track-contracts.yml --event schedule --limit 1`) under 7 days old; otherwise the schedule is late or disabled, so push the marker by hand. If no `track-contracts` run is in progress (`gh run list --workflow track-contracts.yml --limit 1`, or a bundle newer than about 20 hours) and the last run finished, push an empty commit on `dev`: `git fetch origin dev && git rebase origin/dev`, then `git commit --allow-empty -m "[track t3 orca]"` and `git push origin dev`; confirm the remote head is that commit. Name only the apps whose `check` says `drifted`, or both when unsure: an app that is not behind costs two requests and no record. If the last run ended `incomplete`, push the same marker again: it resumes the checkpoint (add `chunk=15` when the chunks keep running out, `fresh` only to drop a checkpoint on purpose). Never push the marker twice in one hour.
2. **Wait for the run, then read the drift report.** `status` of each app is one of: `current` (nothing to do), `incomplete` (a set did not finish: step 1), `discrepancies` (the new recording differs from what our adapter answers: `sets[].replay.candidates[]` has the counts of `drift` and `breaking`), `needs-work` (the coverage rebuild reports problems: rows the new source added or moved), `clean` (the new contract is replayed without a difference: only the pin and the records are left to land).
3. **Land the contract.** For an app that is behind and whose run is not `incomplete`: `wf parity track bump --app <app>` (it lists `rerecord`, `stale` and the `review` fields of the pin, which only a person can read from the new source: for T3 `protocol`, `databaseMigration` and `conformedStable`; `conformedStable` advances only when the diff is empty or fully allowlisted); `pnpm run submodule:init` and check `references/<app>` out at the new commit; `wf mimic fetch <run-id>` for the new sets; `wf parity coverage --app <app>`, `wf mimic crawl` and the scenario generator as `stale` says, and the replay of section 7 of the recording runbook to derive `known-gaps.json` again. `wf mimic fetch <run-id>` reads the bucket run of `wf mimic publish`, which may hold only some of the sets (run 42505420726 held `orca-scenarios` only): the others are the workflow artifacts `track-set-<set>` (`gh api repos/<repo>/actions/runs/<id>/artifacts`, then `gh api repos/<repo>/actions/artifacts/<artifact-id>/zip`), of which only `cassette.json` and `interactions.jsonl` change; the pin files and `t3.*` / `t3-methods.json` come from `contracts/` of the `track-contracts` artifact. Do not set the `review` fields of the pin by hand: the new sets stamp the hash of the pin file the runner had (the old `protocol`, `databaseMigration`, `conformedStable`), so any edit makes `wf mimic verify` fail on `pin_hash`; they advance only with a re-record. The sets the track does not record (`*-crawl`, `t3-scenarios`, `t3-v0.1.6`, `orca-crypto`, `orca-agent-session`, `orca-mobile-bundle`) go stale on `pin_hash` the moment the pin moves, and `recorded_r1` replays the crawl set: record them too (`[record <sets>]`) before the pin lands. The commit that moves a pin carries `parity: pin-bump` in its message (that is what lets `pending` rise) and lists the new rows.
4. **Fix the discrepancies**, the `breaking` ones first, as adapter fixes in `clis/t3-serve` or `clis/orca-serve` through the normal gate: work on `dev` (never a session branch, never delete a branch), run the lefthook suite (never bypass), `git fetch origin dev && git rebase origin/dev`, push, and confirm the remote head equals the pushed commit. A fixed discrepancy loses its entry in the set's `known-gaps.json`; an adapter that cannot follow (the new server does something the phone does not need) is a decision in `docs/plans/rca-parity/coverage/<app>-decisions.json` with its reason, not a silent allowlist entry.
5. **Record what you cannot fix** in the BODY of issue #80, section "H. Owner" (#79 is closed; read it with `gh issue view 80 --json body -q .body`, edit it with `gh issue edit 80 --body-file <file>`), never as a comment, in the format that issue defines: one checkbox per problem under the section that says who has to act:

   `- [ ] YYYY-MM-DD [tracker] what is wrong — evidence (run id, pin version, set, interaction id) — why it was not fixed`

   Put it under "Open: an agent can fix this" when a later night can retry it, under "Open: needs the owner" when it needs a decision, a credential only a person holds, the phone, or a risk an agent should not take alone. Update the entry for the same problem with the new evidence instead of adding a second one; tick a fixed entry and add the commit sha. Typical entries: a record that stays `incomplete` after two resumes (read the leg's log and the checkpoint, `docs/runbooks/record-reference-servers-on-the-vm.md`); a set whose provision block no longer builds at the new commit; a release whose `SHA256SUMS` lacks a platform the pin names; `check` failing with a service error for more than two runs in a row.
6. **Say what you did.** End the session with the run id, each app's `pinned` and `latest`, what landed (commit shas) and the #80 entries added or ticked.

## Guardrails

- The tracker never gates or fails a push: it starts from its schedule, a dispatch or an empty marker commit.
- A pin lands only together with the records, the methods list and the coverage table of the same commit (step 3): a pin ahead of its cassettes fails `wf mimic verify`, and a table behind its pin fails `wf parity coverage --check`.
- Never edit a cassette, a methods list or a table by hand. They are generated; the decisions files, the known gaps and the adapters are the hand-kept side.
- Never skip, loosen or quarantine a test to make a discrepancy pass, and never move a pin back to avoid one.
- The session never starts a heavy job on the VM by hand: the record is the workflow's, one job at a time behind CI. If a CI run is waiting, the marker waits behind it; do not push a second marker to hurry it.
- A fix needing more than about 150 changed lines, or a new dependency, is an #80 entry, not a push.
- Never print a secret. The workflow holds none in the capture legs; the bucket write link of the publish steps comes from the vault.

## Verifying

Run it once by hand from a checkout: `git commit --allow-empty -m "[track t3 orca]" && git push origin dev`. The run summary lists each app's verdict; the artifact `track-contracts` holds `drift-report.json`, `summary.md`, the pins, the methods lists and the cassette sets; `wf test results --query "track-contracts"` lists the bundle. With both pins at the newest release the run has no capture leg and the report says `current` for both. Then fire the scheduled task by hand: it follows the steps above and ends with the summary of step 6.
