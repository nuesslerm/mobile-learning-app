# Remove the TypeScript the Rust migration left behind (keep TS only where the alternative is JavaScript)

## Context
After the standard-crates migration the repository still holds about 1,120 tracked `.ts/.tsx` and 160 `.js/.mjs/.cjs` files. Owner instruction (2026-10-10): list what is left, plan the removal of what can go, and keep TypeScript wherever the alternative would be JavaScript. Answers already given: port `vm-ops-api` last, with a canary; port the `wf` black-box suite (`tooling/wf-blackbox`, 88 vitest files) to Rust tests but keep the TypeScript suite as backup until both suites pass and fail in unison, then delete the TypeScript one.

Rules that hold throughout (repo and owner): tests first (black box against the old implementation, green on old and new); never the Agent tool; never bypass lefthook; fetch and rebase `origin/dev`; draft PRs, merging is the owner's; deploy is the pipeline (`wf ship --changed`), never `/redeploy` by hand; benchmark every port (n=5, before and after) and keep the records in `docs/audits/benchmarks/` plus the decision log; one report per changed package in `docs/audits/reports/`; no destroying vault secrets or tfstate history; downtime is no concern but recoverability without a human is (vm-ops-api).

## Phases (each its own draft PR; benchmarks and a report per phase)

0. **Dead code first: checked, nothing to delete yet (2026-10-10).** The `@cli/harness-*` packages are the dependencies of `harness-ui` (the device-frame page `wf browser` serves), so they stay; `@lib/vm-request-auth` is the real verifier `wf-blackbox`'s `vm-ops` test checks signatures with (it goes with phase 6/7); `@lib/secrets` and `@lib/eslint-config-node-ts` are still used by `remote-chat-agent`'s e2e helper and eslint config. Group C and the `vm-request-auth` row of group B are therefore not dead; they leave with the phases that remove their last user.
1. **`leetcode-auth-cookie-capture` to Rust (done on the branch, pending the pipeline deploy)** (smallest deployed service; 747 LOC: a signin poll, a browser session over `wf browser`/CDP, a Telegram notifier, a backend client). Reuse `service-kit` (tracing, health, shutdown, rate limit) and `clis/cdp` as a library crate. Tests first: a black-box suite against the Node image (HTTP routes, the poll, a fake backend, a fake Telegram), green on both. Pipeline leg `leetcode-auth-cookie-capture` keeps its name; image and compose change; the entrypoint's Xvfb/VNC stack stays. Delete `src`, `tests`, `Dockerfile` Node stages, `service-bundle`, `cli-bundle`, `socks5-forward`, `rate-limit` after the cut-over.
2. **`reporting-service` to Rust** (1,352 LOC: docker and host sampling, plan stats, a SQLite-like store, scheduler, headroom). Crates: `bollard` for Docker, `sysinfo`, `rusqlite` or the existing store format, `tokio` intervals; `service-kit`. Black box first against the Node service, then the Rust one.
3. **Library sweep.** Delete `socks5-forward`, `rate-limit`, `secrets`, `vm-request-auth`, `service-bundle`, `cli-bundle` and the `@lib/logging` babel register where only the deleted services used it; trim `browser-client` if the capture service was its last non-app consumer. Keep `logging` for the app.
4. **Generated contracts.** Replace the hand-written `backend/remote-chat-agent-contracts` TypeScript with types generated from the Rust serde structs (`ts-rs` or `specta`, run by `wf`, checked in CI by a drift check like `sync:check`); the app imports the generated package unchanged. Tests first: a golden comparison of the generated types against the current hand-written ones (every exported type present, same shape), then swap. `voice-edit-dsl` stays (the app needs it offline) but its grammar is checked against the Rust `voice_dsl` golden file already shared by both.
5. **`watchdog.mjs`, `t3-code-cookie-bridge.mjs`, `pagerduty-transform.js`** to Rust binaries or `wf` subcommands (watchdog is 199 lines of health checks and restarts; the bridge copies a cookie; the transform is a function the function platform calls, so confirm whether it must stay JS before porting).
6. **`vm-ops-api` to Rust, last** (owner's answer; the canary, the standby and the flip back of (c) to (e) below were dropped by the owner on 23 Oct: nothing runs beside the Rust service, and a broken one is fixed or the VM recreated). It is the only way into the VM and has no break-glass path (`docs/gaps/vm-has-no-second-door.md`), so: (a) port it as the crates `backend/vm-ops-api/{core,rs}` on `service-kit` (owner, 21 Oct; the 10 Oct text named `infra/oracle-cloud/vm-ops-api-rs`); (b) write the integration tests first, in Rust, against the Node service from `wf`'s and the app's real call shapes (redeploy, redeploy status, agent-shell job, Expo Go page, opencode log, state files; the trunk deployer, BetterStack proxy, bootstrap token, desktop resize and, since 22 Oct, the dev bridge are removed, not ported), green on Node; (c) run the Rust one beside the Node one on a second port and mirror read-only traffic, compare responses; (d) switch the tailnet name only when every route matches and a second door exists (or the owner accepts the risk in writing); (e) keep the Node image tagged and one `wf vm` command that flips back. Deploy through the pipeline's self-redeploy, as today (owner, 21 Oct; only agent-shell is deployed by hand, because the pipeline runs on it). The plan: `docs/plans/vm-ops-api-rs/plan.md`.
7. **Port the `wf` black box to Rust, TypeScript kept as backup** (owner's answer). Scope: 88 files, 1,186 tests. Harness first: a Rust test crate `tooling/wf-blackbox-rs` with the helpers the TS suite has (`run_wf`, stub tools, mock HTTP and HTTPS servers, mock daemon and tailnet) on `assert_cmd`, `tiny_http`/`axum`, `rcgen` for certificates. Port file by file in the same order as the TS directory, one PR per ~10 files. **Parity gate:** a `wf check`-style check that maps each TS test name to its Rust twin (same Given/When/Then title), and a mutation run: for a set of seeded faults in `wf` (a changed status code, a swapped flag, a dropped header) both suites must fail on the same test titles, and both must pass on the clean binary; the report lists any title that fails in only one. Only when the parity table is complete and the mutation runs agree does the final PR delete `tooling/wf-blackbox`. The service black boxes (`backend/*/tests/blackbox`) are out of this phase.
8. **JS to TS where it can be.** Convert authored `.mjs/.js` (group H) to `.ts` and run them with a pinned runner (Node 22.18+ strips types unflagged; `mise.toml` pins 22.14, so either bump it or run with `--experimental-strip-types`). `libraries/hook-runtime` and `scripts/guards|hooks` are invoked by Claude Code and opencode through generated config (`.agents/config/*.json`), so change the commands there and run `pnpm run sync:agent-config`. Leave group G and tool configs as they are (ESLint can read `eslint.config.ts`; do that only if it works with the pinned versions).
9. **Cleanup and enforcement.** Remove emptied workspace entries from `pnpm-workspace.yaml`, regenerate the lockfile, update `CONCEPTS.md` and the architecture workflow, add an `ls-lint`/CI rule that fails a new `.js/.mjs` outside the allowed groups (G) and outside tool configs, and record the final inventory in the decision log.

Order: 0, 1, 2, 3, 4, 5, 7 (parallel with 4 to 6), 6, 8, 9. Phases 1 and 2 are the first to ship because they remove deployed Node images and need no new control-plane risk.

## Status (2026-10-10)

- Phase 1 (`leetcode-auth-cookie-capture`) and phase 2 (`reporting-service`) are done on `claude/ts-removal` (PR #344): black box green on Node and Rust (20/20, 39/39), flow tests, benchmarks and reports recorded; both run on the VM from images built with `wf ship --ref claude/ts-removal` (the pipeline builds them on the first merge to `dev`). Phase 3 (library sweep) was absorbed by phases 1 and 2: the four libraries only the capture service used are gone, and the rest leave with their last user.
- Phase 4 finding (before any code): `remote-chat-agent-contracts` is not only types. It holds Zod schemas (about 1,760 lines) that the app runs as validators (39 `Schema.parse/safeParse` call sites outside the package). Generating only TypeScript types from the Rust serde structs (`ts-rs`, `specta`) would drop those runtime checks. The workable route is `schemars` (JSON Schema from the same serde structs) plus a JSON-Schema-to-Zod generator run by `wf`, with a drift check in CI and the golden comparison of exported names and shapes first. That is a design change to confirm with the owner before the swap; the golden comparison itself can be written now.

- Phase 5 so far: `watchdog.mjs` ported (PR #344, black box 19/19 on both). `t3-code-cookie-bridge.mjs` removed instead of ported: the Rust browser daemon already rejects JavaScript middleware, so it could not run; the recipe is in the solutions doc and git history. `pagerduty-transform.js` stays until the owner says whether the function platform needs JavaScript.
- Phase 4 measurement (2026-10-10): `remote-chat-agent-contracts` has 147 exported Zod schemas; the Rust service has 50 serde-derived types in total and 57 places that pass `serde_json::Value` through its API and application layers. The provider runtime union (462 lines, ported from t3code) has no Rust type at all. Generating the contracts from Rust therefore means first writing typed Rust models for everything the contracts describe, not generating from what exists. Recommendation: keep the Zod contracts hand-written and add a conformance check instead: the service black boxes (`backend/remote-chat-agent/tests/blackbox`) validate the real payloads the Rust service emits (routes, WebSocket events) against the Zod schemas the app uses, so drift fails a test. Generating Zod from Rust (`schemars`) stays possible per type once a Rust type exists; it is not the whole of phase 4.
