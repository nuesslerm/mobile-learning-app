### What vm-ops-api does

It is the bearer-gated HTTP control surface of the one VM, `main`. It is about 3,700 lines of TypeScript in `vm-ops-api/src` (Node 22), after the 22 Oct removal (it was about 4,300). It:
- reports health, containers, logs and memory (`/health`, `/services/:app/ps`, `/services/:app/logs`, `/stats`);
- redeploys every other app, and builds and swaps in itself (`POST /services/:app/redeploy`, `POST /redeploy?ref=`);
- runs scripts in agent-shell for `wf vm exec` and every `wf ship` image build (`/services/agent-shell/exec-script`);
- keeps two small state files (pool cooldowns, the opencode run log) and serves the opencode-log dashboard.

It runs as `ops-api` in compose project `vm-ops-api`, inside the netns of its tailscale sidecar, as tailnet host `vm-ops-api-main`, port 8080, with no host port (`vm-ops-api/docker-compose.yml:1`, `:17-26`, `:47-54`; `vm-ops-api/src/api/server.ts:310-311`). The Rust `watchdog` runs in the same project (`vm-ops-api/docker-compose.yml:90-108`).

### Why it is risky

- It is the only way into the VM. When it stops answering, every deploy, build and `wf vm exec` stops with it, and the recovery for a dead vm-ops-api is vm-ops-api (`docs/gaps/vm-has-no-second-door.md:14-20`). SSH and OCI Run Command are both closed (`docs/gaps/vm-has-no-second-door.md:22-28`).
- CI ships it first and it builds itself: `wf ship --changed` puts its leg at index 0 (`wf/deploy.rs:378-383`), and the leg calls `POST /redeploy?ref=<sha>`, then waits up to 900 s for `/health` to report the commit (`wf/ship.rs:56-61`, `:72-86`; `.agents/instructions/root.md:33`). Every other leg then deploys through it.
- Its image is also its own helper: every redeploy, status read and self-swap runs `docker run <ns>/vm-ops-api:<running tag> sh -c <script>`, and those scripts call `node /app/dist/api/cli/{provision,appendEnvLocal,verifyEnv}.js` (`vm-ops-api/src/application/scripts/redeploy.ts:7-9`, `:106-113`).
- Its compose healthcheck runs `node -e fetch(...)` (`vm-ops-api/docker-compose.yml:81-82`). A Rust image without node would turn unhealthy, and the watchdog recreates unhealthy containers (`backend/watchdog/core/src/domain/decide.rs:83-84`).

## 2. The contract

This is the spec the integration tests check. It follows the code, not the README: `infra/oracle-cloud/README.md:660` names the wrong token (`VM_GATEWAY_AUTH_SEED`), `:703-711` give the wrong default ref and the wrong status for an unknown app, `:650` and `:732-735` point at the removed sslip.io host, and `vm-ops-api/docker-compose.yml:58` and `vm-ops-api/.env.defaults:20` name a `/debug/ping` route that does not exist.

### Request pipeline (every route)

1. The URL is parsed with `new URL(req.url, 'http://localhost')`; `parts` is the pathname split on `/` with empty pieces dropped (`vm-ops-api/src/api/server.ts:135-136`). Segment routes therefore accept doubled and trailing slashes after the first segment; whole-path routes (`url.pathname === …`) do not. A request target that starts with `//` is scheme-relative: its first segment becomes the host, and the pathname and the signed canonical string start at the second segment (`//services//leetcode-backend//ps` has pathname `//leetcode-backend//ps` and parts `['leetcode-backend','ps']`, so no route matches; `//health` has pathname `/`). Segments stay percent-encoded.
2. The first route whose method equals `req.method` exactly and whose matcher passes wins (`server.ts:137-139`). HEAD is not served as GET. There is no OPTIONS route and no `Access-Control-*` header anywhere.
3. A public route runs with no body read and no auth (`server.ts:140-143`).
4. Otherwise the body is read, at most 65,536 bytes, and decoded as UTF-8 (`vm-ops-api/src/api/http/body.ts:3-31`). Over the cap the reader calls `req.destroy()`, so the 413 `{"error":"body exceeds 65536 bytes"}` is almost never delivered; the existing test accepts either (`vm-ops-api/tests/slim-router.test.mjs:142-153`). The body is read before auth.
5. Auth fails: 401 `{"error":"unauthorized"}` (`server.ts:151-154`).
6. The handler throws: 502 `{"error":"request failed","detail":<message>}` and the event `http.handler_failed` (`server.ts:155-163`). An error outside that guard: 500 `{"error":<message>}` if no headers went out (`server.ts:165-170`).
7. No route matched: 404 `{"error":"not found"}`, but only after auth, so a caller without a token gets 401 (`server.ts:113-118`).
8. JSON replies carry only `content-type: application/json`, no charset and no `content-length`, so Node sends them chunked (`vm-ops-api/src/api/http/json.ts:3-6`).
9. No handler has a timeout. App redeploy and retire hold the request for minutes (`vm-ops-api/src/infrastructure/sibling.ts:5-21`).

### Auth

- **Rotating token plus signature.** The bearer is `hex(HMAC-SHA256(VM_OPS_API_AUTH_TOKEN, UTC date YYYY-MM-DD))`, today's or yesterday's (`auth.ts:5`, `:24-30`, `:46-54`). It must carry `x-signature` (base64 Ed25519) and `x-signature-timestamp` (epoch ms, within 60,000 ms; parsed with JS `Number()` for the skew check only), over `METHOD\n<pathname><search>\n<timestamp>\n<sha256 hex of the decoded body>` with the WHATWG-normalised pathname and search (`auth.ts:56-71`). `<timestamp>` is the header text as received, which Node's HTTP parser has already trimmed of surrounding whitespace, not the parsed number; the Rust port signs over the same trimmed text. The key is the SPKI PEM in `VM_GATEWAY_REQUEST_SIGNING_PUBLIC_KEY` with literal `\n` turned into newlines (`auth.ts:19`; `vm-ops-api/.env.defaults:32`). A rotating token never falls back to the legacy check (`auth.ts:79`). wf signs the raw `path_with_query` (`wf/vmops.rs:28-51`).
- **Legacy raw token.** `Authorization` must match `/^Bearer (.+)$/` exactly; the token is compared in constant time, padded on length mismatch, and is accepted unless `REQUIRE_SIGNED_AUTH === 'true'` (`auth.ts:32-41`, `:74-81`). Compose passes it through empty (`vm-ops-api/docker-compose.yml:70`).
- **Public.** Only the three public opencode-log routes: the dashboard on `/opencode-log`, `/opencode-log/` and `/opencode-log/<runId>`; the runs list; the run detail (`vm-ops-api/src/api/routes/opencodeLog.ts:62-107`). `api` matches the run-id pattern, so `/opencode-log/api` serves the dashboard with no auth (`opencodeLog.ts:66-72`; `domain/validators.ts:34`). `/health` is gated.
- **Start-up guard.** `main()` exits 1 when `VM_OPS_API_AUTH_TOKEN` is empty (`server.ts:229-235`).

### The doubles

- **Fake Docker Engine**: an HTTP/1.1 server on a Unix socket in the case's temp dir. It serves `/containers/json` (with and without `all=true`, and with containers in any `State`, exited included), exec create (201, or a scripted status such as 409 for an exited container), start (framed output) and inspect, `PUT …/archive`, logs (snapshot and a follow stream that can split a frame across chunks, split a multibyte UTF-8 character across two frames, or fail after the headers) and stats. Answers come from per-case rules keyed on the exec `Cmd` (exact argv, or a prefix plus a regex), with an optional sequence of answers for polling. It records every request with its body. It can inject a status per path. reporting-service's flow test already serves an Engine on a Unix socket (`git show cfab6018b`). It lands with the first case that needs it (B4), not in B2a.
- **Fake `docker` CLI**: `fake-tool` linked as `docker` first on PATH. It appends `{argv}` as a JSON line to `$FAKE_TOOL_LOG`, never runs the script it is given, and answers scripted stdout, stderr (optionally split mid-character across two writes), exit code and delay by argv rule; `run -d` prints a container id. Because it never runs the script, the integration suite alone cannot see a helper command that is missing from the sibling's image; `helpers.rs` and the core static check cover that (cases below). It lands in B6.
- **Fake BetterStack**: `fake-tool` linked as `wf` records `log emit` and `secret env` argv and prints `{"sent":true}` for `log emit` (Node's path, `betterstack.ts:42-53`). The Rust run has `BETTERSTACK_OTLP_HOST` unset, so telemetry export is off; its OTLP path is covered in `rs/tests/flow.rs` in process, the way `backend/service-kit/tests/flow_telemetry.rs:28-35` tests it over plain http with `Destination::new`. Event assertions read the service's stdout JSON lines, which are the same on both.
- **Fake host**: a temp `PROC_ROOT` with `meminfo`, `loadavg` and `pressure/{io,memory,cpu}`; temp `VM_DIR` and state files.
- **Signer**: a copy of wf's `sign_request` (`wf/vmops.rs:20-51`) over ed25519-dalek 2, hmac 0.12, sha2 0.10, base64 0.22 and hex 0.4, the versions wf uses (`clis/wf/Cargo.toml:21-32`), with a fixed test key pair (no randomness). Everything else is already an env var or PATH. ### Comparing recorded calls

Recorded engine requests and sibling argv are compared with goldens captured from Node, byte for byte, after these normalisations: history `ts`, job UUIDs, the tar header's mtime and checksum, the self-build backstop seconds (±10), and the three rows of section 4 that change sibling argv or script text: the image element of every sibling argv (`ns/vm-ops-api:<tag>` on Node, `ns/vm-ops-api-rs:<tag>` on Rust, row 7), the helper commands (row 3) and the swap's service name (row 4). The normalisation is exact per implementation, not a wildcard: a Rust argv that names `vm-ops-api:` fails.

### The self-redeploy sequence (`self_redeploy.rs`)

Given an agent-shell container in the fake engine and low pressure in the fake `/proc/pressure`:
1. `POST /redeploy?ref=dev` answers 202 `{started:true, building:"dev"}`. A second POST, and a POST with `ref=feature/x`, both answer 202 `{started:false, building:"dev"}`.
2. The engine records, in order: the agent-shell list; `mkdir -p -m 700 /tmp/exec-jobs/<uuid>`; the archive PUT of `script.sh` (mode 0700), whose content equals the self-build golden for ref `dev` and namespace `ns`; the detached `setsid sh -c <wrapper> sh <dir> <about 14400>` (the 4-hour ceiling in seconds, `server.ts:176-178`; `application/buildSupervisor.ts:149-152`).
3. The status exec is polled every 5 s. The case answers "running" (`120\n---EXITCODE---\n`), then `400\n---EXITCODE---\n0`. Then `tail -c 4000 <dir>/output.log` answers `[vm-build] done tag=sha-1234567 commit=<40 hex>`.
4. The fake `docker` records the detached swap `run --pull always --rm -d …`, equal to the golden, with `IMAGE_TAG=sha-1234567` and the provision URLs at the commit, not at `dev` (`selfRedeploy.ts:47-52`; `server.ts:202-211`).
5. stdout has `self_redeploy.build_started` and `self_redeploy.swapping`. A new `POST /redeploy` answers `started:true` again.

Variants: the job exits 1, or the tail has no done line, or there is no agent-shell: `self_redeploy.build_failed` and no swap. An exited agent-shell is not picked, so it is the no-agent-shell variant above (question 8, closed 24 Oct); an exec create that answers 409 anyway: `self_redeploy.failed` and no swap (`selfRedeploy.ts:59-68`). `ref=..`: 400 and no engine call. No pressure files: `self_build.pressure_unavailable` and the build still starts (`buildSupervisor.ts:65-73`). The Rust image is built by the same script (`SELF_IMAGES`): a failed build ends it red and nothing swaps.

The scripts themselves (`swap_script.rs`, F1): the `docker` double never runs a sibling, so these cases take the swap and app-redeploy argv the service recorded and run their scripts under `sh -c` in the case's world (`World::run_script`: provision URLs on the raw double, `/home/ubuntu/` inside the world, the implementation's helper commands, `docker` and `wf` answering by rule and recording each call's directory, the compose files it saw at that moment and the OTLP and tag variables it held). A rule's `nth` fails a first `compose up` and passes the second; the `wf` double's `secret sync-env` writes its base file plus two vault secrets. Cases: a good swap runs `config -q` and `pull` in the staging dir with the old files still in place, swaps in (the marker `.swap-pending` is held across the three renames only), runs `up -d --wait --wait-timeout 120` with the new tag and no OTLP token, and only then pins `IMAGE_TAG` in `.env`, keeping the old files as `.prev`; a swap that fails at provisioning, at the env sync, at the bootstrap source (a `.env.local` BWS line the shell cannot parse), at `.env` verification, at `config -q` or at `pull` calls no later compose command, leaves all three files byte for byte, and still writes the `redeploy.failed` history line and emits it with the OTLP host and token; a `.prev` copy that fails stops the swap before any file moves; a failed `up -d`, and a pin that fails after a passing `up -d`, put the three `.prev` files back and run `up -d` again, with no `--wait`, at the tag that was running (the old `.env` may pin nothing), also when the restore's `up -d` fails (`restored=failed`) and when a staged file is gone after `.env.defaults` was swapped in; a swap killed between two renames (the marker, mixed files) is undone by the next run before it stages, whether that run passes or fails; a second swap keeps the first one's files as `.prev` and clears a left-over staging dir; an app redeploy pins its tag only after compose passed, and over an `.env.defaults` default `IMAGE_TAG=latest` the pin is the last line, which compose takes (checked with compose v5; a duplicate key in an env file takes its last value). Every one ends with no `.staging`, marker or temp file, and the history line and the event carry `restored` (`none`, `ok` or `failed`). The Rust render is held to the same cases and goldens.

The self-build script (`self_build_script.rs`, F3): the script the service archives for `POST /redeploy?ref=dev` is run under `sh -c` by `World::run_build_script`, in the case's world, with `docker`, `git`, `df` and `sleep` linked to the fake-tool in the world's `build-bin/` (checked on PATH like the other doubles, so the script reads no real disk and waits for nothing), the repo dir and its GitHub URL moved into the world and to a loopback port nothing listens on, and only the variables the script reads. A rule with `stdin` makes the double record what a call reads on its standard input. Cases: with the builder there, the docker calls are `info`, the device gate, the builder check, the prune (on `--builder agent-shell-builder`) and the CPU shares, then one `buildx build --builder agent-shell-builder ... --cache-from ... --cache-to ... --push` per image of `SELF_IMAGES`, tagged with the commit tag only and with wf's cache ref and attributes, no plain `build`, `push` or `tag`, no `latest`, no free-space prune, git fetching the ref at depth 1, checking it out and resolving HEAD, and the done line naming the tag and commit; a dockerd that refuses `docker info` twice is asked a third time, with a second's sleep after each refusal, before the device gate, and one that never answers is asked 60 times and the script goes on; a missing builder is created once as wf creates it, and one that cannot be created ends the script with exit 1 at the create, docker's message in its log and no build; a build that fails when it reads the registry cache is followed, per image, by a prune to 25 % free disk (`--min-free-space` of a quarter of what `df` reports, none when `df` prints no number) and a build with no cache flag, and the script ends 0 with a line naming the retry, a line naming the images that went without the cache just before its done line, and the done line; a build that fails both ways ends 1 with no done line and no summary, before the next image; a Docker Hub token logs in as the named user before the builder with the token itself on the login's stdin, and reaches no argv, and a failed login still builds. The rails (`rails.rs`) refuse a script naming GitHub or a path outside the world, a variable the script does not read, and a `git` that is not the fake-tool. TERM during any docker step (`info`, `inspect`, `create`, `prune`, `update`, `build`, the retry's build and its free-space prune), sent to the shell alone and to the whole group as the cancel sends it, is the unit test's (`job-cancel.test.mjs`), as the Rust render is held to the same bytes by R3.

## 5. Cutover

### One service

Callers keep `vm-ops-api-main:8080` (the tailnet ACL allows all to all: `infra/tailscale/policy.hujson:18-20`). The compose project `vm-ops-api` runs one control-plane service, `ops-api`, on the Rust image, beside the tailscale sidecar and the watchdog. There is no second implementation, no role, no `roles.env` and no pin (owner, 23 Oct, section 1).

### Image tag

`ops-api` and the watchdog both follow `IMAGE_TAG`, and the self-swap runs `docker compose up -d` over the whole project with the compose file and `.env` it has just provisioned from the new commit (`redeploy.ts:221-248`). Every swap keeps the files it replaces as `docker-compose.yml.prev`, `.env.defaults.prev` and `.env.prev`, and writes `IMAGE_TAG` into `.env` only after `up -d --wait` exits 0 (F1). The self-build pushes the commit tag only; `latest` moves once a commit has served (below). A bad commit is restored by the swap itself or fixed by the next push; a broken compose file, env sync or sidecar needs the `.prev` restore or the Terraform recreate (below).

### Second door

What exists: the watchdog recreates a container that is unhealthy, restart-looping or left without its network (`backend/watchdog/core/src/domain/decide.rs:65-110`), from its own container (`vm-ops-api/docker-compose.yml:90-108`). Docker's `restart: unless-stopped` restarts a crash.

What does not: the watchdog has no rule for an exited container (`decide.rs:83-91` has only `Unhealthy`, `RestartLoop` and `OrphanedNetwork`), so "stopped on purpose", the gap doc's acceptance test (`docs/gaps/vm-has-no-second-door.md:32-34`), would not recover; `restart: unless-stopped` (`vm-ops-api/docker-compose.yml:49`) never restarts a stopped container, and neither does `wf vm recover`'s OCI reboot (`wf/vm_recover.rs:1-3`); and a recreate runs the same image, so a bad image stays bad.

The plan:
- **D2a, an exited rule in the watchdog.** A container of compose project `vm-ops-api` whose service is still in the project's compose file and that has been exited for more than two minutes gets `docker compose … up -d --no-deps <service>`, with the same cooldown as the other rules (`decide.rs:8`, `:93`). A compose recreate removes the old container within seconds, so a swap never trips it. Flow tests in `backend/watchdog`.
- **D2b, the stop drill: the gap doc's own test.** `POST /drill?action=stop` on the service validates, answers 202, then spawns a detached sibling `sleep 5; docker stop <its own container>`. `wf vm ops drill stop` asserts `/health` on 8080 stops answering, then polls it until it answers (limit 10 minutes). `by` is `watchdog` only when the watchdog's `recreate` event names that container and the container id changed. If it has not recovered in 10 minutes the drill reports `recovered:false` and exits 1: there is nothing to flip to, so the service is fixed or the VM recreated.
- **D2b, the freeze drill.** `POST /drill?action=freeze` spawns a detached sibling that is its own dead-man's switch: `sleep 5; docker kill -s STOP <id>; sleep 600; docker kill -s CONT <id> || true`. The thaw therefore depends on neither the sandbox, nor wf, nor 8080; after a watchdog recreate the id is gone and the CONT is a no-op. `wf vm ops drill freeze` asserts `/health` stops answering before it waits, then polls as above.
- **The wire contract `wf` implements** (`wf/vm_drill.rs`, pinned on `FakeVm` in `clis/wf/tests/flow/vm_drill.rs`): `POST /drill?action=stop|freeze`, Rust only, signed token only (the raw token gets 401): 202 `{accepted:true, action, container}`, where `container` is the name of the service's own container the sibling will take down, exactly as the watchdog's `watchdog.recreated` line names it; 400 for another action. wf reads that line (`message`, `container`, `ok`, `timestamp` at the top level of the watchdog's JSON log, through `GET /services/vm-ops-api/logs`, key `watchdog`) and takes it as the proof of the recreate, so `by:'watchdog'` needs the line to be newer than `/health`'s `time` from before the drill; the new container id follows from `--force-recreate`.
- **The recovery, recorded here in writing: fix it and recreate the VM.** There is no standby and no automatic fallback (owner, 23 Oct). A Terraform recreate is pre-authorised (`infra/oracle-cloud/AGENTS.md`), and cloud-init brings vm-ops-api up unattended from the compose file at `PROVISION_REF` plus `latest` images (`infra/oracle-cloud/cloud-init.sh.tftpl:255`, `:340-346`, `:354-360`). It is not drilled. To keep it working: `latest` is promoted only after a swap is verified (F1), and a recreate lands on whatever the compose file on `PROVISION_REF` says, which S1 records.

The gap doc closes after D2b only when the stop drill recovers with `by == "watchdog"`. The owner chose D2a plus D2b (21 Oct, section 1); written acceptance of the risk is not the route, and the cutover needed the owner's written go in this file (S1).

### The switch

One cutover, one commit (commit A), which changes the compose file to the one Rust `ops-api` service, makes the self-build build the Rust image and the watchdog (`SELF_IMAGES`), and carries everything else of the plan except the retirement of the Node source. Landing model:
- Commit A lands while the old Node service is still the running one. The push's own swap is therefore rendered by the old Node code, so Node-side script edits in commit A are dead code in production; the Node source and its tests stay green and buildable in commit A, because the old self-build builds the Node image once more.
- The Rust image `vm-ops-api-rs:sha-<7>` of that push is built by hand on the VM first (`wf ship --build-only vm-ops-api-rs --ref <sha>`): the old swap provisions the new compose file, sets `IMAGE_TAG` to the push's commit tag and pulls `vm-ops-api-rs:${IMAGE_TAG}`, which must exist.
- From that swap on the Rust service renders every script (R3, byte-identical to the goldens) and runs its own self-redeploy (R8), with the `.prev` restore of F1 as its only rollback.
- Commit B (S4 with A2), after the VM test, deletes the Node source (written 23 Oct, in the tree after commit A).

- wf: `VM_BUILDABLE_IMAGES` and the release companions gain `vm-ops-api-rs` (`wf/build_image.rs:38-42`, `:79`). It differs from wf in one way. wf's push build only reads the registry cache, and a separate job after the redeploy writes it, because the upload is minutes nothing waits for (`wf/deploy_run.rs:246-259`); nothing runs that job for these images (`wf ship vm-ops-api` goes through the self-redeploy, and `--build-only` never exports: `start_build` is `Mode::Push`), and `vm-ops-api:buildcache` and `watchdog:buildcache` on Docker Hub date from 6 Oct. C1a's `--build-only` build warms the shared builder's local cache (the cargo cache mounts live there), not the registry.

## 7. Risks and open questions

Risks:
- **A broken Rust service blocks every deploy.** There is no standby and no fallback (owner, 23 Oct): it is fixed, or the whole VM is recreated with Terraform (pre-authorised). Mitigated by the one-pass VM test before anything depends on it, D2a plus D2b, and the `.prev` restore of F1.
- **The image is its own helper.** The Rust image must keep glibc, the docker CLI and compose plugin, `sh` and coreutils, the wf link and the three subcommands, and its siblings must run that image (deliberate difference 7), or every app redeploy breaks after the first swap (`redeploy.ts:106-113`, `:168-191`). The fake `docker` never runs a script, so the integration suite alone cannot see this; the helper cases that run the emitted lines, the static check in the core goldens, the "no `vm-ops-api:` in a Rust argv" case and the VM test's redeploy hold it.
- **A healthy container is not a working service.** The swap's `up -d --wait` proves the new ops-api container answers its healthcheck (any status below 500 on `/health`) within 120 s, not that every route works; a build that passes it and then fails a route is pinned, and the exit is the next push or `wf vm recover`.
- **`--wait-serving` does not see a failed swap.** It polls `/health` for the commit (`wf/verify_tier3.rs:320-335`) and never reads the redeploy history, so a swap that failed or was restored holds the CI step for its full 900 s before it fails. Before F1 the same wait ran out, and F1 only made the failure visible in `wf ship --status`; making the wait read the `redeploy.failed` line of its tag and stop at once is a later wf change, outside F1.
- **A swap killed mid-rename is undone at the next swap, not at once.** The marker is read when the next redeploy starts; until then the compose dir holds the mix, and a watchdog recreate resolves `latest`. The window is the three renames, milliseconds.
- **One commit breaks the service.** The swap restores the `.prev` files and the running tag when the new stack does not become healthy (F1); a broken compose file, env sync or sidecar still needs the restore by hand or the Terraform recreate.
- **Bootstrap order.** The running service writes the build script and renders the swap, so the push that lands commit A is rendered by the old Node service: the Rust image of that commit is built by hand first (section 5, "The switch"), and the script changes of F1 and F3 are checked on the second push.
- **Build time against the 900 s wait.** F3 puts the registry export inside the leg (wf runs it after the redeploy), and its first build may find the shared builder cold: warm it first (section 5, "Build time"). Every image of the build delays the swap, because the swap waits for the job to exit (`selfRedeploy.ts:31-52`).
- **Workspace ripple.** R1 edits all five Rust Dockerfiles, which redeploys their services (COPY lines only); R1's done-when reads all five.
- **The integration suite runs beside real credentials.** CI's runner holds the raw token, the gateway seed and the BWS read token and reaches 8080 directly; the harness clears its env, refuses a non-loopback base URL, checks its PATH doubles, and never pins the destructive retire.
- **The EAS build's pinned IP.** `eas.json:27` uses the tailnet IP, which survives only while the sidecar's state volume does; nothing in this plan recreates it.
- **Fidelity traps.** WHATWG path normalisation in the signature, including a leading `//` read as an authority; the signed timestamp being the trimmed header text, not the number; JS `Number()` and lenient base64; UTF-16 tails (`agentShell.ts:174`; `wf/vm_exec.rs:89-97`); per-chunk and per-frame UTF-8 decoding (`sibling.ts:11-16`; `docker.ts:23`, `:42`); JS number printing, omitted keys, field order. Each has an integration case.
- **A restart resets the cooldown version.** The cooldown version restarts at 0 on every start, which costs a client one 409 (`cooldownLedger.ts:7`).
- **The Nx cache: disk and a poisoned entry.** The in-VM cache this item once bounded (a volume, an LRU cap, a disk floor, per-scope tokens, a signed purge) was removed on 23 Oct. Nx replays an entry as a pass, so a bad entry turns a task green on every machine whose inputs hash the same, the shape of CVE-2025-36852 ([Nx's notice](https://nx.dev/docs/reference/deprecated/self-hosted-cache-packages)); the bound that remains is the weekly `--fresh` audit (`docs/plans/nx-cache/plan.md:168-170`), and the blob-cache plan owns the write guard, the first-write-wins rule and the purge (`docs/plans/blob-cache/plan.md`).
