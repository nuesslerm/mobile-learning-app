## native-apis: what Expo SDK 58 (expo-router 58.0.32, react-native-screens 4.30.1, @expo/ui 58.0.29, expo-glass-effect 58.0.5) gives for Liquid Glass top bars, the morphing settings menu and the grouped toolbar pill, in Expo Go 58 on iOS 26, with Android and web fallbacks

### Findings

**There is no API called 'morph' or 'morphing popover' in SDK 58. The morph is iOS 26's own behaviour for a native menu opened from a glass bar item or glass button..** I searched every v58 doc page I fetched (swift-ui menu, popover, confirmationdialog, namespace, toolbar, host, modifiers, glass-effect, router Stack, Stack Toolbar, ExperimentalStack, zoom-transition, the @expo/ui drop-in menu), the SDK 58, 58-beta and 57 changelogs, the @expo/ui 58.0.29 tarball and expo-router 58.0.32: 'morph' appears nowhere (one hit is an unrelated Compose LoadingIndicator). The nearest documented statement is in the SwiftUI Menu page: for a glass menu use buttonStyle('glass') or buttonStyle('glassProminent'), and do not put glassEffect() on the label because that 'causes a visual artifact where a rectangular halo briefly appears behind the trigger when the menu is dismissed. Always use buttonStyle instead, which correctly integrates with the Menu's dismiss animation.' So the morph is not something to call. It is the system presenting a UIMenu (UIKit) or Menu (SwiftUI) from a glass item. The only way to author a morph yourself in Expo is GlassEffectContainer + Namespace + glassEffectId + animation (below), which is a hand-built card, not the system menu.  
Evidence: https://docs.expo.dev/versions/v58.0.0/sdk/ui/swift-ui/menu.md (section 'Glass menu'); grep of na-docs/*.md and na-pkgs/expo-ui-58 in the scratchpad dir /tmp/claude-0/-home-user-mobile-learning-app/c4590e90-29d4-599a-a787-1d33b95c214d/scratchpad; https://expo.dev/changelog/sdk-58.md

**What is the grouped glass pill: adjacent header items share one glass background by default; a fixed Spacer or separateBackground splits them.** Every header Button and Menu is converted with sharesBackground: !separateBackground, and separateBackground defaults to false, so adjacent items in one placement are handed to UIKit as sharing a background. On iOS 26 UIKit draws that as one grouped pill (RNSBarButtonItem sets UIBarButtonItem.sharesBackground, hidesSharedBackground, identifier and badge only under iOS 26). Stack.Toolbar.Spacer width={n} becomes {type:'spacing', spacing:n}, which RNS turns into a UIBarButtonSystemItemFixedSpace with that width, and that splits the groups. In left and right placements a Spacer with no width is dropped with a warning. separateBackground on one item gives it its own glass piece. hidesSharedBackground removes the glass behind an item. Right items are reversed internally, so author them left to right. Raw option equivalent (not needed): unstable_headerRightItems returning {type:'button'|'menu'|'spacing'|'custom', sharesBackground, hidesSharedBackground, variant}. This is what the Claude screenshot's right-hand pill (branch glyph plus '...') is: two adjacent Button/Menu items. The Claude round buttons and the spinner are separate pieces, so use Spacer or separateBackground between them.

**Menu behaviour on iOS: it is a real UIMenu on a UIBarButtonItem, checkmarks come from isOn, keep-open is unstable_keepPresented, submenus are nested Menus.** Stack.Toolbar.Menu becomes {type:'menu', menu:{multiselectable:true, items}} and RNS builds UIBarButtonItem.menu from it. Because multiselectable is true on the root and every submenu, there is no automatic single-selection: a checkmark is only the item's own state. isOn maps to state 'on'|'off' (UIMenuElementStateOn, the leading checkmark). unstable_keepPresented maps to keepsMenuPresented, which RNS sets as UIMenuElementAttributesKeepsMenuPresented (iOS 16+). The docs warn: 'This is marked as unstable, because when action is selected on iOS it will recreate the menu, which will close all opened submenus and reset the scroll position.' That matches the recording (a font-size pick returns to the root with the new value). A nested <Stack.Toolbar.Menu title=...> becomes a UIMenu child (submenu); the d.ts says 'Nested submenus ... opens as a separate menu'. inline gives UIMenuOptionsDisplayInline (a section with a divider, which is how to get the hairline between Line wrap and Tabs). palette gives a horizontal row (iOS 17). Action subtitle is UIAction.subtitle. A destructive action renders red. Drill-in replacing the menu in place with a header row is standard UIKit behaviour for a submenu; nothing in the code overrides it, but I could not observe it from here. Apple forum thread 804410 reports that on iOS 26 a keepsMenuPresented menu still collapses when its bar item is grouped with another item and its style or menu is rebuilt, and that with a single item it stays open. The recommendation therefore puts the settings item on its own background.

**Title, subtitle, large title and scroll-edge effect.** There is no native subtitle: Stack.Title takes only children, asChild, style, largeStyle, large, and react-native-screens 4.30.1's classic header has no subtitle (subtitle exists only in its experimental 'gamma' stack, and ExperimentalStack honours only title, headerShown, headerTransparent, headerBackVisible). ### Constraints

- Expo Go means only modules in bundledNativeModules.json: @expo/ui ~58.0.29, expo-glass-effect ~58.0.5, expo-symbols ~58.0.5. None is a dependency of frontend/mla-tamagui/package.json today (pnpm links expo-glass-effect only under expo-router), so each one used must be added with its bundled version and vetted (the repo rule: pnpm run audit). No custom native code and no dev client.
- The grouped pill, the morph and the Liquid Glass bar need iOS 26 and a glass-capable Expo Go. Gate native chrome on isLiquidGlassAvailable() from expo-glass-effect; on web and Android it returns false, so the existing JS ScreenHeader keeps working there (parallel change, nothing moves for Android or web).
- A custom `header` option turns the native bar off (NativeStackView.native.js:203). Any screen that adopts Stack.Toolbar must not set `header`. Stack.Toolbar left and right placements set headerShown: true.
- Stack.Toolbar renders nothing on web. On Android it needs @expo/ui plus image-source icons, drops text-only items, has no glass and no grouped pill, and its items take no testID, so the Android e2e units that tap ProblemEditorMenuButton and similar testIDs would lose their targets. Keeping Android on the JS header avoids the new dependency and breaking those units.
- No native bar item accepts a testID. Native bar behaviour cannot be asserted by a flow test or by the browser export. The owner's iPhone, through an EAS Update, is the only proof; say so plainly.
- The flow-test harness stub for expo-router has no Stack.Toolbar, Stack.Title or Stack.Header members and Stack.Screen is () => null (frontend/libraries/flow-test-harness/src/stubs/expo-router.cjs:21). A screen that renders <Stack.Toolbar> needs the stub extended (a native-runtime stub, allowed) or the flow suite throws. Pure model logic (menu items, state, ids) should live in the feature's domain/ and be unit-tested; the design system stays delivery only.
- Never import @expo/ui/swift-ui outside *.ios.tsx files: Metro then keeps it out of the web export and the Android bundle.
- Stack.Toolbar names are 'unstable_' in the types (unstable_keepPresented, unstable_headerRightItems) although 58 calls toolbars stable. Declared menu state changes recreate the menu on iOS (closing open submenus, resetting scroll), which the docs state.
- ExperimentalStack is not an option: it honours only title, headerShown, headerTransparent and headerBackVisible.
- There is no iOS simulator on this machine and the emulator runs only in CI, so nothing native-iOS can be visually verified in a session. Web goldens can show only the fallback.
- Expo's own dark-mode note applies: without expo-router's ThemeProvider the glass buttons can flicker in dark mode, and the native header follows the system scheme, not the app's theme mode, unless headerUserInterfaceStyle is passed.

### Unknowns that need a device

### Constraints
