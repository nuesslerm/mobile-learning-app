## Summary

SECTION H (after G), reviewed against the code, the installed expo-router 58.0.32, react-native-screens 4.30.1, expo-glass-effect 58.0.5 declarations and the repo's rules. Shorthand: DS = frontend/libraries/tamagui-design-system, H = frontend/libraries/flow-test-harness/src, CEA = frontend/libraries/code-editor-api/src, A = frontend/mla-tamagui, L = A/features/leetcode, S = A/features/settings/src, T = A/tests. 12 items, 60 slices (was 54: H3.3, H7.3, H8.3 and H12.5 each split, see the REVIEW lines).

ONE MECHANISM. Every topbar is declared once as a ScreenHeaderSpec through the existing `ScreenHeader` name (a facade; a `useScreenHeaderOptions` hook serves layouts). On iOS with Liquid Glass available (isLiquidGlassAvailable and isGlassEffectAPIAvailable), the persisted setting `glass-headers` on and the screen opted in (`glass` prop), a pure DS builder turns the spec into react-native-screens header items through expo-router's `unstable_headerLeftItems/RightItems` (adjacent items share one glass pill; a spacing item or `sharesBackground: false` splits groups; menus are UIMenu with `state` and `keepsMenuPresented`; every item type comes from expo-router's public type exports). Everywhere else (Android, web, iOS below 26, flow tests, goldens) today's Tamagui header renders unchanged, permanently. `Stack.Toolbar` JSX is never mounted (it throws on Android without @expo/ui and renders nothing on web); the only new dependency is expo-glass-effect ~58.0.5, added in H3.3 where it is first imported (already a dependency of expo-router 58.0.32, ExpoGlassEffect is therefore in Expo Go 58 and an EAS Update needs no native build). ONE setting (Appearance row, default off), per-screen opt-in by code, so a screen group is its own slice; the contract flips the default and deletes both. Opaque bar first (`headerTransparent: false`, verified: RNS then lays the content out below the bar): no inset, toast or console-sheet arithmetic changes; scroll-under is opt-in in H10.

EDITOR BAR (B): back | two-line glass title capsule | busy spinner (while a run is in flight) | settings pill (own glass piece, sliders glyph; the item also carries the language as its label, UIKit decides whether it shows) | one grouped pill [Info, More]. The language row stays; Format moves from More into the settings menu.

SETTINGS MENU (C): SDK 58 has no 'morph' API; the morph is iOS 26's own behaviour for a UIMenu opened from a glass bar item. The menu is a declarative header menu (root and every submenu multiselectable, else UIKit's single selection would uncheck the sibling toggle; toggles keep it open, Font size and Tabs drill in place, Symbol Bar opens a sheet, Format Code drills to a destructive row). Android and web get the same menu tree in the widened HeaderMenu popover. Plan B (a SwiftUI Menu in an @expo/ui Host) is built only if the phone shows the menu collapsing on a toggle.

WHAT ONLY THE IPHONE SHOWS: the native bar, the grouping, the morph, keep-open, the title capsule, swipe-back, theme following, the drag feel, whether isLiquidGlassAvailable is true in the owner's Expo Go. No session, CI job or golden can; flow tests prove the wiring through a native twin stub, not pixels, and every new flow test also freezes a golden (twin DOM, not glass). An EAS Update ends H3, H8 and H11.

ORDER: H1, H2.1 to H2.3, H4 (after H1.2), H5.1 to H5.3, H5.5, H7.1 to H7.5 and H8.3 touch no screen or generated file and can start at once in parallel worktrees. H6.1 regenerates cm6Bundle.ts (queue with F2.4 and F2.15). ## H1. The design system's header core: spec, builders and the setting (pure, nothing wired)

**Do.** In @lib/tamagui-design-system (type 13) write the part of the topbar that needs no screen. (1) The persisted setting `glass-headers` (off). (2) The header spec: title, subtitle, back, ordered groups of actions and menus, a busy status, and an optional `sfSymbol` beside every Lucide icon; today's ScreenHeaderProps stays assignable to it (so action nodes of the menu tree take an optional `kind`, existing HeaderMenuItem objects have none). (3) The menu tree: action (with checked and keepOpen), section, submenu, confirm. (4) Three pure functions: spec to native header items (adjacent items share one glass piece, a spacing item and sharesBackground false split the groups, toggles carry state and keepsMenuPresented, root menu and every submenu are multiselectable because RNS maps `singleSelection: !multiselectable` and UIKit's single selection would uncheck the sibling toggle), spec and environment to Stack.Screen options (native: headerShown true, headerTransparent false, headerBackVisible false, headerShadowVisible false, theme colours, headerTitle, unstable_headerLeftItems and unstable_headerRightItems; otherwise today's `header` function), and the environment truth table (Platform.OS ios, Liquid Glass available, setting on, screen opted in). The options builder and the items builder import no react-native: the classic `header` renderer and the title element are injected by the caller, so the DS node-env tests can run them. **Proof.** Unit tests in DS/tests (node env, no react-native import), Given/When/Then; tsc and the DS depcruise lint; `wf check --layout` unchanged. Nothing is wired, so no flow test, golden or e2e moves. Test type: unit only, said plainly: no native behaviour is shown by H1.

## H3. The renderer: ScreenHeader as the one call site, the glass title, the theme bridge, the setting row, the first phone probe

**Do.** Make the facade real, still invisible by default. `ScreenHeader` keeps its name and props (so 20 in-body call sites do not change) and gains `glass` (per-screen opt-in) and `placement` ('body', the default, or 'navigator'); `useScreenHeaderOptions(spec)` serves layouts. Classic renderer when the environment says so (exactly today's: in flow for 'body', `options.header` for 'navigator'); native when it says so: a Stack.Screen with the H1 options, null body. In classic mode the header function is fresh every render as today; in native mode options are memoised by headerSignature and press handlers go through one ref, so a rebuild happens only when displayed data changes (a rebuild recreates an open UIMenu). The glass title is an expo-glass-effect GlassView capsule with two Text lines and a pure max width (a plain themed View when isGlassEffectAPIAvailable is false); the native bar publishes `insets.top + 44` to useHeaderHeightStore so toasts clear it. The theme bridge: expo-router's ThemeProvider whose value is DefaultTheme (what the NavigationContainer uses today, fork/NavigationContainer.js) unless the native path is active, then Dark or Default by the app-resolved scheme (a value switch, never a conditional wrapper, so flipping the setting does not remount the navigator), and Appearance.setColorScheme (system maps to null, cleaned up to null) only on iOS when the native path is active, because the native chrome follows the OS and the app's Light/Dark choice is separate. The setting gets an Off/On row on the Appearance screen; the EAS link opens there (no URL parameter, decision 49's reason). First phone probe: Appearance and About opt in.

## Decisions this plan proposes

- H-A One setting, per-screen opt-in. The persisted setting `glass-headers` (design system, AsyncStorage, default off) switches the new header spec on (an Appearance row; the EAS link opens there; no URL parameter). Each screen or screen group opts in with a `glass` prop in its own slice, so it is moved and rolled back alone. The contract flips the default and deletes the setting and the prop one release later. Not a setting per screen: migration state is not a user choice and N rows churn goldens.
- H-B Mechanism. Native topbars are react-native-screens header items declared through expo-router's Stack.Screen options (unstable_headerLeftItems and unstable_headerRightItems), typed by expo-router's public type exports, built by one pure design-system module, active only when Platform.OS is ios, expo-glass-effect reports Liquid Glass and the glass API, the setting is on and the screen opted in. Stack.Toolbar JSX is never mounted (it throws on Android without @expo/ui, renders nothing on web, drops text-only items and has no glass); @expo/ui is not added on the default path. Android, web and iOS below 26 keep the Tamagui header permanently: that is the fallback, not debt. All unstable_ names live in DS/composites/native-header so a rename is one folder.
- H-C One call-site API. `ScreenHeader` keeps its name and props and becomes a facade over ClassicScreenHeader (today's component, moved) and the native renderer; `placement` is 'body' (in-body screens: the facade renders the Stack.Screen options and no body) or 'navigator' (the editor); `useScreenHeaderOptions` serves layouts. One ScreenHeaderSpec feeds both renderers; the options builder takes the classic renderer as a parameter so it stays free of react-native.
- H-D Opaque first. Native bars start with headerTransparent false and the theme background, so the screen root still starts below the bar (react-native-screens only translucent-lays-out when headerTransparent is true): no inset, toast, console-sheet (decisions 50 and 55) or hero arithmetic changes. Scroll-under is an opt-in per screen (H10) through contentInsetAdjustmentBehavior automatic; the editor goes transparent only on the owner's word and with G's consoleInset subtracting the bar.
- H-E The editor bar. Left: round back with the existing dirty guard. Centre: a glass capsule with the title and the 'category · Difficulty' subtitle (a GlassView inside headerTitle, because a native subtitle does not exist in react-native-screens 4.30.1). Right: a busy spinner while a run is in flight, the editor settings pill on its own glass piece (label and icon, UIKit decides), then one grouped pill [Info, More]. The language row stays (decision 51); Format leaves the More menu for the settings menu when the setting is on.
- H-F The settings menu is the system menu. SDK 58 has no morph or morphing-popover API; the morph is what iOS 26 does to a UIMenu opened from a glass bar item. The menu is declarative header-menu data: root and submenus multiselectable, toggles and option picks carry state and keepsMenuPresented (a pick recreates the menu, so it returns to the root, as recorded), Font size and Tabs are submenus drilled in place, Symbol Bar is a plain action that opens the sheet, Format Code is a submenu with one destructive row. The settings item sits on its own glass piece because a kept-open menu on an item grouped with others collapses when rebuilt (Apple forum thread 804410). Plan B, a SwiftUI Menu with buttonStyle glass in an @expo/ui Host inside a header custom item, is built only if the phone fails keep-open.
- H-G One menu tree, two renderers. The menu tree (action with checked and keepOpen, section, submenu, confirm) is owned by the design system. The native renderer maps it to UIMenu items; HeaderMenu (the Tamagui Popover) is widened to render the same tree with in-place submenus and a confirm card, so Android and web are a faithful twin. A parity flow test runs one table of behaviours through both.
- H-H Editor preferences are per device and persisted (`leetcode-editor-prefs`: fontSize 12 13 14 15 16 18 20, tabs 2 4 8, wrap, whitespace), never per problem, with today's values as defaults (font 14, tabs 4, wrap on, whitespace off) so no golden or test moves; old store fields stay until the contract. Show Whitespace is one new typed config key through library, legacy mapping, page and a regenerated bundle in one commit (decision 44 serialisation); the combined updateConfig patch must carry it in MAPPED or every live update is refused. Tabs changes the toolbar's indent unit too; existing indentation is not rewritten.
- H-I Symbol Bar is new and opt-in. Eight groups of at most four code points, persisted (`leetcode-symbol-bar`: shown, groups, railStyle default classic), a DS Switch, an opt-in SheetHeader with leading and trailing slots, ReorderableList opt-ins, a SymbolBarRail that types through typeText. The classic rail stays the default until the owner has used the symbols rail on the phone; a temporary Classic | Symbols control in the sheet is deleted at the flip.
- H-J Harness policy. Rendering Stack.Screen headers in flow tests is opt-in (setStackHeadersRendered), not the default, so the 86 editor-route sidecars are not re-baselined; a native twin stub renders header items and a UIMenu as DOM (wiring, grouping flags, keep-open, drill-in) and an expo-glass-effect stub carries a switch; the ThemeProvider stub records its value instead of adding an element. The twin is a native-runtime stub (README rule 2) and is documented as proving wiring only, never glass, the morph or UIKit's rebuild behaviour. Every flow test writes a final golden: new tests commit theirs with the slice.
- H-K The design system's key-value adapter is in memory on native (only web has localStorage), so the new setting persists through AsyncStorage directly; the doc's own target for type 13 is a keyValueStore.native.ts over AsyncStorage, which would also start persisting the theme and font stores and is therefore a separate owner decision (a gap note, not a fix).
- H-L Theme bridge. Native chrome follows the OS, not the app's Light/Dark choice. expo-router's NavigationContainer defaults to DefaultTheme (light), so the root ThemeProvider value is DefaultTheme unless the native path is active (then Dark or Default by the app-resolved scheme), keeping Android and web byte-identical and never remounting the navigator; the root passes headerTintColor and headerStyle from the Tamagui theme and headerUserInterfaceStyle, and Appearance.setColorScheme (system maps to null, reset to null when the path turns off) is called only on iOS when the native path is active, from an extracted NativeChromeBridge.
- H-M Format Code stays on the existing backend gateway: no backend change, it needs the network and fails with the existing toast offline. The confirm moves into the menu; the header-menu Format row and (with G9.6) the action-row Format button are deleted in the contract after twin tests.
- H-N Out of scope by decision: the CollapsingHeader heroes (ProblemListScreen, TamilCourseScreen) are content and stay Tamagui; the overlay routes keep their SheetHeader; showcase and charts-spike keep their stock native headers. Decision numbers: F takes 62 and on, so these are lettered H-A to H-N until they land.
- H-O Dependencies. expo-glass-effect ~58.0.5 is added in the slice that first imports it (H3.3), declared in the DS devDependencies and the app dependencies, vetted in the commit (publisher, licence, footprint, already an expo-router dependency) with `pnpm run audit` (advisories only); @expo/ui is added only if Plan B fires. External packages are not typed by `wf check --layout`, so clis/pipeline/data/package-types.json is not edited.

## Risks

- R1 Keep-open on a rebuilt menu: expo-router documents that a kept-open action recreates the menu (submenus close, scroll resets) and Apple forum thread 804410 reports a collapse when the item is grouped with others. Mitigation: the settings item has its own glass piece, root-level toggles only, Plan B (H8.6). Unproven until the phone: checklist 7.
- R2 isLiquidGlassAvailable() may be false in the owner's Expo Go (built before the iOS 26 SDK, or UIDesignRequiresCompatibility): then the native path never shows and the setting does nothing visible. H3.8 probes it first (open /showcase, the stock native header, and the About screen).
- R3 A page-level headerShown true over a layout headerShown false may flash the old frame. Mitigation: declare static options in the layout for static titles; phone checklist 13.
- R4 A custom left back item may disable the iOS interactive swipe-back, and the editor's dirty guard covers only the header chevron (swipe-back is unguarded today, no usePreventRemove anywhere). Unknown until the phone; checklist 5 and 12 (the Plan and Code swipe competes with the edge swipe).
- R5 The title capsule inside headerTitle may get no size from react-native-screens, or glass behind the title view may double up with the GlassView. Mitigation: pure titleMaxWidth, explicit sizes; a flag to drop the GlassView.
- R6 unstable_ APIs may be renamed by an expo-router bump: all of them are in DS/composites/native-header and pinned by DS/tests/nativeHeaderItems.test.ts and nativeHeaderOptions.test.ts.
- R7 Appearance.setColorScheme changes keyboards, alerts and sheets for the whole app on iOS: it is called only when the native path is active, reset to null when it turns off, and tested at the native API level; a forced Light or Dark flip while the Appearance header is visible relies on it, because headerUserInterfaceStyle cannot change while visible.
- R8 Metro blockList: an unanchored /ios/ regex once blocked react-native-screens' own header sources and only a device noticed. H3.3 reads the hosted eas-update job's iOS export log; web and the emulator would not show it.
- R9 expo-glass-effect, AsyncStorage and expo-router are new DS declarations: external packages are not typed by `wf check --layout`, so no data file is edited; the vet is recorded in H3.3's commit and `pnpm run audit` covers advisories only.
- R10 The native twin is our model of UIKit and can drift from the truth; parity tests prove agreement with documented behaviour only. Every slice says so.
- R11 The fallback popover is taller than any header menu before it: on a small Android screen or with the keyboard up it may clip; maxHeight and scroll; the Android unit (H11.2) is the only check.
- R12 Opening a native menu while the editor WebView has focus: whether the keyboard and the live font and wrap changes behave is a phone question (checklist 7).
- R13 The toast offset for the native bar is a constant (insets.top + 44); if the glass bar is taller the toast sits under it. Checklist 11; the measureInWindow probe is the upgrade.
- R14 Gates that a new file can trip: platform-forks.json and native-ui-residuals.json (both guard tests are excluded from test:unit and walk only frontend/mla-tamagui, so they are registers today, not gates; keep them current), the layer gates, check:editor-bundle, the staged lint of frontend/libraries (the pre-commit gap in the architecture doc: DS lint may not run at commit, so run it by hand).
- R15 Section collisions in shared files: ProblemEditorScreen.tsx, EditorInput.tsx, EditorHelperRails.tsx, cm6Bundle.ts, DS index.ts and icons.ts, harness setup.ts: serialised as listed in conflicts.
- R16 The Tamagui Popover has never been opened in a flow test (headers were never rendered): H2.4 may need a harness fix before anything else in H4 or H8 is trustworthy.
- R17 The reanimated stub's per-render useSharedValue may not drive a ReorderableList drag faithfully; H7.3 finds out on today's code before any product change.
- R18 A persisted store's async rehydrate can overwrite a test's setState (the merge pattern resets a missing field to its default): tests reset the store in beforeEach and flip it inside act, as AutocompleteSetting.flow.test.tsx does; rehydrate at import has settled before a test body runs.
- R19 Whole routes under a patched Platform.OS 'ios' can hit forks beyond the one under test (HeaderClearToaster, device-lab): native-branch flow tests mount the smallest unit (the bridge hook, a probe screen) and keep route-level tests on web.
