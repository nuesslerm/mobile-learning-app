## Summary

Shorthand: L/ = frontend/mla-tamagui/features/leetcode/. The block view is a pure client of the editor API that already shipped in D2 and E1: it reads `tree` (detail 'outline') plus the text, projects statements into fixed-height rows, and turns a drop into exactly one `moveNode` (a block dragged by its grip) or `insertSnippet` (a palette chip) call made `at` the revision and `instance` of the tree it drew. No page, bundle, library, port or backend change: cm6Bundle.ts and pyodidePage.ts are untouched, so no slice regenerates a generated file and none must be serialized against one. The only hot files touched are ProblemEditorScreen.tsx, EditorInput.tsx and ProblemListScreen.tsx, all in one slice (F3.7), and that slice must follow any F1 or F2 slice that edits the first two.

Verified facts. (1) react-native-gesture-handler 3.3.0, react-native-reanimated 4.7.1 and react-native-worklets 0.13.0 are runtime dependencies in package.json and installed. They already run in the web export: app/_layout.tsx mounts GestureHandlerRootView (line 90), and app-shell/DebugFab.tsx (a Pan and Tap race) and ui/ReorderableList.tsx use both. RNGH on web defaults touch-action to none, so a handle drag does not scroll the page. A real drag has never been driven in the export: no e2e touches the FAB's pan, so F3.10 is the first proof. (2) RNGH 3.3 marks the builder API (`Gesture.Pan()`) deprecated in favour of `usePanGesture`; DebugFab, ReorderableList and the harness stub all use the builder. F3 does too, because the stub only emulates it. (3) When Reanimated is installed RNGH workletizes every gesture callback and runs it on the UI thread, so a callback that calls the plain-TS planner or setState needs `.runOnJS(true)`. (4) In the flow harness both libraries are stubs (flowTestConfig.ts lines 49 and 62). The gesture stub turns DOM pointer events into the Pan lifecycle (onBegin, onStart past minDistance, onUpdate, onChange, onEnd(e,true), onFinalize) with x, y, absoluteX, absoluteY, translationX and translationY, and Race, Exclusive and Simultaneous. `session.stroke` and `session.drag` (page coordinates from the element's getBoundingClientRect, which `session.layout` can set) or manual `fireEvent.pointerDown/Move/Up` drive it. So a drag CAN be simulated in a flow test. What the stubs cannot do: `activateAfterLongPress` is missing (calling it throws) and the delay is not simulated; there is no velocity; `useSharedValue` returns a fresh `{value}` every render, `useAnimatedStyle` runs once and `useAnimatedReaction` is a no-op; `useFrameCallback` does not exist. ReorderableList could not render under the stub and no test renders it. So motion (ghost position) is not assertable in jsdom.

Testable seam: a pure drop planner `planDrop(model, source, pointer) -> DropPlan | null` (all geometry, tested exhaustively) behind a thin gesture shell that only converts translation into a pointer in list coordinates, calls the planner, sets React hover state when the slot changes, and on a successful end calls `applyDrop`. Flow tests then drive the shell with `session.stroke` over the real CodeMirror page and check three things: the exact call (through a recording EditorBridgePort double, the existing `bridgeWith` pattern from RunErrorLine.flow.test.tsx, moved into testing/), the resulting text and one undo step, and the redrawn rows. The shell gets no test of its own beyond that.

Block model (pure, L/domain/blocks): rows come from `outline(language, root)` of the tree reply, using only the library's public exports (classify, outline, STATEMENT_BLOCK, isDamaged, errorRanges, lineStartOf, lineEndOf, isUnread). Statements only; expressions never appear. Compounds show a header row, then their Body rows one depth deeper; a Python else, elif or except line (the text line of a later Body's colon) is a non-draggable clause row. A compound with no statement Body (decorated, match) is a leaf. A statement whose subtree has an error node, that shares its line, or that lies past `parsedTo` is a `text` row: not draggable, never a drop reference, so a region that does not parse stays plain text. Each row has a path id, index, depth, kind from an explicit table (no patterns), label, content range, `movable` and `subtreeEnd`. Slots are the canonical insertion points per block: position k>0 is `{after: statement k-1}`, k=0 in a compound is `{into: owner, at:'start', block: i}`, k=0 at the root is `{before: first}`. Each slot has a gap (row boundary), a depth and a `valid` flag that mirrors what `locateRun` and `resolveDestination` refuse (damaged block or reference, shares-line, no statement). A differential test previews every offered slot through the real engine, so the model cannot drift into offering a drop the engine refuses.

Drop planner: gap = round(y / ROW_HEIGHT) clamped; among the valid slots at that gap, pick the one whose depth is nearest (x - GUTTER) / INDENT_STEP. Slots inside the dragged node's own subtree, and slots that would leave it where it is, are excluded, so the planner never produces `invalid` (move into itself) or a no-op call. Palette snippets for Python: `if condition:` / `for item in items:` / `while condition:` / `def name():`, each with a `pass` body, and `return`; the engine re-indents them. Placeholders stay plain text for the person to edit.

Stale handling: the model carries instance and revision. The call is `transact([step], {at: revision, instance, label: 'blocks.move' | 'blocks.insert', budgetMs: 1000})`; a move step carries `expect` = the node's text. Semantic calls ignore `stale: 'map'`, so a stale answer cannot be mapped. `stale`, `structure-changed`, `instance-mismatch`, `range-lost`, `text-mismatch` and `out-of-range` mean `outdated`: nothing applied, a latest-wins refetch (no timers, no debounce) redraws, a short message shows, and the drop is never replayed. Refusals (not-a-node with its reason, would-not-parse, parse-timeout, unsupported, not-ready, transport) leave the text untouched and show a message from a pure `describeOutcome`. Model reads take the text and the tree at one revision (retry once), ask again until `complete` (bounded), and hold back redraws while a drag is in flight.

Layout and toggle: the view sits below the editor zone and outside the tap-away Pressable (decision 18), shown only for Python with the setting on. There is no dev-tools settings screen (the dev-tools feature dissolved into the shell; DebugFab is only a log sheet), so the toggle follows the leetcode setting convention: a persisted zustand store `leetcode-block-view` (version 1, zod fallback, default off) and an Off/On radio row on the problem list. It is not gated on __DEV__, because an EAS Update is a release bundle and the phone must see it.

Finding to carry: the untouched starter body is whitespace after `def ...:`, which Lezer reads as an error, so E1 refuses `into` (damaged) and the empty function body is plain text. The first palette drop needs a statement already there. E1 would need a 'fill an empty block' destination to fix that; F3 does not extend E1.

## Open choice and the default taken

Statements only, expressions stay text. A row is a simple or compound statement from the outline tree; expression nodes never become blocks. The Python palette is if, for, while, def and return, each inserted with a `pass` body and plain-text placeholders (`condition`, `item in items`, `name`) that the person edits in the editor. A block is picked up by its grip handle, the nearest row gap picks the slot, and the horizontal position picks the indent among the legal slots at that gap.

## Decisions this plan proposes

- The block view is a client of the public editor contract only (tree with detail outline, text, apply with moveNode and insertSnippet, the changed and ready events): no new request, step, event, port, page or bundle change, and statements only, Python only, with expressions left as text.
- The block model, drop planner and palette live in the leetcode feature's domain/blocks, built on the library's public syntax functions, and not in @lib/code-editor-api core as the Rules line first said; the move is mechanical if a second client appears, and a differential test against the real engine's previews keeps the model's validity rules from drifting.
- A drop is exactly one call made at the revision and instance of the tree that was drawn: moveNode (with expect set to the node's text) or insertSnippet, to the canonical slot destination (after the previous sibling, else into the owner at start, else before the first statement at the root), labelled blocks.move or blocks.insert with budgetMs 1000; the planner never emits a move into itself or a no-op.
- A stale, structure-changed, instance-mismatch, range-lost, text-mismatch or out-of-range answer leaves the text untouched, redraws the rows from a fresh tree (latest-wins, no timers) and is never replayed; every refusal shows a message and applies nothing.
- Blocks are picked up by a grip handle (Pan, minDistance 8, runOnJS(true)) on rows of a fixed height, so the drop geometry is arithmetic over the model and is tested as a pure function; the shell uses the deprecated Gesture builder like DebugFab, ReorderableList and the harness stub, and moving all of them to usePanGesture is a separate change.
- The toggle follows the leetcode setting convention (persisted zustand store leetcode-block-view, default off, an Off/On row on the problem list) and is not gated on __DEV__, because an EAS Update is a release bundle and the phone must see it.
- The spike does not extend E1: inserting into a Python body that holds no statement stays refused as damaged, so the untouched starter's empty function body is plain text in the block view; whether E1 gains a fill-an-empty-block destination is decided after the phone check.

## Risks

- Pan versus page scroll: a handle drag inside the page's ScrollView may lose to the scroll on Android or iOS (on web RNGH sets touch-action none, so Chromium cannot show this). Fallback is a long-press pickup (`activateAfterLongPress(250)`), which needs one line in the harness stub's CONFIG list (it is missing today and calling it throws) and a gestures.test.tsx case; the browser swipe does not hold at the start, so a long-press pickup also needs a different e2e gesture.
- Callbacks are auto-workletized when Reanimated is installed: without `.runOnJS(true)` the planner and setState would run on the UI thread and crash. With it the drag runs on a JS thread that also serves the editor bridge (19 to 30 ms per call on the Android emulator), so the ghost may stutter; only a phone shows how much.
- The builder API is deprecated in RNGH 3.3 and a later release removes it; the shell, DebugFab, ReorderableList and the harness stub would move together to usePanGesture, which has no stub today.
- The jsdom stubs cannot show motion (shared values are fresh per render, no useFrameCallback), so tests assert the planner's output, the indicator state and the final text, never the ghost's position; edge auto-scroll cannot be tested without extending the reanimated stub.
- Layout constants (44 high rows, indent step, palette offset) are the contract between the pure planner and what is drawn; font scaling, Android dp rounding or a wrapped label would shift the geometry. Rows are single-line and truncated, and the browser e2e asserts the real row spacing equals ROW_HEIGHT, but a large system font is only checkable on a phone.
- No auto-scroll and a row cap: a drag cannot cross more than one screen of rows and the page cannot scroll during a drag, so long programs are limited to the first rows (the cap row says so). There is no tap or accessibility-action alternative to dragging, so the view is not usable with a screen reader.
- The empty starter body is an error region for Lezer, so right after opening a problem the whole class and def are plain text and the first palette drop needs a statement the person typed; the demo and the e2e seed a body.
- Parse cost on a low-end phone: an outline tree read per change while the view is on (coalesced to at most one extra read), and a drop runs two scratch parses (decision 39's 250 ms default is raised to 1000 ms per call here). The E1 note asks for one measurement; F3.8 logs it but nothing here has run on a device or on the CI emulator.
- Model drift from the engine: the model mirrors locateRun and resolveDestination refusals in about 40 lines. The preview differential covers the corpus only; a case outside it shows as a refusal message, never as wrong text, because the engine verifies the result before committing.
- The unit tests parse with the fake editor's tiny parsers, which leave out decorators, match, multi-line headers and one-line bodies; those cases are covered only by the real-bundle flow tests (F3.7 and F3.8), which use the page's own Lezer tree.
- Hot files: ProblemEditorScreen.tsx and EditorInput.tsx are also edited by F1 and F2, so F3.7 can conflict on rebase; it keeps its edit there to a handful of lines and goes after those slices.
- Async outcomes land after the stroke returns; a state update outside act would be a warning that fails flow tests, so every test awaits a rendered signal (waitFor) before asserting, as the existing editor flow tests do.
- First app-level use of a semantic apply: the engine's changes reach React through the page's legacy contentChanged echo and the write chain, which no app path has exercised with a node step before (E1's flow tests drive the page directly). F3.8 is where that interplay (value sync, run card clearing, edit marks following the text) is first proved.

## What only the phone or the owner can show

- Whether a handle drag wins over the page scroll on a real Android phone (Expo Go) and on an iPhone, and whether the pickup threshold (8 px) feels right; Chromium cannot show this.
- The feel of the drag: the finger covering the indicator (a ghost offset above the finger may be needed), ghost smoothness under the JS-thread drag, and whether the drop line is readable.
- Thumb ergonomics: 44 high rows and chips, reaching the palette versus the rows one-handed, and whether the view below the editor, outside the keyboard, is reachable with the soft keyboard up or must lower it first.
- Whether the long-palette-to-far-row drag is needed in practice for real problems (no auto-scroll in the spike), and whether the phone wants a tap-to-insert alternative.
- On-device numbers: the tree read time and the moveNode apply time from the leetcode.blocks.read and leetcode.blocks.drop log lines (read in the debug log sheet if it lists info lines, which was not checked, else from a screenshot of the console); this is also the one measurement decision 39 asked for on the 250 ms parse budget.
- The owner's recorded screen on a phone: the browser recording shows RNGH and Chromium touch on the web export, not a native finger.
- Two owner decisions: placing the model and planner in the feature's domain/blocks instead of the library core as Rules line 22 first said, and keeping the deprecated Gesture builder for the spike.
- iOS has not been touched by any slice; nothing here depends on the iOS blur trick, but the first iPhone run of a drag is the owner's.
