# The console and local submit: the plan of section G

Planned 22 Nov 2026 from the owner's recording ([README](README.md)), read against the code and attacked by a second reader. The issue body (#86) holds the decisions and the item states; this file holds the slice-level plan: files, tests and what proves each slice. `L/` is `frontend/mla-tamagui/features/leetcode/`, `DS/` is `frontend/libraries/tamagui-design-system/`, `H/` is `frontend/libraries/flow-test-harness/src/`, `T/` is `frontend/mla-tamagui/tests/`.

## Summary

Shorthand: L/ = frontend/mla-tamagui/features/leetcode/ . DS/ = frontend/libraries/tamagui-design-system/ . H/ = frontend/libraries/flow-test-harness/src/ . T/ = frontend/mla-tamagui/tests/ . Every testID of the new UI starts with `Console`. This is the plan after the skeptic review of 22 Nov against the code; every change is listed as a REVIEW line in conflicts_with_other_sections.

SECTION G (new, after F in the issue; it needs only B4, E2 and E5, so it can run beside F): the LeetCode console for the app's own on-device run. An action bar (Console, Reset, Run, Submit), a Console bottom sheet with Testcase and Run Result tabs, a Pending overlay, and a verdict for every outcome (Accepted, Wrong Answer n/m with the first failing case, Runtime Error with Line N, Time Limit Exceeded, Compile Error). All of it sits behind a new setting `leetcode-console` (default off) that keeps today's Run Local button and card; the owner flips the default in G9, after the old clients have moved. Frontend only: no port, adapter, editor-page, bundle or backend change (every run goes through the existing CodeRunnerPort), and no generated file is touched, so no G slice has to be serialized against F1's jsPage.ts or F2's cm6Bundle.ts. E2 and E5 are implemented but their CI box waits for checkpoint E's hosted run: G1, G3 and G4.1 (new files only) start at once, G2 (it moves E2 and E5 code out of the screen) waits until that run is green.

FACTS READ THAT SHAPE THE PLAN (checked in the code)
- ProblemEditorScreen.tsx is 1123 lines: one KeyboardToolbarAwareScrollView with the editor zone (flex 1, minH 280), then a tap-away Pressable holding the language row (ProblemEditorDiffRow), the action row (Format, Run Local, Run, Reset, pencil, mic), RunOutcomeCard and the E5 test-input zone. Run Local is `runLocal(mode, runParamsFor(...))`: editor checkpoint (E2, 500 ms, inside EditorInput) -> runner.run -> stale discard against `latestBufferRef` -> card + E2 jump (`jumpRef`) + toast. The leetcode.com `Run` only logs. `RunCard` and `errorLocationOf` live in ui/run/RunOutcomeCard.tsx, which state/ may not import.
- KeyboardToolbarAwareScrollView pads the content by `bottomInset` (default 24) only while the keyboard is down, else by keyboard plus rail height. The keyboard rail is a body-level portal (z 2000) = EditorHelperRails (SyntaxToolbar and ActionToolbar, each a horizontal KeyboardToolbarRail); it unmounts while any DS Sheet is open (`useOpenSheetStore`).
- The DS Sheet (DS/ui/sheet.tsx) is gorhom's inline BottomSheet: snap points are percent of the container (the screen root, below the native header), dim backdrop, `enablePanDownToClose`, returns null when closed (a programmatic close does not slide out), puts the keyboard away on open and lifts itself above a keyboard that rises for a field in it (decision 27). On NATIVE gorhom's hosting container is box-none; on WEB (`styles.web.ts`) it is a full-size absolute div with no pointer-events rule, and the repo's patch of gorhom removed the prop as well, so a sheet without a backdrop would still swallow every tap on the editor above it in the web export. gorhom's scrollable registers ONE scrollable with the sheet (no horizontal support).
- The flow harness's gorhom stub is a plain View (no gestures, `onClose` never fires, `handleComponent` not rendered); its reanimated stub is inert (`useSharedValue` returns a fresh `{value}` per render, `withTiming(v)=v`, no `useReducedMotion`); its RNGH stub drives Pan and Tap from pointer events. react-native-web's `AccessibilityInfo` captures `window.matchMedia('(prefers-reduced-motion: reduce)')` ONCE when the module is evaluated and resolves `true` when there was no matchMedia then; the harness installs a static matchMedia stub. react-native-web's `BackHandler.addEventListener` calls console.error (the flow harness and the browser e2e fail on a warning); nothing in the app uses BackHandler yet.
- DS: theme keys `$success`, `$warning`, `$destructive`, `$color2/3`, `$borderColor` exist; reanimated styles cannot resolve tokens (AnimatedWaveform reads `useTheme().x.val`); icons Terminal, Play, Plus, Pencil, RotateCcw, Trash2, X exist, FileText does not. No expo-blur or backdrop-filter anywhere. The DS package's own `test` script runs only `DS/tests/` (the existing ui/__tests__/Tabs.unit.test.tsx is outside it) and has no react-native alias, so a DS unit test that touches reanimated or AccessibilityInfo cannot run there: DS behaviour is proved in T/flow.
- The judge runs every case (no early stop). A case that hangs is a row error 'TimeoutError: Code execution timed out (Ns limit)'; a whole-run or module-level timeout comes back as `runtime_error` 'Timeout: ...' (runResponseOf drops the `timeout` kind); a crash comes back as `runtime_error` 'The Python runtime stopped/crashed ...' with no input to point at; a syntax error is `compile_error` + `error_at`. The e2e Lua runtime has `json.encode` and `json.array` only: no `json.decode`. The web editor autofocuses on open, and the on-device interpreter is warmed when the editor hydrates, so a Run is usually warm and the Pending overlay can flash for tens of milliseconds. Valid Parentheses (the recording's problem) has 15 bundled cases and one parameter `s`; the smallest catalog problem has 4; two-sum has 12, so the chip row scrolls; the catalog's third case of valid-parentheses is `(]`, not the recording's `()`.
- decision 18 (no touch-claiming view above the editor WebView), 27 (sheet lifts for the keyboard source), 43 (a custom case has expected null and no verdict), 45 (a result and its error mark live as long as the code they describe), 46 (no sleeps) all bind G.

A new `backdrop='none'` makes it non-modal and, because gorhom's web container would otherwise swallow the editor's taps, the DS passes `containerStyle={{ pointerEvents: 'box-none' }}` with it. Opening it lowers the keyboard (`dismissEditorKeyboard()`, then the DS Sheet's own dismiss). The editor focusing while it is open (EditorInput already offers `onFocusChange(true)`; EditorInput.tsx is not edited) closes it: the keyboard then belongs to the editor and the bar returns above it (recording t 9 s); a blur never closes it.
Editor strip: while the sheet is open the scroll view's `bottomInset` is `round(rootHeight * 0.70)` (the screen root's own onLayout, so a flow test sets it with `session.layout` and nothing depends on gorhom's internals) and the editor zone's `minH` drops from 280 to 96 (pure `consoleInset` and `editorZoneMinHeight`). (2) TESTCASE MODEL (domain/console/testcases.ts, caseFields.ts). Chips: bundled cases `Case 1..n` in catalog order, then custom cases numbered on from n+1 (labels positional, ids stable: `bundled:<i>`, `custom:<k>`). Parameter fields: names are `parameterNames(problem)`; the caption is the name plus ` . ListNode` or `TreeNode` when `problem.paramTypes[name]` is set. Every value is shown as JSON text through a new `jsonText` (JSON.stringify: `"([)]"` with quotes, `false`, `null`), NOT `showValue`/`showInput`, which print strings bare (`s = ()`) and would not match the recording. A bundled case shows each value in a read-only card (caption + monospace value, `clip` with tap to expand, RunCaseList's `Field` rule). A custom case holds one JSON text per parameter in an editable plain TextInput, parsed per field at Run (`parseCaseFields`, sharing `parseJsonValue` extracted from customCase.ts); a bad field blocks the run with an inline role=alert message naming the parameter. `+` adds a custom case seeded with the selected case's values, selects it and focuses its first field (cap 10 per problem). The pencil on a bundled case makes an editable custom copy and selects it (the bundled case is never mutated); on a custom case it focuses the first field. A selected custom case shows 'Delete case'; deleting selects the previous chip. Reset (footer pill and the bar's round icon, one action `resetCases`) drops every custom case and selects Case 1, no confirm (session-only data), a plain toast. Persistence is session-only: a non-persisted zustand store (`state/console/consoleCasesStore.ts`) keyed by problem id. A bundled case runs with its `expected` and gets a verdict; a custom case runs as E5's custom case (`expected: null`, `pass` ignored) and gets output only.

(3) RUN SEMANTICS. One run path: `planRun` (domain) builds `RunCodeParams` with `runParamsFor`; `runLocalOnce` (state/run, extracted in G2) takes the editor checkpoint, calls `runner.run`, applies the stale rule through an `isCurrent(params)` callback the screen supplies from `latestBufferRef`, logs `editor_v2.run_local.*`; both the classic card and the console call it. The console adds `editor_v2.console.open`, `.close` (reason), `.run_start` and `.run_end` (verdict): the signals tests and e2e wait on instead of a transient overlay. Run runs the selected chip only (the recording's Last Executed Input is Case 3); Submit runs `problem.testCases`, ignoring custom chips and the selection. Run is disabled while pending, with a bad custom field (the console opens on Testcase with the message) and for a problem with no bundled cases; Submit is disabled while pending and with no bundled cases. Run and Submit from anywhere call `dismissEditorKeyboard()` and `Keyboard.dismiss()` (a field focused in the sheet keeps the keyboard up otherwise). Stale rule: the answer is dropped (log `editor_v2.run_local.discarded`, toast 'Code changed while it ran', no tab switch, pending ends) when the editor's text or language moved since the checkpoint; unmounting drops it silently; Android back is swallowed while pending (Android only). The console path shows no result toast. A result is cleared when the code changes, on language switch, on code reset and on testcase reset, and the E2 mark with it (decision 45). `error_at` marks the line through `showErrorLine`; 'Line N (Solution.py)' calls the same `handleShowLine`, closes the sheet and re-reveals the line. Verdict (domain/console/consoleResult.ts, pure): `compile_error` -> Compile Error; otherwise the first failing case in bundled order decides: a timeout (row error 'TimeoutError: Code execution timed out' or `runtime_error` starting 'Timeout:', one exported `isTimeoutText`, pinned against the real judge) -> Time Limit Exceeded; a row with `error` -> Runtime Error; a non-error mismatch -> Wrong Answer; all pass -> Accepted; a `runtime_error` with no rows (a crash) -> Runtime Error with no input; a thrown CodeRunnerError -> 'Run failed' (not a verdict); a custom case -> 'Custom case' or the error verdict. n/m is `total_correct / total_testcases`; runtime is the sum of `elapsed_ms`.

(4) PENDING OVERLAY (ui/console/PendingOverlay.tsx, ScanGlyph.tsx). Shown from the press of Run or Submit until the answer lands, over the screen root (the native header is not covered) and above the sheet: a scrim (`$background` at about 55%), a translucent rounded card (`$color2` at about 92%, `$borderColor`, 160 by 140), a glyph of plain Views (window frame with three dots and a bar, a grid of 1px `$warning` lines at 35%, two pulsing dots, a 2px `$warning` scan line sweeping top to bottom with a trailing glow of stacked fading strips) and `Pending...` in `$warning`. Animated styles take colour strings from `useTheme()` (reanimated cannot resolve tokens). Built with reanimated (`useSharedValue`, `withRepeat(withTiming(...))`, `useAnimatedStyle`; the AnimatedWaveform precedent): it runs for real in the export and is inert in the harness stub. Reduced motion: a new DS `useReducedMotion` with a source per platform (native AccessibilityInfo; web reads matchMedia when the hook mounts, like keyboardSource.web.ts), and the harness gets a controllable query (`setReducedMotion`); when reduced the scan line is drawn at a fixed 60% and the dots at full opacity, and a test asserts that rendered style, not a data attribute (no `dataSet` is used in app code). The scrim swallows touches (a deliberate, transient exception to decision 18), exposes role=progressbar with aria-busy and a label, and mounts `useOpenSheetStore.open()` so the rail is gone at once. TestIDs: `ConsolePending`, `ConsolePendingText`, `ConsoleScan`. A flow test waits on `ConsolePending` only with a gated runner (it stays up until released); the browser e2e never waits on it for a normal run (a warm run flashes it) but on `editor_v2.console.run_start/run_end`, and proves the overlay on a deliberately slow custom case. No blur in v1; an optional last slice adds expo-blur. No minimum hold.

(5) RUN RESULT TAB (ui/console/RunResult.tsx and cards). Order: headline (verdict, `$success` / `$destructive`, role=status aria-live polite), counts (Submit only: `k / m testcases passed`), runtime, error box, IO cards, stdout, Last Executed Input. Accepted (Submit): `Accepted`, `n / n testcases passed`, `Runtime X ms`, no cards. Accepted (Run, bundled): headline plus Input, Output, Expected cards. Wrong Answer: red headline, counts (Submit), first failing case Input, Output (red) and Expected, stdout. Runtime Error: red headline, red-bordered box (role=alert) with the error text and `Line N (Solution.py)` (Solution.js for JavaScript), then Last Executed Input (caption `s =`, as in the recording; the Testcase tab's caption is `s`) = the input of the raising case with an `Open Testcase` link (FileText icon, added in G6.6). Time Limit Exceeded: same shape; Last Executed Input is the first case with no row (`cases[results.length]`) for a process-limit timeout, none for a module-level timeout. Compile Error: box with message and Line N, no input. Run failed: heading, message, muted hint, no input. Custom case (Run): neutral heading `Custom case`, Input, Output, stdout, Time, no expected, no verdict. Empty state: `Run your code to see the result here`. `Open Testcase` selects that case's chip and switches to Testcase (hidden when the case has been deleted or reset). The sheet switches to Run Result by itself when the answer lands, and rises on it when it was closed.

## G1. The console's pure core: case fields, testcases, run plan, verdicts

**Proof.** Unit tests, Given/When/Then, over the real response shapes (`runResponseOf` of judge rows, `passingRun`, `failingRun`, `customRun` shapes built inline); a real-judge pin (G1.5) proves the timeout classifier against the interpreter's own strings.

## Decisions this plan proposes

- Section G exists because of the owner's recording and request (owner direction, 22 Nov): 'i also want this same UX for the local code submit'. It covers the app's own on-device run only; no backend, no new port.
- The console is behind the persisted setting `leetcode-console` (one boolean field, default off), so today's Run Local button and card stay until the owner flips it (parallel change); the phone turns it on from the problem list row, with no URL parameter (the dev seed is gated to dev bundles and an EAS update is a release bundle), and the EAS link opens on /leetcode.
- The console is the design-system Sheet inside ProblemEditorScreen (not the workspace), one detent at 70% of the screen root (the recording's sheet top is at 35% of the screen), no backdrop (non-modal; the DS passes a box-none container because gorhom's web container would swallow taps), editor focus closes it, and the page's bottom inset is 70% of the root height with the editor zone's minimum height dropped to 96, so the E2 reveal lands in the visible strip. EditorInput.tsx is not edited (its onFocusChange and handle are enough).
- The action bar is one component in two hosts, never both: the top row of EditorHelperRails (`topRow` slot, its own row) when the keyboard is up, a dock under the scroll view when it is down and the sheet closed; while the sheet is open the footer carries the same actions and the Console button is not on screen (it only opens). The classic Run Local, the leetcode.com Run (whose result is only logged), Reset, Format and the test-input zone leave the screen in G6.4, once Run, the cards and custom cases work, so the setting never costs the ability to run; the pencil and mic move to the language row, Reset code joins the header menu.
- Testcase model: bundled cases are read-only chips Case 1..n; custom cases are editable, numbered on, capped at 10 per problem, session-only in a non-persisted store keyed by problem (saved drafts stay parked); a custom case runs as E5's custom case (expected null, no verdict, decision 43). Values are shown as JSON text (`jsonText`), not with showValue. `+` copies the selected case, the pencil makes an editable copy of a bundled case or focuses a custom one, Delete case lives under the fields, Reset (footer pill and bar icon: one action) drops every custom case without a confirm.
- Run runs the selected chip; Submit runs problem.testCases and ignores custom chips and the selection; both go through planRun -> runLocalOnce (extracted in G2) -> CodeRunnerPort, the same function the classic card uses, so there is one run path. The stale rule is the existing one; a result and its error mark are cleared with the code, the language switch and the code reset (decision 45). Run and Submit put every keyboard away first (the editor's and a field in the sheet). The console logs editor_v2.console.open, close, run_start and run_end, and tests and e2e wait on those.
- Verdicts are computed in domain by the first failing case in bundled order: compile error, then time limit (judge texts 'TimeoutError: Code execution timed out' and 'Timeout:', one exported `isTimeoutText`, pinned by a real-judge test and reused by F1's worker messages), then runtime error, then wrong answer, else accepted; a crash with no rows is a Runtime Error with no input; a thrown runner error is 'Run failed', not a verdict; n / m is total_correct / total_testcases and runtime is the sum of elapsed_ms. The judge is not changed (judge.py regenerates pyodidePage.ts); a per-row error kind from the judge is the alternative.
- The Pending overlay is reanimated (inert in the flow stubs, real in the export), has no blur and no minimum hold in v1, covers the screen root (not the native header), publishes useOpenSheetStore while mounted so the keyboard rail drops at once, and swallows touches while a run is in flight: a transient, deliberate exception to decision 18. Tests wait on `ConsolePending` only with a gated runner; the browser e2e proves it on a deliberately slow custom case and waits on log events for a normal run.
- Reduced motion: a DS `useReducedMotion` with a source per platform (native AccessibilityInfo, web matchMedia read at mount, like the keyboard source) and a harness switch `setReducedMotion`; react-native-web's own AccessibilityInfo captures the media query at import and is not used. The frozen state is asserted from the rendered style.
- Design-system additions are opt-in and leave every existing user unchanged: Sheet backdrop 'none' (with its box-none container) and handleLabel, SegmentedControl variant 'thumb', Button variant 'success' (added in G7.1), useReducedMotion, a FileText icon (added in G6.6); the harness gorhom stub mirrors data-backdrop and data-container-pointer-events and renders the handle. DS behaviour is proved in T/flow, because the DS package's test script runs only DS/tests and has no react-native alias.
- Android back is registered only on Android (react-native-web's BackHandler logs a console error); the flow test sets the platform and spies the native API, as sheetBranches does. The chip row is a plain horizontal ScrollView so gorhom's single registered scrollable is the body's; content panning stays on, with `disableContentPanningGesture` as the fallback if the phone shows a fight.
- Proof policy: flow goldens carry both colour schemes; the browser e2e golden is light only because `wf browser test` has no colour-scheme option; drag-to-dismiss and the keyboard handoffs are proven in the browser or on the emulator only if the export or the emulator answers the swipe, otherwise on the phone, and the gap is filed; an e2e never waits on a transient overlay or reads bounds straight after an animated scroll.
- G needs only B4, E2 and E5 and regenerates no generated file, so it may run beside F; its ProblemEditorScreen.tsx, ProblemWorkspace.tsx and ProblemListScreen.tsx slices go through one queue and rebase on whichever F slice landed first; G2 waits for checkpoint E's hosted run.
- The classic path is deleted only after the owner has used the console on the phone: clients move first (new twin flow tests, the Lua scripts), then the default flips in the same commit that pins the classic originals to off, then the old rows, card and E5's line-oriented input helpers go (expand, migrate, contract).

## What the recording does not show, and the default taken

- The Submit result screen, the Accepted state and the Wrong Answer and Time Limit Exceeded layouts are not in the recording. Default: the Run Result tab's own layout (headline, counts line, error box or Input/Output/Expected cards, Last Executed Input), with Accepted showing n / n testcases passed and the runtime sum and no 'beats x percent' (nothing to compare against offline). Why: one layout for every verdict, built from the cards the recording does show.
- Adding and editing a case, and what the pencil does, are not shown. Default: `+` copies the selected case and selects it; the pencil makes an editable copy of a bundled case or focuses the first field of a custom one; Delete case sits under the fields of a custom case; bundled cases are never mutated. Why: bundled cases carry their expected values, so editing one would create a case with a stale expectation.
- The round reset icon in the action bar versus the 'Reset' pill in the sheet: the recording shows both and never taps them. Default: one action, reset testcases, in both places; 'Reset code' moves to the header menu. Why: a testcase reset is harmless on a bare icon; the code reset keeps its confirm route and history snapshot. One handler swap if LeetCode's icon means 'reset code'.
- Whether Run runs the selected chip or every chip. Default: the selected chip, because the recording's Last Executed Input is the selected Case 3 (`s = "()"`); planRun takes a scope argument so every chip is a one-line change.
- Light versus dark: the recording is dark only. Default: every colour is a theme token (`$background`, `$color2`, `$color3`, `$borderColor`, `$success`, `$warning`, `$destructive`; animated styles read `.val` from useTheme), so light is derived, and the flow goldens prove both; the browser e2e golden is light only (no colour-scheme option on `wf browser test`; a flag on that runner is a clis change outside this section).
- Tablet, landscape and desktop web: not shown. Default: phone portrait only; the sheet stays 70% of the root with a scrolling body and no tablet layout; the browser e2e runs the phone device frame.
- Sheet height, rise and slide timings, the scan sweep period and the pulse rate are not measurable from a 2 fps contact sheet. Default: 70% of the screen root (sheet top at 35% of the screen in the frames; 62% would have put it at 45%), gorhom's own rise, a 180 ms thumb slide, a 1.4 s scan sweep and a 0.9 s dot pulse; the phone retunes them.
- The blur behind the Pending card is clear in the recording. Default: not in v1 (no blur dependency exists in the repo): scrim plus translucent card; slice G8.5 adds expo-blur if the owner wants the look. Android blur is costly, so it falls back to the scrim there.
- Whether the editor strip above the open sheet is interactive. Default: yes, and focusing it closes the console (the recording's t 9 s: tap the editor, keyboard up, bar back). ## Risks

- The sheet is a non-modal gorhom sheet over the lower part of the editor WebView: on Android a touch-claiming sibling can cancel the WebView's touches at the first MOVE (decision 18). The sheet covers only its own region and the editor strip above is untouched, and the Pending scrim exists only in flight, but only a phone or the emulator shows the interplay. On web gorhom's container covers the whole root unless the DS makes it box-none (G3.2); the flow stub cannot show that, only the browser e2e step that taps the editor above the open sheet can.
- gorhom's pan-down has never been driven in the web export (the gap note wf-browser-swipe-needs-frames says touch swipes depend on the render mode), the flow stub ignores gestures and onClose, so drag-to-dismiss is proven only if the export or the emulator answers the swipe in G8; otherwise it is the phone's.
- The chip row scrolls horizontally inside a sheet that sits under ProblemWorkspace's tab-swipe PanResponder (dx over 20 and larger than dy claims it) and gorhom's pan: the swipe lock while the console is open is a one-line predicate that jsdom cannot test, and a plain horizontal ScrollView inside a sheet with content panning on is unproven on Android; the phone checklist covers both, `disableContentPanningGesture` is the fallback.
- Resizing the editor above the open sheet (bottomInset = 70% of the root, zone minimum 96) relayouts the WebView at open and close and may jump while the sheet rises; if it shows, the inset is applied when the sheet settles instead of on mount. A field focused in the sheet shrinks the room (decision 27) and the strip with it: the editor is not usable then and does not need to be.
- Vertical room: with the keyboard up the bar (about 56), the symbol rail (about 50) and the action rail (about 50, plus F2's cursor pad) sit over the keyboard; on a 667 pt phone that leaves little editor. The open choice is to drop ActionToolbar's keys while the console is on; the owner decides after the phone check. The taller rail also covers the part of the language row that five Lua scripts tap to lower the keyboard (G9.3 fixes the helper).
- Reanimated and gorhom are inert in the flow harness, so motion (rise, thumb slide, scan sweep, dots) is asserted only as end state and rendered style; the browser e2e and the phone are the only judges of feel.
- The timeout classification reads judge text.
