Planned 22 Nov 2026 by a read-only reader of the code, checked against the issue (Decisions 1 to 47, sections A to E). The issue body (#86) holds the decisions and the item state; this file holds the slice-level plan: files, tests and what proves each slice. Shorthand: `L/` is `frontend/mla-tamagui/features/leetcode/`.

## Summary

JavaScript runs on the device in a Web Worker the hidden runner page starts for each run. The worker's main script is the learner's code behind a one-line harness prelude. There is no eval wrapper, so top-level `var`, `function` and `class` behave as on LeetCode's Node. The same line-1 trick keeps the learner's line numbers exact. A syntax error or a module-level throw reaches the page as the worker's standard ErrorEvent (message, lineno, colno). A runtime error in a case is read from its stack frames that name the script's own blob URL. This is how `error_at` works on V8 and on JavaScriptCore without engine-specific wrapper tricks. A boot self-test checks that both mechanisms work on the engine at hand, and `error_at` is left out where they do not. A Worker is the only thing that can stop `while(true){}`: the page `terminate()`s it at the case deadline, even through a `try{}catch{}` loop, which closes for JavaScript the gap in `docs/gaps/pyodide-bare-except-defeats-the-deadline.md`. In the browser export the hidden page shares the app's thread, so an in-page loop would hang the tab for good. There is therefore no in-page fallback: a WebView that cannot start a worker makes JavaScript Run Local report `unavailable` at stage boot. The harness copies the semantics of `judge.py` (arguments in key order, in-place parameter by name, compare modes exact, sorted, setOfSorted and approx, ListNode, TreeNode and graph shapes, design and round-trip harnesses, per-case stdout, module-level output in case 1, a 256 KiB cap, the per-case and whole-run limits and their messages). The named divergences are JS value rules (undefined, NaN, -0, BigInt, Set and Map), timeouts that carry no `error_at`, and a restart that resets module state. The existing Pyodide runner engine is generalized (a pure move) into `data/runner/pageRunner.ts`. Both adapters are configs over it, and a router sends a run to the runner of its language. The JS page is a new generated file with its own `build:js-runner` and `check:js-runner` gate (about 30 KB, against Pyodide's 12.9 MiB). The catalog has 76 problems, all with JavaScript starters and shared bundled cases. 75 of 76 starters are `var name = function` rather than `class Solution` (only two-sum is a class), and the backend's `rs/harness/node.js` can only call `class Solution` methods with unbuilt values, so the backend cannot score JavaScript. JavaScript therefore routes to the device whatever the Run Local setting says, but only in the last behavior slice, after 75 JavaScript reference solutions pass the shared cases (B3 and B5 pattern). Until then nothing in the app can reach the adapter. 19 slices: 5 independent starters, 5 harness and runner slices, a gate, 5 reference batches (cheap-model work), the flip, and the proof tiers.

## Open choice and the default taken

Run each JavaScript run in a Web Worker whose main script is the learner's code behind a one-line harness prelude, with no in-page fallback. The other choice is to evaluate the learner's code with an eval wrapper in the page's own realm, with a fallback for a WebView that has no Worker. It would hang the browser export's tab and a phone's hidden page on an infinite loop, and it needs engine-specific code to find syntax-error lines. If the owner wants a fallback anyway, it is a native-only 'inline' engine behind the same engine interface (workerEngine's spawn seam), about 40 lines, with only the app-side hard limit as its stop.

## Decisions this plan proposes

- JavaScript runs in a Web Worker that the hidden runner page starts for each run, and never in the page's own realm: only a Worker can be terminated out of an infinite loop, and in the browser export the page shares the app's thread, so an in-page loop would hang the tab; a WebView that cannot start a worker makes JavaScript Run Local report unavailable at stage boot, with no in-page fallback.
- The worker's main script is the learner's code behind a one-line harness prelude (the harness configuration is on that line too), so there is no eval wrapper, top-level var, function and class behave as on LeetCode's Node, the learner's line numbers are exact, and a syntax error or a module-level throw arrives as the worker's own ErrorEvent with its line and column; a leading 'use strict' directive is therefore not honoured (named divergence).
- A runtime error in a case is located from the stack frames that name the script's own blob URL (V8 and JavaScriptCore formats), and a boot self-test checks that the event and stack mechanisms work on the engine at hand: where they do not, error_at is left out, because a wrong highlighted line is worse than none; a timeout carries no error_at.
- The JavaScript harness copies judge.py's semantics (arguments in key order, in-place parameter by name, compare modes exact, sorted, setOfSorted with the outer order kept, and approx, ListNode and TreeNode and graph shapes, design and round-trip harnesses, per-case stdout, module-level output in case 1, the 256 KiB cap, the 5 s case and 30 s run limits and their messages); the backend's rs/harness/node.js is read and not changed, and is only a differential on the class-Solution subset.
- JavaScript value rules: undefined becomes null; NaN, Infinity and -Infinity are shown as their text and never equal or approx-equal a finite value; -0 equals 0; a BigInt is a number when safe and digits otherwise; a Set, Map, function or class instance is shown by String and fails against an array, as Python's default=str does; console.log, info and debug go to stdout and warn and error to stderr, with strings raw and other values as compact JSON.
- The harness finds the callable the way the catalog's JavaScript starters write it: a class named className (default Solution) that has the method wins, with a fresh instance per case; otherwise a top-level function of that name; otherwise a compile-kind error 'No Solution class or <name> function defined'. ListNode, TreeNode and _Node (also Node) are provided as configurable globals, and a definition of the same name in the learner's code is the one the harness builds with.
- The on-device runner engine becomes data/runner/pageRunner.ts and both adapters are configs over it, with a router that sends a run and a warm-up to the runner of its language; log events become device_runner.* with an engine field. The other choice, copying the 300-line state machine for JavaScript, was not taken: it leaves two engines to fix every limit and discard bug in.
- The JavaScript page is its own generated file with its own build:js-runner and check:js-runner pair, Nx target and staged and drift gate, mirroring check:pyodide; it costs about 30 KB per update against Pyodide's 12.9 MiB. The other choice, extending check:pyodide to build both pages, needs one is_pyodide_input line but ties the two pages' caches and failure messages together.
- JavaScript always runs on the device, whatever the Run Local setting says, because the backend's Node harness can only call class Solution methods with unbuilt values and 75 of the catalog's 76 JavaScript starters are 'var name = function'; this extends decision 42's routing rule and supersedes decision 26's 'only Python goes to the device'. It ships in the last behavior slice, after the 75 JavaScript reference solutions pass the shared cases, so nothing in the app reaches the adapter before then.
- The JavaScript reference corpus is 75 files under data/javascript/__tests__/fixtures/references/javascript, checked by the same bundled cases that independent Python references and brute-force oracles already validated, so there are no JavaScript oracles; group-anagrams stays the one pinned exception, and a shrinking PENDING_REFERENCES list names what is missing until it is empty.
- The folder tree of item F1 is posted before F1.2 moves any file (the structure rule of the architecture doc): data/runner becomes the shared on-device runner capability, data/javascript the new one, and data/pyodide shrinks to Python; proceeding with this tree, and a redirect is a new numbered decision.

## Risks

- R1, workers on the phones: Blob-URL workers from the hidden page are proven only in Chromium (the browser export) and on the CI Android emulator; iOS WKWebView with an html page and no real origin may refuse them. Mitigations in the plan: the page loads as html with baseUrl https://localhost/ (the JS page needs no assets, so it avoids the file-URI path the Pyodide page needed), the spawn falls back from a blob URL to a data URL, and a failed boot probe is a typed unavailable error at stage boot. If iOS refuses both, JavaScript Run Local on iOS says so and the follow-up is the owner's call.
- R2, error lines on JavaScriptCore: the ErrorEvent path is standard, but the stack-frame format on JavaScriptCore is covered only by captured samples in a unit test. The boot self-test turns lines off per engine instead of reporting a wrong line. The ErrorEvent path itself is proven only at the browser and Android tiers, because the Node unit adapter normalizes Node's own error format.
- R3, the extraction in slice 2 touches the Pyodide runner, which has Android and browser evidence. Guards: the 18 engine, 3 real-Pyodide and 7 device-runner tests move and must pass unchanged, the generated pyodidePage.ts must stay byte-identical, the log-name rename is one test, and the slice lands before any new file exists so nothing moves twice.
- R4, generated files: jsPage.ts is a third generated file. Every slice that touches data/javascript sources or @lib/webview-rpc after slice 9 must regenerate it, and a webview-rpc change regenerates cm6Bundle.ts, pyodidePage.ts and jsPage.ts together; those pushes are serialized (decision 44), and slice 9 must not land beside another bundle push. A rebase conflict in a generated file is resolved by regenerating, never merging.
- R5, the Rust gate edit (slice 9) touches clis/pipeline and clis/wf: cargo runs go under `flock /tmp/cargo.lock`, the machine is shared, and the pre-commit time for that slice is longer than the TypeScript slices.
- R6, the 64 new JavaScript references are content. A wrong reference shows as a failing golden, not a silent pass, and the shared cases are already validated by Python references and oracles, but cheap-model batches can still need several rounds; the ratchet lets each batch land alone, and a harness bug a batch exposes is fixed in that slice with the page regenerated.
- R7, semantic edges that the plan names rather than hides: a module-level cache resets when a timeout restarts the worker; an async function's promise is not awaited (LeetCode's judge does not either); a timer or promise from a finished case can raise later and is attributed to the case then in flight; a leading 'use strict' is not honoured because the prelude shares line 1; Node globals other than process.stdout.write (require, Buffer) are absent and give a ReferenceError row.
- R8, lint: the harness replaces console, which no-console flags, so it assigns through Reflect.set and needs no override; the one indirect eval that looks up a name at run time carries an oxlint-disable-next-line no-eval with its reason, as the backend harness does, if that rule is on for the frontend.
- R9, the shared engine keeps one known defect that this work does not fix: dispose() does not cancel an execute() already awaiting the page, so a run in flight can still reload the page after a dispose (docs/gaps/pyodide-bare-except-defeats-the-deadline.md); slice 19 files it as its own gap for both runners.
- R10, the hosted Android jobs cannot read the app's own log lines (the BetterStack config gap), so the boot probe's spawn and line results are not visible there; the Android script proves behavior (Accepted, a Line N chip, a TimeoutError) rather than the log.
- R11, a worker is started for every run (a few milliseconds to tens of milliseconds on a phone) and again after each timeout; the page itself stays warm, so JavaScript Run Local should feel instant, but no number is measured until a phone does it.

## What only the phone or the owner can show

- On an iPhone: open the EAS Update, pick JavaScript in the language picker on two-sum, press Run Local, and see whether the run starts at all. This is the Worker question for WKWebView with an html page (R1), and nothing in a session can answer it.
- On an iPhone and an Android phone: make a solution throw and see whether the card offers 'Line N' and the editor marks that line (JavaScriptCore's stack format and ErrorEvent behavior), then make one loop for ever and see a TimeoutError row for that case after about five seconds, with the next Run Local working at once.
- On a phone connection: how long from the tap to the card for the first JavaScript run and for the second (instant feedback is the goal and only a phone can measure it); the CI emulator gives timings, not a low-end phone's.
- The owner's call on two defaults that the plan chose: JavaScript always runs on the device whatever the Run Local setting says (decision 54), and the JavaScript page gets its own check:js-runner gate rather than sharing check:pyodide.
- Seeing the folder tree before slice 2 moves files (the architecture doc's rule): the data/runner capability and the moves from data/pyodide are the only place a redirect would change the plan.
