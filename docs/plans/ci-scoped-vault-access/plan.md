# CI-scoped vault access, identical on both runner kinds

Status: proposed, refined after audit 2026-11-08. Owner requirement (8 Nov): the self-hosted VM runner and GitHub-hosted runners use the **same CI-scoped Bitwarden machine tokens**, so both stay in sync; hosted runners are the point (free compute), tested first in the private repo (2000 free minutes). This is the middle path between today's state and the deferred broker (`docs/plans/secrets-broker/plan.md`); it replaces the "no secrets in hosted jobs" rule of `docs/plans/public-mirror/plan.md` for the **private** repo only. The public mirror holds no vault token.

## Decisions (owner, 8 Nov)
1. **Repo secrets with branch protection**, no protected environment. Both tokens are repo secrets.
2. **Public BetterStack values are repo variables** (`EXPO_PUBLIC_BETTERSTACK_TOKEN`, `BETTERSTACK_INGEST_HOST`), read as `vars.*`, marked `public` in `registry.json`; not vault keys.
3. **Existing CI OAuth client now** for the hosted tailnet join (tag `tag:ci-gh-hosted`); workload identity federation later.
4. **A GitHub repo token a job needs beyond `GITHUB_TOKEN` is a dedicated fine-grained token scoped to exactly that**, a `ci-deploy` key; never `VM_PROVISION_GITHUB_TOKEN`.
5. **Fix the runner-registration token exposure before any hosted runner goes live** (Wave 1, unit U1.5), not after.
6. **`vm-ops-api` listens on two ports.** A CI port serves only what a CI job needs (the `ci-deploy` signed calls: redeploy, status, health, cache and artifact routes); an admin port serves everything else and is reachable only from agent-shell. A token or signature valid on one port is refused on the other.
7. **Production images are built only by CI, in the CI runner.** The VM runner reaches a builder sidecar (its own docker daemon); hosted runners use the runner's local daemon. One composite action (`build-image`) hides the difference from the workflows. Nothing outside CI builds a production tag.
8. **`vm-ops-api` loses every build endpoint and script.** It only pulls, swaps and verifies an image CI already pushed. `agent-shell` may still build, in its own docker-in-docker, for development, and never into a production tag.
9. **The generic agent-shell exec-script route stays on the admin port only.** It is never reachable from the CI port or from a CI job.

## Measured today (names and counts only, 8 Nov)
- Deploy-read token reads 75 keys; the CI-read token (`BWS_GH_CI_SECRETS_READ_ACCESS_TOKEN`) reads 18, a strict subset.
- The 18 are privileged: OCI API key and passphrase, Tailscale OAuth client secrets, Expo token, Docker Hub credentials, the `vm-ops-api` signing seed. So "the CI scope" is not a safe credential today.
- The VM runner container (`infra/oracle-cloud/ci-runner/docker-compose.prod.yml`) holds the **deploy-read** token, so the two runner kinds cannot match, and the runner holds far more than CI needs.
- Keys outside the 18 that CI jobs plausibly read today (to confirm in Wave 0): build and Nx cache pre-signed URLs (some write-capable), the verification-artifacts URL (run-bundle publish, write), ORDS base URLs and passwords, the `vm-ops-api` token, request-signing keys, a GitHub PAT.
- Corrected by the Wave 0 scan (`docs/solutions/ci/job-secret-needs.md`, code only, no credential used): a job on the runner reads 48 keys of the deploy-read project and 5 of the CI-read project (the five Tailscale keys), 53 in union, all in `registry.json`. Of those, 8 are in the `ci-open` list below and 11 in the `ci-deploy` list; **34 are in neither**: the ORDS password and BetterStack ingest values read by almost every job (3), the two app-baked BetterStack values (2), test-code keys of the verification jobs (7), the Gem sync pair (2), and 20 read only because a deploy leg verifies its service's whole group from the runner. No job reads any `OCI_*` key, so 13 of the CI-read project's 18 are unused by workflows or reached through the read fallback (`backend.rs:352-356`); a live listing settles which. `registry.json` has 80 deploy-read keys against the 75 measured live.
- The scan also corrects three claims: `VM_PROVISION_GITHUB_TOKEN` is read on the runner by the `vm-ops-api` and `reporting-service` deploy legs (the `ci-runner` group check is in `wf vm terraform preflight`, not `wf ship`); write URLs are loaded in every run, not only on `push` to `dev`; and `tailscale-rotate-auth-key.yml` uses an edit-capable vault token secret this plan did not list.

## Audit findings (what the first draft got wrong or missed)
Each finding changes a unit below.

1. **Branch protection must not require PRs.** The workflow is direct pushes to `dev` (the owner rule, plus bot commits such as the test-report commits). A required-PR rule would block both. Use a ruleset that blocks force-push and deletion on `dev` and `main`, with no PR requirement.
2. **The tailnet join is itself a secret that cannot come from the vault.** A hosted runner needs the Tailscale OAuth client to join the tailnet; the vault is reached over the public Bitwarden API, not the tailnet, so there is no cycle, but the join credential must be a GitHub secret, not a `ci-deploy` vault key. Use a **dedicated** OAuth client for hosted runners, scoped to `auth_keys` write with only `tag:ci-gh-hosted` allowed, not the broader client stored in the vault. It is the third GitHub secret.
3. **Two "low-impact" claims were wrong.** The build-cache and verification-artifacts pre-signed URLs include write URLs (bearer, expiring, prefix-scoped). Writing a cache from a job that ran untrusted code is cache poisoning. Rule: write URLs are used only on `push` to `dev`; PR and dispatch-from-other-ref jobs get read URLs only (`wf` already gates cache reads on "on dev"). Prefix-scoped, expiring PARs, rotated on a schedule.
3b. **The GitHub PAT (`VM_PROVISION_GITHUB_TOKEN`): checked, no conflict, with one existing exposure.** Where it is read today (code scan, 8 Nov): `vm-ops-api` and `wf ship`'s remote builds (`clis/deploy/src/build_image.rs`, run on the VM, to clone the repo), `reporting-service` (`CI_RUNNER_GITHUB_READ_TOKEN`), `agent-shell`, and the `ci-runner` container as `ACCESS_TOKEN` to register itself. No workflow step reads it; the only CI-side touch is the `wf ship` preflight, which verifies that the `ci-runner` group's keys are present (`clis/deploy/src/infra/preflight.rs`). Its registry entry describes it as a fine-grained token with Contents=Read only on this repo, while `docs/runbooks/health-alerts.md` says Actions and Administration read and `docs/plans/github-access-broker/plan.md` says Administration write: the live scope is unverified (Wave 0). Consequences: (a) it stays out of both CI scopes; (b) jobs use the workflow's own `GITHUB_TOKEN` for any GitHub call; (c) if a job turns out to need a repo token beyond `GITHUB_TOKEN`, mint a **dedicated fine-grained token** scoped to exactly that (owner decision, 8 Nov), as a `ci-deploy` key, never this one; (d) the runner registers itself with this token as `ACCESS_TOKEN` in the `ci-runner` container env, where every job on that runner can read it, together with `VM_OPS_API_AUTH_TOKEN` and `VM_GATEWAY_AUTH_SEED` (`infra/oracle-cloud/ci-runner/docker-compose.prod.yml` L66-72): this exposure exists today and is fixed first (decision 5, U1.5).
4. **Vault values are not auto-masked.** GitHub masks only registered secrets; a value fetched at runtime by `wf secret get` prints in logs. `wf secret get`, `sync-env` and `verify` must emit `::add-mask::` for every value they resolve when `GITHUB_ACTIONS=true`.
5. **Generated `.env` files can leak through artifacts.** `wf secret sync-env` writes `.env` in the workspace; any `upload-artifact` or cache step of a path containing it leaks it. Add a check to `wf check --budget` that no workflow uploads `.env*`, and keep `.env` out of caches.
6. **ARM and arch.** `ubuntu-24.04-arm` is not free for private repos. Use `ubuntu-latest` (x64) for the private test. The VM `wf` is a static aarch64 musl build published to `/opt/clis/current` and mounted by the VM's containers: the `clis` job's **publish step stays VM-only**; hosted jobs build their own x64 `wf` for testing.
7. **Per-app groups already exist.** `clis/secrets/src/secrets/groups.json` lists required and optional keys per app (`leetcode-backend`, `remote-chat-agent`, ...). Scope is an orthogonal field on each key in `registry.json`; do not duplicate the groups.
8. **Parity gate must not mask a real difference.** Comparing hashes of key names per scope proves visibility, not equivalence of values; also compare a keyed hash (HMAC with a per-run nonce) of each value read on both runner kinds in the same run, so a stale or divergent value is caught without printing it.
9. **Rotation order.** Rotating OCI, Tailscale or signing keys breaks Terraform, the VM and the GitHub secrets together; rotate one value at a time, and update the vault and the GitHub secret in the same change.
10. **Rate and cost.** Many `wf secret get` calls per hosted job hit the Bitwarden API from cold runners. Fetch once per job (`wf secret cache` exists) and measure calls per job in Wave 3.
11. **Supply chain in the private repo.** Any workflow on `dev` reads both repo secrets. Pin every third-party action by commit sha (`tailscale/github-action`, `actions/cache`), minimal `permissions:`, and add the pin check to `wf check --budget`.

## Two-port vm-ops-api (U1.6)
Today one listener serves redeploy, build, status, the cache and artifact routes and the agent-shell exec-script route under one auth scheme, so a CI job holding the signing seed could reach all of it. Split it (decisions 6, 8, 9):
- **CI port**: signed requests of the `ci-deploy` scope only: redeploy of a tag CI already pushed, redeploy status, health, the cache and artifact routes. It has **no build route** (U1.7 removes them first, which is why phase 2 precedes phase 3).
- **Admin port**: everything else, including the generic agent-shell exec-script route; bound so that only agent-shell can reach it (the tailnet ACL and the listen address both say so), with its own token. `wf` verbs run from agent-shell use it; CI never holds its token.
- Files: `backend/vm-ops-api` (listener and router split, one auth check per port), the compose file and `infra/tailscale/policy.hujson` (the CI port is the only vm-ops-api port `tag:ci-gh-hosted` and the runner may reach), `clis/wf-vmops` (port per verb). Tests: flow test per route per port (a CI-port request for an admin route and the reverse are refused, each asserting the request arrived); deployment verification from the runner container against both ports.
- **Status (phase 3, first part, code only, nothing deployed, nothing applied):** done in `backend/vm-ops-api`, `clis/wf-vmops`, the compose file, `infra/tailscale/policy.hujson` and the registry. Naming: the existing seed of vm-ops-api is `VM_OPS_API_AUTH_TOKEN` (not `VM_GATEWAY_AUTH_SEED`, which gates the removed gateway and leetcode-backend); it is now the ADMIN seed, scope unchanged until Phase 6. The CI seed is the new `VM_OPS_API_CI_AUTH_TOKEN` (scope `ci-deploy`, required in the `vm-ops-api` group); the signing key pair is shared, so the seed is what separates the ports. `CI_PORT` (8081, `.env.defaults`) opens the second listener; unset leaves it off; the service refuses to start with `CI_PORT` and no CI seed, the admin seed as the CI seed, or `CI_PORT` equal to `PORT`. ## Sharing the builder between agent-shell and the CI runner
Docker has no per-client permission: whoever reaches a daemon's socket or TCP port is root on that daemon, can read every image and layer and can tag or push anything. So a shared builder cannot separate agent-shell from CI jobs. Use **two daemons, enforced by credentials**, not one daemon with a policy:
- agent-shell keeps its own docker-in-docker daemon; it holds no registry credential that can write a production tag.
- The CI builder sidecar is reachable only from the runner's compose network, and the production-tag push credential (Docker Hub token) exists only in `ci-deploy` as job step env, so only a CI job on `push` to `dev` can push one.
- The credential, not the daemon, is the boundary: a build on either daemon can produce an image, only a CI job can publish it under a name the VM will pull.

## Research: arm64 and billing (8 Nov)
- The VM is aarch64 and its images are arm64; a hosted `ubuntu-latest` job is x64. A hosted build of a production image needs either an arm64 runner (`ubuntu-24.04-arm`) or an emulated or cross build (slow; the cross path is not proven here). Hosted jobs that only test can stay x64 (finding 6).
- `ubuntu-24.04-arm` is free for public repos but billed for private ones; the private repo's 2000 free minutes are Linux x64 at 1x, and per-minute multipliers and rounding up per job apply. Treat the arm price and multiplier as unknown until the U0.3 measure below; until then image builds stay on the VM runner's builder sidecar, and hosted runners run test jobs.
- **U0.3 minute measure**: `.github/workflows/hosted-minutes.yml` (`workflow_dispatch`, input `runner`, no secrets) runs one small cargo job per runner and prints runner, arch and elapsed seconds; the procedure and stop rule are `docs/solutions/ci/hosted-minutes.md`. Numbers go into U3.5 before any default moves.

## Risks
- **The CI scopes are broad until split.** Run nothing untrusted on hosted runners before Wave 3 narrows what reaches them; this plan runs only trusted `dev` code in the private repo.
- **Any workflow on `dev` reads the repo secrets it is given.** Mitigations: step-level env, sha-pinned actions, minimal permissions, rulesets on `dev`.
- **Hosted runners are third-party VMs.** Secrets pass through GitHub's infrastructure, as for any GitHub secret; accepted for the private repo, which is why the public mirror stays secret-free.
- **Minutes.** 2000 Linux minutes at 1x; macOS and larger runners burn faster or are unavailable; Wave 3.5 measures first.
- **Rotation blast radius.** Touches Terraform, the VM and the GitHub secrets together; do it last, in order.
