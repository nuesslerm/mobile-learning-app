# RCA parity plan: T3 Code and Orca over one agent API

Status: plan, 3 Nov 2026. This plan adds to `docs/plans/rca-client/architecture.md` and `docs/plans/rca-client/protocol.md`. It does not replace them. The owner's method names, event model and group rule in `architecture.md:12-20,41-57` stay authoritative. Anything this plan adds beyond them is either an addition with the same shape or a §7 owner decision. The design is fixed by the owner. This plan covers order, crate layout, ports and measurement only.

## 1. Goal and done-when

The rca service (`backend/remote-chat-agent`) serves one app-neutral agent API on `/agent/v1/socket`. Two mappers translate a phone app's wire to that API: `t3 serve` (`clis/t3-serve`) for T3 Code, and a new `orca-serve` (`clis/orca-serve`) for Orca. Every file, git, process and terminal action runs in `rca-exec` (`clis/rca-exec`) at the workspace. Nothing in the service touches a workspace filesystem (`architecture.md:52`).

**Parity, per app.** In a generated coverage table, every phone method, `dispatchCommand` type, `projects.mutate` type, HTTP call and subscription is a row in exactly one of three states:
- `served`: answered functionally. The row names a test that passed in the latest published run bundle (`wf test publish`, `verification/test-runs/index.json`), and the mapper's method-hit trace from that run shows the test called this method.
- `not-offered`: the owner decided so, with a reason, a "decided by" milestone and a stable refusal. T3 refuses with `UnsupportedOperationError`. Orca refuses with `{ok:false,error:{code:"not_offered"}}`.
- `pending`.

Parity for an app is reached when no row is `pending`.

**The method sets come from the reference sources, not from a hand list.** Every count below is an estimate from the static survey. The generator (§5) gives the real numbers, and each milestone quotes the generator's number, not one added up by hand.
- **T3:** `references/t3code` at v0.1.6 (`tooling/t3-conformance/t3-pin.json:2-4`, commit 2359643c). The survey estimates:
  - 136 of the 208 catalog RPCs are reached from `apps/mobile` and `packages/client-runtime`;
  - 36 `orchestration.dispatchCommand` types;
  - every `projects.mutate` type the phone sends, each its own row (`project.delete` is one; `clis/t3-serve/core/src/domain/command.rs:18` accepts only create, update and archive);
  - HTTP rows: `threadHistoryPage`, `threadTranscript`, the peer pairing-code mint (`cr/state/peerPairingCode.ts:82`), and the HTTP side of `attachments.createUploadUrl` and `assets.createUrl`.
- **Orca:** `references/orca` pinned to a SHA (dc7cd7be, v1.4.214, `tooling/orca-conformance/orca-pin.json`).
  - The rows are the phone's call sites intersected with the host's `defineMethod` registry. That settles the method-list source, which `architecture.md:54` gives as the mock handler list and `:62` as the host registry. This plan fixes `:54` to match `:62`.
  - The survey estimates 289 methods: 286 shipped and 3 behind `ORCA_SIDEBAR_INPUTS_IS_MAIN`. The 3 flagged rows are counted as a separate "flagged" class: tracked, but outside the parity target until the flag ships.
  - The audits disagree on the allowlist size (350 vs 354 entries); the generator's count settles it.
  - The E2EE handshake, `pairing.provisionRelay`, the three `mobileWeb.bundle.*` methods and the two HTTP endpoints (`mobile-relay-resume-director.ts:45`, `connection-diagnostics-submission.ts:25`) are rows too.

**Today:**
- `t3 serve` answers 13 RPCs (`clis/t3-serve/contracts/src/rpc.rs:8-22`), 12 of which the phone uses. They were tested only against `ScriptedHost`, and five of them (`getThreadProjection`, `projects.listEntries`, `projects.readFile`, `projects.writeFile`, `filesystem.browse`) were never recorded from real T3. So the baseline table marks all 12 as `pending`. M3 re-verifies them through the real `rca-exec` and records goldens.

- Orca: 0 methods served.
- The agent API serves `service`, `state` and `files` (`backend/remote-chat-agent/core/src/agent_api/mod.rs:12`). `workspace.list` is served but its group is not listed (`agent_api/mod.rs:42`, `architecture.md:55`).

**Done when:**
- Both coverage tables show 0 `pending`.
- Every `served` row meets the two-condition rule above.
- T3 goldens recorded from the pinned real server replay for every served tag, both at flow tier and end to end through t3 serve, the real rca-service and rca-exec (§5).

### Capability groups

**The rule.** `service.status` lists a group only when every method in it is served (`architecture.md:41`). Owner groups keep the methods the owner listed (`architecture.md:43-50`). New methods go into named sub-groups sized to one milestone, so no milestone ever advertises an incomplete group.
- An owner umbrella name (`agent`, `files`, …) is listed once all of its owner methods are served.
- A sub-group is listed when its own methods are.
- `files` stays listed with today's `file.read/list/diff`.
- `state` stays listed with `state.get/set`. `state.watch` is a separate sub-group.

**Mapper start check.** Each mapper's needed groups are generated from what it serves, never typed by hand: the adapter declares one list of the agent methods it calls (`USES` in `clis/t3-serve/src/adapters/rca.rs`), its calls and its start check both read that list, and the groups are those of the listed methods. A flow (`rca_agent`, "the groups a mapper needs are those of the methods it really sends") runs every operation of the port against a stand-in rca and asserts that the methods sent are exactly the listed ones, so a call added without being listed fails. So a mapper refuses to start only for what it actually serves (today `service`, `agent.threads` and `files`).

Owner names are kept: `catalog.get`, `service.status`, `thread.subscribe {thread, after_seq}`, `thread.history`, `approval.answer`, `input.answer`, and the neutral events of `architecture.md:19`. The draft's renames (`service.catalog`, `events.subscribe`, `item.*`) are dropped.

### Commands: service state vs app-local projection

`t3-core`'s decider (`clis/t3-serve/core/src/domain/decider.rs:86,239,271`) no longer decides thread lifecycle. Every lifecycle command is forwarded to an agent method, and the service engine decides it. `t3-store` keeps only:
- read-model caches rebuilt from agent events;
- T3-only fields the agent API does not model, if any. Candidates are pin order, active order and visits; whether these are device `state` keys or T3-only is settled per command in the M1 baseline.

The M1 baseline lists all 36 command types, each with a target (agent method, `state` key or t3-local) and a milestone:

### Events, seq and replay

- **One seq owner.** `rca-thread-core`'s engine already has a decider, a projector, sequence numbers and replaying thread and shell subscriptions (`core/src/application/engine.rs:1-3`, `core/src/domain/decider.rs:124`, `projector.rs:1-2`). The agent API's per-thread `seq` (`architecture.md:17`) is that engine sequence, and `thread.subscribe {thread, after_seq}` is a view over the engine log. A thread's events carry the thread, the turn and that seq on the owner's envelope, and their topic is `thread/<id>` (`agent_api_proto::Event::topic`), the stream `agent-api-client` resumes. No second event log is built for threads or the thread list.
- **Which engine, which events.** The agent API's threads live in an instance of that engine of their own (`<state_dir>/agent-api`, memory when no state directory is set), not the thread view's: the thread view's clients (`/ws`, `subscribeShell`) decode a closed set of event types and must never be sent an agent event. An agent event is one engine event of kind `thread.neutral-event` (`{turnId?, event: {type, ...}}`, the `ThreadEvent` of `agent-api-agent`), so the engine's number is its `seq` and a thread's numbers have the gaps the engine's other events leave (the thread's creation, the others' events). `thread.created` carries the thread's defaults (`workspace`, `driver`, `model`); the projector keeps them, the sequence of the thread's newest neutral event (`last_seq`, 0 for a thread with none) and the turn that runs (`turn.started` to `turn.finished`). `thread.subscribe` replays from the log and goes live under the engine's lock, so no event is missed or repeated between the two. A turn a crash left running is settled at start: the engine interrupts it in the thread's view and the adapter appends its `turn.finished {reason: interrupted}`.
- **Slow readers.** Every frame of a socket (answers and events) leaves through one bounded queue (4096 frames). A peer that stops reading overflows it and the socket is closed; the peer resumes from the last `seq` it saw (`agent-api-client` does). The replay of a `thread.subscribe` is the exception: its events are all in hand and the peer asked for them, so it waits for room, up to three quarters of the queue (the rest is for answers and live events), and a backlog longer than the queue is no stall. Flow `agent_threads` replays more events than the queue holds.
- **Non-thread streams.** These are not engine events: terminal output, git status, worktree setup progress, provider auth, schedule runs and service lifecycle.
  - Terminal replays by byte offset, as the owner set (`architecture.md:46`).
  - The others use a bounded, non-persisted per-stream seq owned by the group crate that produces them. A resume past the retained tail answers `{type:"reset", snapshot}`.
  - Their topic names and the reset event are additions, so they are owner decision 7.
- **Every phone subscription has a row**, which either maps to a topic or is marked mapper-local in the coverage table:
  - T3: `subscribeShell`, `subscribeThread`, `subscribePreviewEvents`, `subscribeDeviceState`, `subscribeProjectClones`, `pullRequests.subscribeRefreshes`, `scheduledTasks.subscribe`, `subscribeTerminalMetadata`, `subscribeCommandOutput`;
  - Orca: `agentSession.subscribe`, `terminal.subscribe`, `session.tabs.subscribe`, `nativeChat.subscribe`, `accounts.subscribe`, `notifications.subscribe`, `browser.screencast`, `clientEvents.subscribe`.
- **Phone reconnects.** Each mapper keeps the last seq or offset per phone stream, so a phone reconnect replays without loss. Today the socket sends one reply per request and no events (`rs/src/api/routes/agent.rs:24-37`).

- **Executor-initiated events.** `protocol.md:9` has only request/reply plus request-bound streams, so `exec-proto` adds a `subscribe` action whose stream outlives the request. It carries git status, worktree setup, pty output after a re-attach, and preview events, each with a per-stream seq or offset. On executor reconnect the service re-subscribes with the last seq it saw. A `REPLACED` close (4001) ends all of that executor's streams.
- **Registry keyed by executor.** The registry is keyed by executor, and each executor holds workspaces: the repo root plus its worktrees. Confinement widens from the one root to `{root, worktree base}`, set by `rca-exec serve --root <dir> --worktree-base <dir>`. `workspace.create` and `worktree.create` route to the executor that owns the repo. This changes the `?workspace=<id>` keying of `architecture.md:24`, so it is owner decision 8.
- **The model's tool set stays separate from the app's action set.** `protocol.md:20` says a tool reaches a CLI only after functional tests. The MCP bridge `TOOLS` list (`core/src/exec/mcp.rs:12`) gains only `stat`, `read_chunk`, `create_file`, `git_status`, `git_log` and `git_blob`. `git_push`, `git_commit`, every `pty_*`, `hosted` and `preview` action, and `browse` are reachable only through agent API methods that an app calls. A test asserts the exact `TOOLS` list.
  - **Amended in M4 (proposed, awaiting owner confirmation):** the MCP server also lists two tools that are no executor action, `approval_prompt` and `ask_user`, after the seven (`rca_exec_channel::mcp::SERVICE_TOOLS`, asserted by the same test and by the flow `exec_remote`). The service answers them itself and never asks an executor: the call records `approval.requested` or `input.requested` on the thread and waits for `approval.answer`, `input.answer` or `input.dismiss`, whose answer is the tool's result, so a turn that ends first gets an answer that says so. `approval_prompt` is Claude Code's `--permission-prompt-tool`, which `command_for_remote` names (`mcp__executor__approval_prompt`) only in the runtime mode that asks (`approval-required`, not a plan); opencode and Codex have no such hook, so only `ask_user` reaches them. It is not tested against the real Claude Code, whose prompt-tool reply (`{behavior, updatedInput}` or `{behavior, message, interrupt}`) is written from its documentation.

### Per-provider credential isolation

Each provider gets its own directory on the service's persistent volume, `/data/providers/<provider>/`:
- Claude Code runs with `CLAUDE_CONFIG_DIR` pointing there.
- Codex runs with `CODEX_HOME`.
- opencode runs with `XDG_DATA_HOME` and `XDG_CONFIG_HOME`.

The environment rule is a pure function in `rca-cli-driver` (§3), with a test. It decides which variables survive for which provider. The spawn adapter stays in `rs/src/infrastructure/exec.rs`.

Login runs through `accounts` (`provider.auth.*`, device-code or paste flows), and the CLI writes its tokens itself. Keys for the extra model APIs come from `clis/secrets/src/data/registry.json`, and each entry is added before use. Jira and Linear credentials need the same placement decision as `gh`/`glab` (decision 4). Mappers see provider status, never a token.

### Auth on `/agent/v1`

Until M3 the socket authenticated with the service secret (`exec_remote::channel_authorised`). The owner design calls for one bearer per paired device (`architecture.md:14,53`). M3 adds, and the service half is built:
- a `DeviceBearers` port in `rca-agent-core` (the digest, the lookup and the rules over the records are its pure `bearers` module), with a store adapter on the volume (`rs/src/infrastructure/device_bearers.rs`: `~/.local/state/rca/device-bearers.json`, mode 0600, the SHA-256 digest of each 244-bit token and never the token);
- a mint flow, where the service secret is used by an operator, through `wf offload bearers mint|list|revoke` over `POST|GET /agent/v1/bearers` and `DELETE /agent/v1/bearers/{id}`;
- mapper credentials: each mapper holds only its own app pairing state and one rca bearer, never the service secret (`wf t3 serve` reads `T3_RCA_BEARER` and no service secret, and names its workspace with `--rca-workspace`).

**Who opens what.** A device bearer opens `GET /agent/v1/socket` and nothing else: the bearer endpoints and the executor channel (`/exec/v2/executors`) answer it 401. The service secret opens the executor channel, the bearer endpoints and the machine routes, and no longer the agent socket. `POST /exec/v2/turns` is retired and answers 404 to both. A service with no secret configured mints, lists and revokes nothing, so its socket stays shut. A revoke takes effect at the next connection; a socket that is open stays open until it closes.

## 3. Crate split for Nx cache efficiency

### Rules (checked by `pnpm run arch:services` plus a cargo-deps check over `clis`)

- **Ports.** A port lives in the crate that uses it, and its double ships behind that crate's `testing` feature (hexagonal-architecture-by-package-type.md:29,103).
- **No central routing tables in cores.** `rca-agent-core`, `t3-core` and `orca-core` each define a `Group`/`Area` trait (methods, scopes, handle, not-offered rows). The composition root (`rca-service` `main.rs`, `t3-serve`, `orca-serve`) assembles the routing and not-offered tables from the group and area crates. The `--api` export reads the assembled table.
- **Adapter libraries depend on nothing that consumes them.** `agent-api-client` is an adapter library (type 6) with a concrete client. Each mapper core owns its `AgentApi` port, typed in its own words. The composition root holds the thin adapter that implements the port over the client. `t3-core`'s `ExecutionHost` port is deleted (M3): `t3-core` owns `AgentApi` (`clis/t3-serve/core/src/ports.rs`: `ensure_thread`, `start_turn`, `interrupt`, `follow`, `history`, `list_dir`, `read_file`, in t3's own words and events), `RcaAgent` in `t3-serve` is the thin adapter over `agent-api-client`, and the area crates take their narrower ports from M4 on.
- **`exec-testkit`** is only ever a dev-dependency, of `rca-service`, `rca-exec`, `rca-cli-driver` and `t3-serve` (its integration chain); `cargo_deps` checks it. It is not a wire contract: it starts processes and writes files, so the `contract-crate-does-no-io` rule and the purity registry leave it out, as they do `agent-api-client`.
- **Golden and recorded fixtures** live under `tests/fixtures/` or a data directory named only in `[package.metadata.flow] inputs`. They are never in `rustProduction` (`nx.json:56-60`), because dependants hash `^rustProduction` (`cargo-crates.js:142-152`).

### Fixes to `tooling/nx/cargo-crates.js` (M1)

1. **Crates inside a pnpm package get their own projects.** Today they are folded in (`cargo-crates.js:128-137`). Add an opt-in key `"nx": {"cargoCrates": true}` that emits `crate-<name>` projects with `cargo-clippy` and `cargo-unit`. Also override the rca package's `test:flow` and `test:integration` inputs: they use `default` = `{projectRoot}/**/*` today (`nx.json:35-38,127-140`), and become `rs/**` plus `^rustProduction` of the crate projects.
2. **Nested crate roots leave the parent's `rust` input.** Today `crate-t3-serve` hashes `clis/t3-serve/core/**` and its other sub-crates.
3. **Flow groups.** Add `[package.metadata.flow] groups`, which exist today for e2e only (`cargo-crates.js:218-244`; flow is one target per crate, `:201-203`). The rule is one `tests/flow/<area>.rs` per area or group crate, keyed on that module plus that crate's `^rustProduction`. It is used by `t3-serve` (per `t3-*` area), `orca-serve` (per `orca-map-*`), `rca-service` (per `rca-group-*`) and `rca-exec` (per family).
4. **Hash each crate's own slice of `Cargo.lock`.** Today every target hashes the whole lockfile (`cargo-crates.js:150,171,193,234`). 5. **Explicit cross-package edges.** The rca-service flow that spawns `rca-exec` declares its edge. Today an edge exists only when a package script runs `cargo -p <crate>` (`cargo-crates.js:254-269`).
6. **Fix the stale comment** at `cargo-crates.js:99`.

A planted-change test in `clis/pipeline/tests/nx_contract.rs` covers fixes 1-5. That suite runs only because `tooling/nx/**` changed, and it takes minutes (`cargo-crates.js:211-217`). M1 is costed for it.

### wf router

`wf` path-depends on `t3-serve` and `rca-exec` (`clis/wf/Cargo.toml:19-20`), so every mapper or executor change reclippies the whole wf graph. The plan:
- `orca-serve` is never added to `clis/wf/Cargo.toml`;
- in M1, `t3-serve` and `rca-exec` move to ship as their own thin binaries (`t3-serve`, `rca-exec`), which `wf` dispatches by name;
- each crate's flow tests already enter through its thin binary, and `WF_BIN` parity covers the router path.

It could not, so M1 added that dispatch (`clis/wf/src/external.rs`): `wf t3|exec ...` runs `t3-serve`/`rca-exec` in place of wf, found beside it, else on PATH, and install-wf installs all three.

## 4. Tests and tiers

- **rca-service flow (per group).** Drives `/agent/v1` with the real `rca-exec` binary on a temp git repo and the scripted CLI from `exec-testkit`.
- **Mapper flow (per area).** Runs through `t3-serve` or `orca-serve` against an `AgentApi` double driven by the per-group contract fixtures. This keeps the mapper flows off the rca-service edge. It is a double of an external dependency, as the flow tier requires, and not a stubbed feature.
- **Integration.** A `tests/integration.rs` per mapper (its `cargo-integration` Nx task, one test at a time) runs the chain mapper → real rca-service → real rca-exec → scripted CLI as built binaries, and nothing is doubled but the model. It is keyed on both sides: `[package.metadata.integration] uses = ["rca-service", "rca-exec"]` adds those crates' sources, their workspaces' manifests and cargo config and their lockfile slices to the task (the flow task reads none of them), and `inputs` the files the chain names its rows from. This is the black-box parity tier for every `served` row, and it records the method-hit trace.
  - **The chain.** `clis/t3-serve/tests/integration.rs` starts the service, attaches the executor to a temporary git repository, mints a device bearer, starts `t3-serve serve` with it, and drives the T3 wire as the phone does: the HTTP pairing and auth calls, then the Effect RPC socket, a second socket for the streams it keeps open. The executor and the mapper reach the service through a `Tap`.
  - **The trace.** Each wire call is a window on the tap (`Case::call`): the agent API methods and executor tools that were answered while it ran, with the coverage rows the call exercises. A test that sends a message waits for the run to end inside the window, so the window holds the whole turn. A test asserts where a call went: the message test asserts that `{tool: write_file, ok: true}` is in the message's window, so a write that did not go through rca-exec (a shortcut through the service's filesystem) fails it. Every row a test names is checked against the reference scan's methods list.
  - **The output.** After each test the suite writes `$WF_TEST_OUTPUT_DIR/t3-serve-integration/report.json` (a harness run record, schema 1, `platform: integration`, `error` until every test of the binary has run) and `trace.json` beside it:

    ```json
    {"schema": "method-trace/1", "app": "t3", "suite": "t3-serve-integration", "sha": "<commit>", "complete": true,
     "tests": [{"test": "chain::a_message_runs_...", "verdict": "pass", "ms": 1142, "calls": [
       {"rows": ["rpc:orchestration.dispatchCommand", "command:message.dispatch"], "ok": true,
        "agent": [{"method": "thread.create", "ok": true}, {"method": "turn.start", "ok": true}, {"method": "thread.subscribe", "ok": true}],
        "executor": [{"tool": "write_file", "ok": true}]}]}]}
    ```

    `ok` of a call says whether the wire served it (a refusal is `ok: false`); a hit that failed also carries its `code`. `wf test publish` lists every `trace.json` of the run's directory in the bundle's `traces` (the bundle's schema stays 1: the field is an addition), and the CI step that publishes the integration bundles covers `t3-serve-*` beside `vm-ops-api-*`.
- **Deployment verification.**
  - One real turn per provider against the deployed rca, plus a credential-directory check on the deployed service (M3 and M10).
  - The orcad oracle (M5 onward).
  - A real test repository for `gh`/`glab`, if the owner agrees (M11).
- **Recorded CLI fixtures.** M3 writes the stream-json of Claude Code, Codex and opencode from their documented formats and from what `rca-cli-driver`'s `translate` reads, and `recordings.json` says so for each (`provenance: documented-format`): a run of the real CLI would use the host's own sign-in. Recordings from the real CLIs at pinned versions are pending (`docs/gaps/exec-testkit-recordings-not-from-real-clis.md`); they rerun when a pin or the recording scenario changes, and replace the written ones with no change to the tests that read them.
- **Real phone apps.** A per-milestone runbook, or an Android e2e in the CI emulator job, loads each pinned reference phone client against the deployed mapper. Every run publishes a recording and a report. Whether either app builds for the emulator is decided by the M1 spike.
- **Style.** Every test is Given/When/Then and asserts behavior: a file exists after `file.write`, `git status` changes after `git.stage`, a second provider cannot see the first provider's files.

## 5. Parity measurement

- **The coverage generator** is `wf parity coverage --app t3|orca`, in a new `clis/parity` crate dispatched by `wf`. It has two targets:
  - **reference scan:** keyed on `t3-pin.json`, the Orca pin and the scanner. It parses the pinned sources: T3 `WS_METHODS`, `ORCHESTRATION_V2_WS_METHODS`, command builders, `projects.mutate` types, and RPC, HTTP (fetch and URL builders) and subscription call sites under `apps/mobile` and `packages/client-runtime`; for Orca, the host `defineMethod` registry, `mobile/` call sites and HTTP calls. It writes checked-in method lists. It flags dynamic method names, Swift native-module RPCs and `bridge-host-requests.ts:69-73`, and it settles the 350/354 count. It runs in M1.
  - **coverage check (`cargo-flow`):** it does not path-depend on the mappers and does not parse `references/`. Its `[package.metadata.flow] inputs` are:
    - the checked-in method lists;
    - the per-area `--api` JSON exports (each area crate writes its own export in its build, so the check depends on the exports, not on every mapper crate);
    - the checked-in coverage JSON;
    - the checked-in evidence (`<app>-evidence.json`), which is the latest bundle's method-hit traces and pass list reduced to the rows they serve.

    It checks four things: the generated output equals the checked-in output; every `served` row has a passing test and a trace hit; every `not-offered` row has a reason and a "decided by" milestone; `pending` never rises. A pin-bump commit, tagged `parity: pin-bump`, may raise `pending`, and its milestone must list the new rows.
  - **Evidence.** A row is `served` only when `<app>-evidence.json` names it, and the file is written only by `wf parity coverage --app <app> --traces <dir|bundle>` from the method-hit traces of a chain run (§4). The rule, per trace, is:
    - the run is `complete` (every test of the binary ran: an aborted run is an error run and nothing in it counts);
    - the test passed;
    - the call is `ok`: a call that only gets a refusal never counts;
    - for a command or mutation whose target in the decisions file is `agent:<method>`, that method answered ok in the same call's window. A row whose target is `state:<key>` or `t3-local`, and every RPC and HTTP row, needs only its answered call.
    - A row the evidence names is served unless a `reverify` note holds it in `<app>-decisions.json`: the mapper refuses it or answers without doing it, and the note is removed in the commit that makes the answer functional and reverified through the chain. The evidence names the test (`suite`, `test`) and where its call went (`agent`, `executor`); among several tests that serve a row the one whose name sorts first is named, so a refresh names the same test whatever order the tests finished in.
    - `--check` fails on a decision that claims `served` without evidence (`served-without-evidence`), evidence for a row the table does not serve (`stale-evidence`), and a trace row the phone does not reach (`unknown-trace-row`, unless the decisions file lists it under `traceNoise` with a reason). Without `--traces` the checked-in evidence stands, so the flow check never needs the run; with it the evidence rows are compared with the run's (the provenance in the file does not count).
  - **Refreshing the table from CI's bundle.** CI's published run bundle is the evidence of record. The integration-tests job publishes `t3-serve-integration` as a run bundle (`wf test publish`), whose `bundle.json` lists the trace in `traces`. To refresh: take the bundle's URL from the job's log or from `verification/test-runs/index.json`, run `wf parity coverage --app t3 --traces <bundle.json URL or downloaded file>`, and commit `t3-evidence.json`, `t3.json` and `t3.md`. When the integration task replays from the Nx cache no new bundle is published and the last one stands. For a local refresh (what the checked-in tables of M3 were made from), run the chain with the three binaries built (`RCA_SERVICE_BIN`, `RCA_EXEC_BIN`, `EXEC_TESTKIT_CLI` name them, else the test builds each once) and `WF_TEST_OUTPUT_DIR` set, then pass that directory: `WF_TEST_OUTPUT_DIR=/tmp/out cargo test -p t3-serve --test integration -- --test-threads=1`, `wf parity coverage --app t3 --traces /tmp/out`.
  - Output goes to `docs/plans/rca-parity/coverage/{t3,orca}.json` plus a Markdown table. This replaces the unbuilt `clis/t3-serve/tests/coverage.json`.
- **T3 goldens.**
  - Extend the `tooling/t3-conformance` recordings from the pinned real server for each tag as it is served. Scenarios: turn, approval, queue, fork, files, terminal, vcs, PR, settings, scheduled, search, `projects.*`, `filesystem.browse`.
  - Recording reruns on the VM when `t3-pin.json`, the recorder or a scenario file changes.
  - Close the replay gaps:
    - compare the `capabilities.*` booleans (`conformance.rs:178`);
    - report extra replies (`conformance.rs:324-329`);

## 7. Risks and open owner decisions

**Decisions.** Each one has a "decided by" milestone.
1. **Not-offered sets** (by M5 for pairing, M7 for `aiVault`/`party*`, M12 for the rest). Candidates:
   - Orca: trackers, speech, notifications/push, browser automation, `aiVault`, `pairing.*` on desktop-paired phones; ssh is already not offered;
   - T3: `mcpApps.*`, `updateServer*`, `commitDesktopUpdate`, `provider.uploadFeedback`, device and preview. M12 proposed default (awaiting owner confirmation): all of these not-offered except preview, which is served (only `runtime: "server"` is refused); the full list with reasons is `coverage/t3-not-offered.md`.
2. **Codex as a remote driver** (by M3, from the M1 spike). `command_for_remote` (`backend/remote-chat-agent/cli-driver/src/domain/driver.rs`) turns builtins off. Whether Codex fully honours that (no local shell or apply_patch) is unknown.
3. **Provider credential storage** (by M10). The options are plain directories on the volume (proposed), encryption at rest under a vault key, or one uid per provider. Tokens the CLI refreshes must survive redeploys.
4. **Hosted and tracker credentials** (by M11).
   - `gh`/`glab`: with rca-exec at the workspace (proposed, because the executor's machine already holds the push credentials). Putting them on the service would break "the service never touches a workspace".
   - Jira and Linear: these are API-only, so either the service's secrets registry or the executor.
5. **Removed: the wf router question** (it was here in the draft). §3 now decides it: orca-serve stays out of `clis/wf/Cargo.toml`, and `t3-serve` and `rca-exec` move to binary dispatch in M1. The risk is that `wf` may not support external dispatch today, which is unknown.
6. **Contracts location** (by M2): `libraries/agent-api` (proposed: it gives the cross-side Nx edge) or vendored copies.
7. **Event additions** (by M3). These are additions beyond `architecture.md:17-19`:
   - non-thread topics and their per-stream seq;
   - the `reset` snapshot event (proposed: the thirteen events of `agent-api-agent`'s `ThreadEvent` do not include it);
   - additional event kinds for queue, requests, git status, worktree setup, provider auth and schedule runs.
8. **Executor registry by executor** (by M6). It replaces the `?workspace=<id>` keying of `architecture.md:24` and widens confinement to a worktree base.
9. **Sub-group names in `service.status`** (by M3). These are additions to the owner's group list, which stays the umbrella.

**Critiques rejected or narrowed:** none contradicts the owner design. Three were narrowed:
- **Mapper flow tests use an `AgentApi` double.** The critique asked for that, and it stands. The owner's requirement of black-box testing against the real service is met at the integration tier, not dropped.
- **The `rs` hexagonal debt.** Accepted, but moved to M2b so that M2 stays within the CI gate.
- **The "rename to the owner's names" critique.** Applied by keeping the owner's names. The plan's new shapes are listed above as decisions 7 and 9.

**Risks:**
- **rca-service Docker context.** It must copy `libraries/agent-api`, so every contract dependency bump changes the image input hash, which means a redeploy plus deployment verification. With three lockfiles, a contract crate's dependencies land in `clis/Cargo.lock` and `backend/remote-chat-agent/Cargo.lock` too.
- **Pin drift.** Both references move. The generator is pinned, pin bumps are deliberate `parity: pin-bump` commits, and the "never rises" rule allows them.
- **Static audit completeness.** Swift native modules and the web-shell bridge (`bridge-host-requests.ts:69-73`) were not read. The generator flags them in M1.
- **orcad on arm64.** Untested until the M1 spike. The fallback is owner-paired goldens.
- **Third-party APIs.** The Orca `github.*` and `gitlab.*` methods and the trackers depend on live third-party APIs, and their deployment verification needs test accounts the repo does not have.
- **CI time.** Per-task times are unknown until M1. M1 and M2 are full reruns, and so is any `agent-api-proto` or `exec-proto` change. Milestone sizes may change once the gate has numbers.
- **Phone apps on the CI emulator.** Unknown until the M1 spike.
