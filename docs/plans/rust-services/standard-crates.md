# Standard crates instead of hand-rolled code, backends first, then CLIs

## Context
The Rust ports (`backend/remote-chat-agent/rs` 14.5k lines, `backend/leetcode-backend/rs` 2k, `clis/*` 34k) were written std-only: a hand-written HTTP/1.1 server, WebSocket framing and SHA-1, multipart parser, outbound HTTP by shelling out to `curl`, OTLP export, logger, rate limiter, CORS, zod-style error JSON, a regex markdown converter. Both backends carry near-identical copies (`limiter.rs` identical; `telemetry.rs`, `log.rs`, `curl.rs`, `server.rs` differ by a few lines). Owner rule from now on: standard, widely used crates; no hand-rolled infrastructure; clean architecture kept wherever Rust allows it.

Decided with the owner: scope is backends, then CLIs; markdown moves to `pulldown-cmark`; where a library's behaviour differs from today's wire contract, the library wins (tests and callers are updated, not adapters written). `clis/rca-edge` stays retired: axum is the skeleton, so that open question closes.

## Architecture: what carries over, what does not
Dependency arrows: `api` -> `application` -> `domain`, and `infrastructure` -> `application` (it implements the port traits `application` defines); only `main.rs` names the concrete infrastructure and passes it in. Layers, from the inside out: `domain` (pure: orchestration `types`, `decider`, `projector`, voice DSL and planner) <- `application` (engine, reactor, use cases; talks only to ports) <- `infrastructure` (implements the ports: reqwest opencode client, tokio process runner, file stores, tracing/OTLP export) <- `api` (axum routes, WebSocket, and `main.rs` as the composition root that wires everything). Layer names are exactly these four, as module names. Ports are traits in `application` (`Backend`, store, clock, process runner).
This is what the Rust community calls hexagonal architecture (ports and adapters), usually as a Cargo workspace with one crate per ring. Per service: a `core` crate holding `domain` and `application` (with the port traits; no axum, reqwest or process code) and the service crate holding `infrastructure` and `api`. Enforcement: a crate that is not in `core`'s `Cargo.toml` cannot be imported, so the dependency rule is a compile error, stronger than the lint-based `arch` check the frontend uses.
Folder layout and its enforcement (2026-10-09, owner request): in every service crate pair, `core/src` holds only `domain/`, `application/`, `lib.rs` and `testing.rs`, and `rs/src` holds only `api/`, `application/`, `domain/`, `infrastructure/`, `lib.rs` and `main.rs`; everything else sits inside a layer in snake_case. `pnpm run arch:services` runs two standard tools: `ls-lint` (`.ls-lint.yml`, the folder layout) and `ast-grep` (`backend/arch-rules/*.yml`, the direction of the imports: domain imports no outer layer, application reaches neither infrastructure nor api, infrastructure does not use api, api does not use infrastructure). It runs in the pre-commit hook and in the architecture workflow. Cargo already enforces the crate boundary (`core` cannot depend on `rs`). Files that still break a direction rule are listed in the rule's `ignores` (a ratchet that only shrinks; `docs/plans/rca-hexagonal/plan.md`).

Size matters: `remote-chat-agent` has real rules (`decider` and `projector` are about 700 lines), so all four layers earn their place. `leetcode-backend` is mostly proxying and a session store, so it gets three: `application` (use cases and ports), `infrastructure`, `api`; no separate `domain` until it has rules worth isolating.
Where it fits less well, to be reported in each PR:
- `async fn` in traits is not object safe: ports use generics or `async-trait` behind `Arc<dyn Port>`.
- Axum handlers are framework-typed, so the HTTP layer is not framework-free (same as Express routes); handlers stay thin and call application functions.
- `serde` derives sit on domain types (data format only, accepted).
- No DI container: wiring is explicit in `main.rs`.

Since 2026-10-21 the rules for every package type, these services included, and the holes in today's checks live in `docs/solutions/architecture/hexagonal-architecture-by-package-type.md`; this section is the history.

## Test tiers (owner's definitions) and how they look in Rust
- **Flow**: like a unit test, but the subject is a significant entry point (a server router, a CLI `run`), and every external dependency is replaced in code. Rust has no module mocking (no `vi.mock`), so deps are injected through port traits (same rule as "no `vi.mock` of project modules"): hand-written fakes in `src/testing/` (`FakeBackend`, fake store, clock, process runner, outbound-HTTP port). The real axum `Router` is driven in-process with `tower::ServiceExt::oneshot` (or `axum-test`); no socket, no network, no spawned process. `mockall` only if a port is too big to fake by hand.
- **Integration**: the entry point as a black box (the real binary, a real process, real sockets), with dependencies faked at network or process level: fake servers (`fakeOpencode.ts`), stub binaries on `PATH`. This is the existing TypeScript black-box suite (`tests/blackbox`, `tests/integration`); it stays the oracle through the whole refactor. `wiremock` belongs here, not in flow tests.
- **E2E**: the entry point against the real running production environment (VM, real vault, real services), via runbooks and `wf vm exec`.
- Name Rust tests by this vocabulary: Cargo calls anything under `tests/` an "integration test", but those run in-process, so by our definition they are flow tests. Files are `tests/flow*.rs`, never `tests/integration*.rs`; the black-box suite stays in TypeScript.
- Contract tests (an adapter honours its port) run one generic test function against the real adapter and its fake.
- Given/When/Then in each; the report names the tier that ran.
- Doc: the ladder already exists in `docs/solutions/testing/verification-ladder.md` and `CONCEPTS.md` ("Verification ladder", "Flow test"), but its `integration` row ("package plus the real neighbouring service, neighbour's mock upstream") does not say black box or network-level fakes, and `CONCEPTS.md` has no entries for integration and e2e. Phase 0 sharpens both with the three definitions above, a comparison table (entry point, where doubles sit, what runs, what it proves), a worked Rust example from `rca-service`, and the Cargo `tests/` naming trap.

## Risks
- Tokio, reqwest and the OTLP stack raise binary size, idle RSS (6.5 MB today) and cold start (32 ms today). Use a small worker count, no default features, and report the numbers; the owner has chosen standard over smallest.
- arm64 cross-build with rustls: check in the VM native build before merging.
- Async migration of the engine is the largest single slice; the black-box suite is the safety net.

## Verification
- Tiers: e2e runbook checks on the deployed services first (health, WS probe, voice, convert via `wf vm exec`), then the integration (black-box) suites, then Rust flow and unit tests; say which tier ran.
- Each PR: `cargo clippy -D warnings`, `cargo test` (flow and unit), black-box integration suites on the new binary, `wf check --staged`.
- Benchmark n=5 with the same method as `rca-post-rust.json`; image size; no resident Node process for the services.
- Deploy through the dev pipeline (`wf ship --changed` legs), then confirm sha at `/health` and a BetterStack query that returns lines from the new tracing path.
