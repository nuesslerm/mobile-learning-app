## The split

`clis/pipeline` deals the flow and integration tests to the caller's `shards` machines by unit key, not round-robin. A unit is a package, a crate (`crate-<crate>`) or, for flow, integration and e2e groups, `crate-<crate>/<group>` (the crate's own key is then the rest of the suite, with its unit and clippy kinds; the runner names a flow group's span `crate-<crate>/<group>` in `CI_UNITS`, as the weights key); its weight is in `clis/pipeline/data/shard-weights.json` (a default per stage, an entry for each heavy unit). The units are dealt longest first to the lightest shard (`assign` in `test_plan.rs`), so the same commit always puts the same unit on the same shard and a shard's Nx cache key and CI timing row mean the same thing from run to run. Change the weights when a unit's measured time moves; the tests in `shard_tests` pin the dealing.

## Overlapping runs

`ci-hosted-backend-core.yml` groups runs per commit (`<file stem>-<sha>`, e.g. `ci-hosted-backend-core-<sha>`), so a push never waits for an older run and a red shard is fixed and re-run at once; a sharded job still pending when a newer run of the same inputs queues is replaced and that run then ends cancelled or superseded (see below), while every other run is measured to its end. Per-job groups still serialise what must not overlap (the deploy per app). The `Is this commit the head of dev` step of the `plan` job in `pipeline.yml` (output `is_head`; it was a job of its own, which took a runner slot for 3 s) gates the deploy and the production EAS publish on the commit still being the head of `dev`, so a slow older run never puts older code over newer.

## The e2e jobs have no group

The browser and Android e2e jobs once shared one concurrency group per platform across all runs. GitHub keeps one running and one pending job per group and cancels the older pending one, so a newer push silently cancelled the e2e jobs of the run before it (3a110f34, no job red). They now have no group at all, so overlapping runs each finish their own e2e jobs.

## The e2e jobs do not wait for the integration tests

`browser-e2e-tests` runs against a web export built on its own runner and `android-e2e-tests` against its own backends, so neither reads the deploy or the production EAS Update, which the deploy waits for (every stage including the slowest integration shard, about 800 s) and the production EAS Update no longer does (it needs only `plan` and `wf-build`). They now need `plan`, `core-tests`, `clis` and `cli-e2e-tests`; Android also needs `eas-update-e2e`, the job that publishes the branch `e2e` update and hands its pointer over, split out of `eas-update` (which keeps the production publish, ungated by the tests).

## Sharded test jobs: one group per shard inputs, a pending job may be replaced (owner, 21 Nov)

Five jobs of `pipeline.yml` have a concurrency group. The sharded jobs (`core-tests`, `integration-tests`, `cli-e2e-tests`) use `hosted-<job>-<workflow>-<shard index>-<shard key>[-fresh]` (`<workflow>` is `github.workflow`, the caller's name; `<shard index>` is `matrix.shard`), shared across runs. The two deploy jobs omit the workflow, because the VM is shared: `hosted-deploy-build-<app>` and `hosted-deploy-<app>`, so a deploy of one app serializes no matter which workflow starts it and the newest pending one wins. `wf-build`, `deployment-verification-tests`, `eas-update`, `eas-promote` and `eas-update-e2e` have no group: a group ending in a run id can never collide with another run, and GitHub never runs two attempts of one run at once. A caller's own group is `<file stem>-<sha>`. `cancel-in-progress` is false everywhere. Pinned by `caller_drift.rs`.

The shard key in that group is `wf ci plan shard-keys` of what that shard runs (the crates it holds and a fingerprint of what they read: the git object ids of their directories and of their dependencies' directories, and the lock file; `core-tests` combines its flow and typecheck keys), and `-fresh` marks a run with the caches off (not on `integration-tests`). The workflow is in the group because two workflows of one commit plan the same keys. The shard index is in it because a shard with nothing to run has the key `none` and several shards of one run can have it: without the index they shared one group, one ran, one waited and the next replaced the waiting one, so a run ended cancelled with no verdict (run 44902599573, integration shard 4/4 cancelled at 0 s). A pending job is now only ever replaced by a newer run's job, never by a sibling shard. Two runs that plan the same shard index with the same inputs share a group: the later run's shard waits as the group's one pending job (no runner, no slot of the cap) and replays the earlier result; a fix changes the inputs, so it is another group and starts at once.

The rule. GitHub keeps one running and one pending job per group; a third run replaces the pending job, even with `cancel-in-progress: false`, and the replaced job ends `cancelled` ("Canceling since a higher priority waiting request ... exists"). The owner (21 Nov) accepts that: a job that has not started may be replaced by a newer job of its group. This lifts the earlier rule that an older run is never cancelled (owner, 19 Nov), and 115236b7 (a run id in the group) is undone for the groups. A job that is already running is still never cancelled by us: `cancel-in-progress` stays false everywhere.

How it reads. A replaced job records a start at the moment of its replacement, so a job cancelled within 2 s of its recorded start is a pending one replaced (`ci_comment::REPLACED_SECS`); one cancelled after more than 2 s was killed while running. `wf ci audit` treats the replaced job as expected and reports only `cancelled-while-running` (P4: no job cancelled after it started running) and `group-overlap`. The run comment's title reads "superseded by a newer run of the same inputs" when the only jobs that did not pass were replaced while pending (the replaced job shows as `🚫`); a red job still makes it "failed".

## Checking the queue after some days of use

The sealed CI database answers these, with `wf ci db query` (`CI_JOBS` holds every finished job of a run, cancelled-while-pending ones included; `NX_TASKS` every task; `CI_METRICS` the same gauge readings Better Stack receives):

```sql
-- work done twice: the same task and input hash that ran in more than one run (should trend to zero)
SELECT TASK, HASH, COUNT(DISTINCT RUN_ID) AS runs FROM NX_TASKS WHERE OUTCOME = 'ran' GROUP BY TASK, HASH HAVING runs > 1;
-- an overlap inside a group: two jobs of one group running at the same time (should be none: the group serialises them)
SELECT a.GROUP_KEY, a.RUN_ID, b.RUN_ID FROM CI_JOBS a JOIN CI_JOBS b ON a.GROUP_KEY = b.GROUP_KEY AND a.RUN_ID < b.RUN_ID
  WHERE a.STARTED > 0 AND b.STARTED > 0 AND a.STARTED < b.STARTED + b.SECS AND b.STARTED < a.STARTED + a.SECS;
-- a job killed while running (a cancelled job that ran more than 2 s: should be none; a job GitHub ends within 2 s of its recorded start was a pending one replaced, which the owner accepts)
SELECT RUN_ID, JOB, SECS FROM CI_JOBS WHERE CONCLUSION = 'cancelled' AND STARTED > 0 AND SECS > 2 ORDER BY SECS;
-- how long a shard waited, by whether it was replaced (a fix push should wait a few seconds)
SELECT CONCLUSION, COUNT(*), AVG(QUEUED), MAX(QUEUED) FROM CI_JOBS WHERE KIND = 'integration-tests' GROUP BY CONCLUSION;
-- why jobs failed, as the run saw it
SELECT RUN_ID, JOB, STEP, EXCERPT FROM CI_JOBS WHERE CONCLUSION IN ('failure', 'timed_out') ORDER BY TS DESC LIMIT 20;
```

A job that goes red also runs `wf ci failed --notify` (the shared job-end step): the verb itself sends the Better Stack log line `ci.job.failed` (run, job, step, task, excerpt, sha, `scrubbed`, and `annotations`: how many error annotations the API showed for the running job, `unreadable` when it showed none, which tells whether they are readable live) through the OTLP logs sink (`ci_metrics::log`), refreshes the run's comment, which then carries a `failing now` row for the job while its other steps run, and with `--notify` posts one JSON line to `CI_FAILURE_HOOK_URL` when the environment or the vault holds one (no URL is a no-op; the verb exits 0 either way). The excerpt is the lines of the job's log the Actions API shows while the job runs, which is none until the job ends, so a live line often carries the step and the Nx task (from the job's own ledger) and an empty excerpt; `CI_JOBS` keeps the excerpt once the job ended.

## One catalogue, two sinks

Every CI gauge is named in `clis/wf-bucket/src/ci_metric_catalog.rs` (name, unit, what its two labels hold, which verb sends it); `Gauges::set` refuses a name the catalogue lacks and says so as a `ci.metrics.unknown` event, and a flow test fails when a gauge name appears in the sources without an entry or the other way round. `Gauges::send` gives a batch to two `MetricsSink` adapters: `LocalDbSink` (rows of `CI_METRICS` in the job's own database, written even when the metrics source is down or unconfigured) and the Better Stack OTLP sink.

## Unit spans, the weights and the split report

The shard runner (`nx::run_many`) writes a `CI_UNITS` row for each unit of a weighted stage when its Nx call starts (`running`) and the unit's span when the call ends (first start to last end, the milliseconds of the tasks that ran, `ran`, `hit` or `failed`; a unit a stage's second call runs again adds to its row). The rows live in the job-local database and are folded into the sealed one by the report job's merge; nothing pushes the state ref from a job. `wf ci progress` run on the runner of a job names the unit that job is in (`running_units`); from another machine it cannot, since the rows are never pushed. `wf ci plan shard-weights --write` takes a unit's weight from `CI_UNITS` and falls back to its Nx tasks (`NX_TASKS`) for units with no span, now also for the browser and Android e2e tests. `wf ci plan shard-weights --report [--run <id>] [--send]` sets one run's split against what it measured (units re-dealt onto the stage's shard count, since a span does not record its shard: predicted seconds per re-dealt shard from the committed weights, actual seconds from the spans, so only the per-unit error is measured); the report job runs it after the merge, the run's comment carries the same table, and the gauges are `ci.shard.predicted_s` and `ci.shard.actual_s`.

## Per-shard sccache entries and the Playwright cache (21 Nov)

`sccache-cache` takes a `shard` input: the entry is `sccache-<stage>-s<shard>-<os>-<arch>-<week>-<locks>` and every shard saves its own (the weighted split above puts the same crates on the same shard every run, so the hit rate of a shard's entry does not depend on another shard's compile). The earlier rule, one writer among the shards of a stage, left shards 2 and up without the compiles of the crates only they build. The cost is one entry per shard (each under the 1536 MB cap that skips a save, so a stage of N shards holds up to N entries a week against the repository's cache quota); the run summary line `sccache-<stage>` names the saved size, and the quota is the number to watch.

`playwright-cache` (restore and save, with `install.sh` beside it) holds `~/.cache/ms-playwright` and the `.deb` files of Chromium's system packages under `playwright-<version>-<image>-<arch>`. `install-test-deps` and the browser e2e job (which installs Chromium detached beside the web export) both restore it, run the script (dpkg from disk first, the bounded mirror path as the fallback, each try 150 s, keeping the downloaded `.deb` files) and save after a miss. The browser e2e job used to run an unbounded `playwright install --with-deps` with no cache, so a stalled mirror held it until the job's timeout. What only a hosted run shows: that the image's `.deb` set installs offline on the next image version (the key carries `ImageVersion`, so a new image is a miss, not a wrong restore), and the seconds saved.

## Six workflows on one push (owner, 19 Nov)

A push to `dev` starts six runs of the one pipeline graph, each for a stage (`stages` input of `pipeline.yml`) and, for the core stage, an area (`area` input, `wf ci plan tests --area`): `mobile_core+lint+pre-release-testing` (`ci-hosted-mobile-core.yml`: the app and the workspace root), `cli_core+lint+pre-release-testing` (`ci-hosted-cli-core.yml`: `clis/`) and `backend_core+lint+pre-release-testing` (`ci-hosted-backend-core.yml`: everything else) run the flow, lint, typecheck and unit tests of their area; `cli_build+publish+release-testing` (`ci-hosted-cli-build.yml`) runs the cli e2e tests and the wf build released as `wf-latest`; `backend_build+deploy+release-testing` (`ci-hosted-backend-build.yml`) the image builds, the integration tests (which belong with the images they run) and the deploy legs with their verification; `mobile_build+publish+release-testing` (`ci-hosted-mobile-build.yml`) the production EAS Update, the Android e2e update and the browser and Android suites, side by side. Each has its own concurrency group, its own pull request comment (a `label` of its own) and its own result, and the shared jobs (`wf-build`, `preflight`, `plan`, `report`) run in each. None waits for another. `--base last-green` is read per workflow (`GITHUB_WORKFLOW_REF`), so a workflow's changed set is measured from its own last green. `cli-e2e-tests` is the job the owner called both the crate e2e and the cli e2e; moving it to `deploy` is one `if:` line. `wf vm ops cancel-run` lists and cancels the runs of all six files (a run number counts per workflow, so `--run <n>` cancels the unfinished runs of that number), and `wf ci audit` lists and judges the completed runs of all six; a workflow GitHub does not list (404, switched off) is a note in the audit and is skipped with a line on stderr by `cancel-run`, which still cancels the other five. The audit also reads the concurrency groups from `CI_JOBS` (`GROUP_KEY` is the full group string, caller workflow, shard index and `-fresh` included, because two workflows plan the same key and the workflow is what keeps them out of one group; it was once recorded one shard off, shard 1 read the leading empty key, since fixed; `STARTED`; a job that began before the window and still ran in it counts): `group-overlap` (hard) is two jobs of one group that ran at the same time, `cancelled-while-running` a job cancelled after it ran more than 2 s while the rest of its run was not, `replaced-while-pending` (soft) a job GitHub ended within 2 s of its recorded start, which is how a replaced pending job reads (older rows in the window carry them; none should appear in runs started after the per-run groups are deployed), and `twin-overlap` (soft, its waste is the overlap) two runs running the same shard inputs at once (a pending job replaced by a newer one is not a kill; a run cancelled by hand or by `cancel-run --all` ends several running jobs and is left out), and `should-have-hit` covers a task that ran again under a `(task, hash)` another run already ran, once the task has been replayed from the cache before. The `HEALTH_RPT` fallback ledger keeps no groups, so there the group checks are skipped with a note.

## The 20-job cap and how many shards (owner, 19 Nov)

GitHub-hosted runners are free for a public repository but the account runs at most 20 jobs at once, whatever the workflow; the rest queue. The first six-workflow push ran 68 jobs and jobs waited up to 267 s for a slot (the push before it, 736 s), so a shard is not free: each repeats 1 to 3 minutes of setup and takes a slot. The callers therefore deal each stage over few shards (3 for the core areas and the cli publish, 4 for the integration tests, whose heaviest unit is 542 s; the repository variable `HOSTED_SHARDS` is no longer read: each caller states its own number in its `with:`) and the Android e2e over 2 devices. Measure the effect with `CI_JOBS.QUEUED` before adding a shard.

## Four cores per runner, fewer runners (owner, 20 Nov)

A hosted runner is 4 vCPU and 16 GB, and the account's 20 slots are shared by all six callers, so a slot that holds two cores' worth of work is half wasted. Two changes, stage names untouched (the test plan, `shard-weights.json`, the run bundles and the last-green logic still say `flow-tests` and `typecheck-lint-unit-tests`; only job names changed):

- **`core-tests` is one job per shard.** It replaces the separate `flow-tests` and `typecheck-lint-unit-tests` jobs. Shard `i/N` starts `wf test run --stage flow-tests --parallel 2 --shard i/N` and `wf test run --stage typecheck-lint-unit-tests --parallel 2 --shard (N+1-i)/N` as two background processes (2 + 2 Nx tasks = 4 cores), waits for both and fails if either failed. Both stages use the caller's one `shards` count (`plan` step `shards`), so a caller's core run goes from 2N shard jobs to N. The typecheck stage takes the mirrored shard because the weighted dealing puts the heaviest units on shard 1 in both stages: mirrored, the machine with the heaviest flow units has the lightest typecheck units. Each stage is still dealt by its own weights. The run bundle is still published as `test-runs-flow-tests-<i>`. Output lines carry a `[flow-tests]` or `[typecheck-lint-unit-tests]` prefix. The job's Nx cache key is `core-tests-<i>of<N>` (the first run after the change starts cold), its sccache key stays `flow-tests`, its sampler and ledger name is `core-tests-<i>` (the ledger rows keep the stage as `JOB`, `nx_ledger::record`, so `wf ci plan shard-weights` still reads them).
- **`plan` also runs the preflight and the head check.** The `preflight` job (58 s of setup for a check that waits on the network) and the `head` job (3 s, a runner slot all the same) are steps of `plan`: `wf ci preflight` starts in the background right after the setup, the plan steps run beside it, and `Collect the preflight` prints its output at the end. That step keeps the old `continue-on-error`, so a red preflight is an error annotation and a line in the log, not a stop; remove that line to make it stop the run (every job needs `plan`). `plan` also calls `wf ci concurrency --phase start` (the start of the run's concurrency record) and the report job runs `wf ci resources` and `wf ci concurrency` after `Timings`.

Runner slots at peak per caller, with the core callers at 3 shards:

| Caller | Before | After |
| --- | --- | --- |
| core mobile, core cli, core backend (each) | 6 (3 flow + 3 typecheck), 2 earlier (preflight + plan), 4 at the e2e wait | 3 (`core-tests`), 1 (`plan`) |
| cli publish | `wf-build` 1, `preflight` + `plan` 2, 3 cli-e2e, `clis` 1 | 1, `plan` 1, 3 cli-e2e, `clis` 1 |
| service deploy | `head` 1 beside `wf-build`, 4 integration, deploy legs | no `head` slot; the rest as before |
| mobile e2e | `head`, `preflight` and `plan` | `plan` only |

Every run also saves `report` (one slot) and the 3 s `trigger` job per caller. The three core callers together peak at 9 test runners instead of 18, which leaves the other callers room under the 20-slot cap.

## Several pushes in a row (owner, 20 Nov)

Every sharded test job (`core-tests`, `integration-tests`, `cli-e2e-tests`) has the concurrency group `hosted-<job>-<workflow>-<shard index>-<key>[-fresh]` (see above). Identical work from two pushes minutes apart waits as a pending job, which holds no runner and no slot of the cap, and replays from the Nx cache or the proof marker; a newer push replaces a still-pending job (the owner accepts it); a fix push changes the inputs, so it starts at once; nothing running is cancelled. The deploy, clis and eas-update gates still read `cancelled` as not passed (`success` or `skipped` only; `!= 'failure'` let it through), which matters for a run a person cancels. `install-wf` caches the built `wf` binaries by the `clis/` tree (exact key), so a commit that leaves `clis/` alone builds nothing in `wf-build`. A shard of `integration-tests` or `cli-e2e-tests` whose fingerprint a passing job marked (a cache entry, `wf ci proven`) is dropped from the matrix by the plan job: `proven-work-skip.md`. Not done, on purpose: skipping a run a newer commit covers, and a job that exits green on a newer or equal run's fingerprint in flight; both wait for the numbers of `CI_RUN_PROFILE` and `CI_CONCURRENCY` (docs/solutions/ci/parallelism-telemetry.md). Push a batch of commits once; push separately only a fix to a red run.


## The e2e stages and the legs probe (owner, 20 Nov)

Measured on 13 recent runs (`wf test results`), per test in seconds: voice-edit 150, tamil-writing 127, editor-typing 90, local-run 38, review-sheet-keyboard 22, stubbed-run-local 6, pyodide-spike 5 on the device; on the browser voice-edit 130, editor-typing 90, tamil-writing 81, app-routes 16, pyodide-spike 5 (local-run and review-sheet-keyboard have no browser time yet and weigh the stage default of 60). Those voice-edit times (150 s on Android, 130 s in the browser) were real-backend times; the browser script is stubbed from issue 86 E3.1 (15 to 20 s per chunk unit locally; Android still runs live), so measure again with `wf test results` after the first green hosted run before trusting them.

- **`android-e2e-tests` weights are the measured per-test seconds of 20 Nov again (21 Nov).** A re-deal that scaled them by what the hosted job took (the shard holding tamil-writing and editor-typing ran a median 319 s against 244 s, in five two-shard runs) moved tamil-writing onto the shard that runs `local-run`, `review-sheet-keyboard` and `stubbed-run-local` first. After them its first POST to the stub never arrived (the device's `! ctstate DNAT` reject rule for the stub's port counted 22 packets, 0 in every passing run), the app waited its 120 s timeout, logged `tamil.write.check_failed` and the unit's zero-warnings gate failed: `tamil-writing-part-write` was red in all three hosted runs after the re-deal (858dd3ab, 765e5178, c51233c6) and never before. The old deal is back, with tamil-writing first beside editor-typing; the 51 s shard gap stays, a green suite is worth more than a balanced one. The unit's dependence on what ran before it on the same phone is the real defect: `tamil-writing` should re-declare its stub and restart the app as `stubbed-run-local` does, which needs an Android run to prove.
- **The e2e jobs now hand their CI database rows to the report job.** `e2e-tests.yml` never ran the `hosted-stats` upload, so the Nx tasks and the unit spans of every browser and Android test stayed on the runner: `CI_UNITS` and `NX_TASKS` held rows for four stages only and `wf ci plan shard-weights --write` and `--report` had nothing for the e2e stages. The workflow ends with the upload (artifact `ci-db-<platform>-e2e-tests-<shard>`), so from the next run each test has a span and `--write` regenerates its weight from the median of the runs.
- **`browser-e2e-tests` is sharded in two** like Android (`shard`, `shards: 2` and a matrix in `pipeline.yml`; `e2e-tests.yml` already passed `--shard i/n` and put the shard in the job name, concurrency group and bundle name). The stage has its own weights; the deal is voice-edit, local-run, app-routes, pyodide-spike against editor-typing, tamil-writing, review-sheet-keyboard (about 211 and 231 weighted seconds). Each shard repeats the runner's setup, backends and export (about 4 minutes of runner time), so the stage costs one more job slot and about 380 runner-seconds more; the job's wall time should fall from about 745 s to about 580 s. Revert by removing the matrix keys and `shards`.
- **`plan` does not ask the VM in a run with no deploy.** `wf ci plan legs --no-lookup` asks no service for its running commit (each reads as unknown, so every leg lists as changed, exactly what a service that does not answer gave before); `pipeline.yml` passes it when `inputs.deploy` is false, which saves the roughly 45 s of timed-out probes in the mobile and backend build workflows. The update's decision still comes from the latest-update pointer. A run with `deploy` true probes as before.
