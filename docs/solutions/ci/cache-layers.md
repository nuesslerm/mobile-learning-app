# Cache layers: one job each, one bucket, one `wf cache` verb each

Every cache the build uses lives in the OCI bucket `mobile-learning-build-cache` and is reached through `wf cache`. Run `wf cache --help` for the live list and `wf cache status` for what each layer holds and how many requests the month has spent.

| Layer | Caches | `wf cache` verb | Prefix | Lifetime |
|---|---|---|---|---|
| Nx | whether a task runs, and its declared `outputs` (Rust verdicts, lint, typecheck, the web export) | `wf cache nx` (the loopback shim `wf test run --stage` starts) | `nx/` | 14 days |
| sccache | Rust compile output of cargo runs in the sandbox and in CI jobs (not inside the Docker builds) | `wf cache sccache` | `sccache/` | 7 days |
| pnpm store | downloaded npm packages | `wf cache pnpm` (`restore`, `save`) | `pnpm/` | 60 days |
| Metro and tsc state | the Metro transform cache and the `tsc` build info, one tarball | `wf cache metro` (`restore`, `save`) | `metro/` | 14 days |

Docker has its own: BuildKit layers on the VM and the registry cache `docker.io/<namespace>/<image>:buildcache` (`clis/deploy/src/build_image.rs`). Every Rust image compiles its dependencies in one cargo-chef layer (`t3-serve` and `orca-serve` moved to it on 15 Nov 2026, proven by `.github/workflows/image-build-probe.yml`, a hosted `docker build` of both that runs when their Dockerfiles or contract crates change, because the deploy legs are off while `vars.HOSTED_DEPLOY` is not `on`) (`cargo chef prepare` writes a `recipe.json` of the service's dependency tree, `cook` compiles only that), so a source change rebuilds the service's own crates and a dependency change rebuilds that one layer. sccache is not used there: measured on 26 Oct, a warm chef layer builds in 14 s and sccache in 99 s, and an sccache entry is machine code for one architecture (the sandbox is x86_64, the images are arm64), so the sandbox cannot seed it for the VM; Nx shares across the two because it stores verdicts, not binaries.

A Rust service that has its own Cargo workspace (`backend/<service>/Cargo.toml` and `Cargo.lock`; reporting-service so far) has its own dependency versions and its own image hash: a change to its manifest or lockfile redeploys that service only. Its `.cargo/config.toml` points `target-dir` at `backend/target`, so compiled dependencies are reused across the services in the sandbox and on the runner; cargo keeps two versions of a crate side by side.

## Rules

- A cached Nx target that writes files lists them in `outputs`; one that only passes or fails lists none. `clis/pipeline/tests/flow/cache_contract.rs` fails on a cached target that is neither a known verdict nor a declared file writer.
- Nx outputs restore only on an exact input hash. State that must survive a changed input (Metro's transform cache, `tsc`'s build info, compiled crates) is not an Nx output: it is a restore-latest tarball (`metro`) or a per-compile cache (`sccache`).
- The EAS export is the cached Nx target `export:eas` (`expo export` for ios and android into `dist`, outputs `dist`; its inputs add the initial route, the app environment, the platform and bytecode flags). `publish:eas` runs it, then uploads with `eas update --skip-bundler`: the upload is a side effect and runs every time, only the export is replayed. Its Metro transform cache is restored and saved by `wf cache metro` around the publish; the web export is the `export:web` target.
- Invalidation is by key, never by hand: Nx by input hash, sccache by source, flags, compiler version and dependency hashes, the tarballs by lockfile and config hash; every prefix also expires by the bucket's lifecycle rule (`infra/oracle-cloud/build-cache.tf`).
- A run that cannot reach the bucket, or that is over a cap in `clis/blob-cache/data/budget.json`, goes cold, never red. Only a clean tree on `origin/dev` with pinned tools writes.
- Free-tier headroom is checked with `oci os bucket get --bucket-name mobile-learning-build-cache --namespace-name <ns> --fields approximateSize`; the Always Free Object Storage allowance is 20 GB across buckets, and 50,000 API requests a month.
- A slow live-model e2e suite is split into one Nx task per group, so a change reruns only the groups it can move. A crate lists `[package.metadata.e2e]` in its `Cargo.toml`: `groups` (a module of `tests/e2e.rs` each), `shared` (files every group reads), `src` (the crate sources the suite exercises) and `extra`, all relative to the crate dir. `tooling/nx/cargo-crates.js` then defines `cargo-e2e-<group>` instead of `cargo-e2e` (command filtered by `<group>::`), keyed by the toolchain, `^rustProduction`, the workspace files and lockfile slice (below), and those files only; `wf ci plan tests` emits one `cli-e2e-tests` entry per group and `wf test run --stage cli-e2e-tests` runs the targets together, so `WF_PUSH_CLI_E2E=1` seeds each group on its own. `crate-rca` has four: `ask`, `compare`, `compare_features`, `compare_capabilities`. The batch, runbook, pricing and worker sources are outside `src` because no group drives them. A new module of `tests/e2e.rs` must be added to `groups`, or it runs in no task. `clis/pipeline/tests/flow/nx_cache.rs` holds the contract.
- A Rust task (`tooling/nx/cargo-crates.js`) is keyed by its crate (`rust`), its path dependencies (`^rustProduction`), its workspace's `Cargo.toml` and `.cargo/config.toml`, and its slice of `Cargo.lock`: `tooling/nx/cargo-lock-slice.js`, a runtime input, hashes only the lock entries the crate's dependency closure reaches (as `wf ship` keys images), so a lockfile edit for one crate reruns the crates that build it, and a comment reruns nothing. A lockfile that does not parse, or lacks the crate, is hashed whole.
- A crate inside a pnpm package is that package's files, unless the package sets `"nx": {"cargoCrates": true}` in its `package.json`: then each of its crates is a `crate-<name>` project with `cargo-clippy` and `cargo-unit`, and the package depends on them. Nx's `targetDefaults` beat a plugin's target inputs and a named input cannot take `{input, projects}`, so the package's own `nx.targets` key `test:flow` and `test:integration` on `["cargoFlow" | "cargoIntegration", "^rustProduction", {"externalDependencies": []}]`, named inputs the plugin defines from file sets: the dir of the crate the script runs (`-p <crate>`), its workspace files and lockfile slice, its `[package.metadata.flow]`, and the package.json. The remote chat agent opts in: its TypeScript e2e tests, Dockerfiles and compose files no longer rerun its flow suite.
- What a crate's tests read beyond the crate is in its `[package.metadata.flow]`, all from the crate dir: `inputs` (files, for the flow tests), and `uses` (crates whose binaries the flow and integration tests build and run, from any workspace: their sources, path dependencies, workspace files and lockfile slice, for those tasks only, not clippy or unit). A `uses` or group name that is no crate stops the graph with an error naming it on stderr; `wf test run` gives Nx `NX_ISOLATE_PLUGINS=false`, as a plugin worker's stderr can be lost when Nx exits. Never override a crate's `cargo-flow` inputs in a `project.json`: that replaces the plugin's list, lockfile slice and `externalDependencies: []` with the whole lockfile. `wf ci plan tests` reads the same keys: a changed file an `inputs` glob (or a group's file glob, or `shared`) matches, or a reached crate a `uses` names, plans the crate's flow entries (and, for `uses`, its integration entry) and nothing else of it. A package that opts in is planned the same way, by its crates: one that depends (cargo) on a reached crate, runs one (`uses`) or reads a changed file (`inputs`) puts the package's own scripts in the plan, so Nx is asked to run a suite it would rerun (`packages_reached_through_crates` in `clis/pipeline/src/test_plan.rs`; the planted cases are in `clis/pipeline/tests/flow/pipeline.rs`).
- A declared glob (`inputs`, a `uses` crate's dir, e2e and flow group files) leaves out every crate nested under it, which is a project of its own; Nx applies a task's `!` file sets to all of them, so a nested crate the task itself names stays in.
- A slow flow suite can be split like the e2e one: `[package.metadata.flow] groups = { <group> = [...] }` (a module of `tests/flow.rs` each, `tests/flow/<group>.rs`) and `shared` (files every group reads). Each group is a `cargo-flow-<group>` task instead of `cargo-flow`, keyed by the crate's own sources, its module, `shared`, the files and crates the group lists (an entry without `/`, `.` or `*` names a crate), and every path dependency no other group names; `wf ci plan tests` emits one `flow-tests` entry per group. A new module must be added to `groups`, or it runs in no task.
- A crate with a `tests/integration.rs` has a `cargo-integration` task next to `cargo-flow`, keyed like it plus `[package.metadata.integration]` (`inputs`, `uses`; `evidence`, a coverage app name (`orca`, `t3`): the chain is planned on every push, not only when reached, because its trace bundle refreshes `docs/plans/rca-parity/coverage/<app>-evidence.json`; a missing or unreadable table is planned too, with that reason; `sources`, when set, replaces the crate's every file by the listed globs, as t3-serve does so a flow test, its Dockerfile or its compose file does not rerun the replay: `nx_contract` proves every file the chain reads by a `CARGO_MANIFEST_DIR` path moves the hash). It is in the weekly drift audit's target list (`TARGETS` in `clis/pipeline/src/nx_drift.rs`) with the other cached targets: a target missing there can move its hash with the checkout's path or the environment unseen, so add a new kind of cached target to that list when `tooling/nx/cargo-crates.js` starts to create it.
- A slow part of an integration suite is its own task: `[package.metadata.integration.groups]` lists `<group> = { filter = "<libtest filter>", files = [...] }` (from the crate dir). `cargo-integration-<group>` runs the filter and is keyed by the crate plus its `files`; `cargo-integration` skips every filter and is keyed by none of the groups' files, and a group is not keyed by another's. `wf ci plan tests` emits the rest of the suite and one `integration-tests` entry per group, and `wf test run --shard` deals each group out as its own unit (a shard that holds only groups of a crate runs them in a call without the crate's `cargo-integration`). `crate-t3-serve` has the four recorded replay sets; a test that names a new set must be added there, and `every_recorded_set_on_disk_has_a_test_above_and_so_a_task_of_its_own` fails until it is.
- A candidate crate replays its recorded sets by feature: `[package.metadata.integration.replay] sets = [...]` on the candidate (orca-serve, t3-serve), and on each mapping crate under it `[package.metadata.integration.replay] rows = ["rpc:terminal.", ...]` (a crate that is several features names `[package.metadata.integration.replay.<feature>]` tables of `rows` and `files`, from the crate dir, as t3-core does). Each feature is the Nx task `replay-<crate>` (`replay-<crate>-<feature>`) of the candidate, running the libtest module `replay_features::<crate>::` and keyed by the candidate's wiring, its cassettes, the deps no mapping crate names and the mapping crate's own closure; `cargo-integration` skips `replay_features::`. `wf ci plan tests` emits one `integration-tests` entry per affected feature (its `replay` field holds the rows, the sets that hold them and the `wf mimic replay <set> --rows ... --gaps check` verbs it is): a changed mapping crate or a crate it depends on, all of them when the candidate's own files, cassettes or `uses` changed, and for named features with `files` only those whose files changed beside the features without files. The test file has one `feature_test!` entry per feature and a test that every row of every set is claimed.
- An integration task carries its run records in its Nx outputs, so a cache hit still has them to publish. Each integration task (`cargo-integration`, `cargo-integration-<group>`, `replay-<crate>`) runs with `WF_TEST_OUTPUT_DIR` set to a folder of its own, `.agents/tmp/test-output/<crate>/<task>/` (removed first, so a run never mixes with an older one), and lists that folder in `outputs`: the suites' `<suite>/report.json` and `<suite>/trace.json` are cached with the pass and restored on a hit. (Nx outputs must be inside the workspace, and a folder shared by tasks would be wiped by each restore, which is why the runner's temp dir and one common folder do not work.) The integration shard's `Publish the integration run bundles` step walks `.agents/tmp/test-output` for the `vm-ops-api-*`, `t3-serve-*`, `wf-mimic-*` and `orca-serve-*` suite folders and runs `wf test publish` on each, so a shard that replayed everything uploads the same `test-runs` bundles as one that ran, and `wf mimic coverage --traces` reads the full set of traces of the run. The `test:integration` scripts of the two package crates (`vm-ops-api`, `remote-chat-agent`) do the same: each sets `D="$PWD/../../.agents/tmp/test-output/<package>/test-integration"`, removes it, passes it as `WF_TEST_OUTPUT_DIR` to the cargo test run, and lists it in its `package.json` `nx.targets.test:integration.outputs`, so a replay of them publishes their `vm-ops-api-integration` and `wf-mimic-*` bundles too (`a_package_integration_script_that_sets_its_records_folder_declares_that_folder_as_an_output` in `clis/pipeline/tests/flow/cache_contract.rs` fails when a script and its outputs name different folders). A bundle made from a replayed task holds the record of the run that wrote the cache entry (its start time and run id are that run's). Proved by `an_integration_task_replayed_from_the_cache_restores_the_trace_its_run_left` (`clis/pipeline/tests/flow/nx_crates.rs`, run by `nx_contract`: it deletes the records, replays from the cache and finds the traces again; with `outputs` emptied it fails). What only a hosted run proves: the `nx-cache` action carries the outputs between runs, and shards 2 to 5 upload a bundle.
- `clis/pipeline/tests/flow/nx_crates.rs` holds these keys: a fixture of three cargo workspaces under the real `nx.json`, plugins and Nx, one planted change per case through `wf test run --stage`.

## CI today: the GitHub Actions cache, one switch for the backend

The Oracle bucket is gone, so hosted CI uses `actions/cache` (pinned by SHA) until another store exists. Which backend a layer uses is one repository variable, `CACHE_BACKENDS` (read as `env.CACHE_BACKENDS` by every cache action, set at the top of `pipeline.yml`):

| `CACHE_BACKENDS` | The Actions-cache steps | The blob store (`wf cache`, the build-cache shim of `wf test run`) |
|---|---|---|
| `gha` (default) | on | off (`WF_BLOB_CACHE=off`) |
| `blob` | skipped | on: the stores in `BUILD_CACHE_READ_STORES` and `BUILD_CACHE_WRITE_STORES` |
| `gha,blob` | on | on: reads take the first hit, writes go to every store |

Moving to R2 or Hetzner Object Storage is the variable plus the two store lists (`clis/blob-cache/src/stores.rs`), with no workflow edit. The sccache layer is the one exception to `gha,blob`: sccache has a single backend, so while the blob shim owns `RUSTC_WRAPPER` the directory cache stays out (`sccache-cache` does nothing when `WF_BLOB_CACHE` is not `off`). `CACHE_PNPM=on` brings the pnpm store back; it is off because it does not pay.

What each layer is worth, measured on 14 Nov (run 43558013495, `docs/audits/2026-11-14-ci-cache-bench.md`): sccache 96 s per use for 268 MB, metro 70 s for 17 MB, nx 38 s (identical rerun) for 1 MB, the pnpm store 13 to 17 s for 705 MB (and none in the real jobs), the rust target directory 86 s for 348 MB (sccache beats it), toolchain 4 s, cargo registry 0.5 s. Together the layers kept hold about 0.6 GB: the 10 GB quota is not the constraint, key churn is.

No shard can skip the pnpm install. Planned with `wf ci plan tests --all`, every `flow-tests`, `typecheck-lint-unit-tests` and `integration-tests` shard (6 each) carries at least one Node package, and the six `cli-e2e-tests` shards hold crates only; but a stage runs its crates' tasks through Nx (`crate-<name>` projects, `clis/pipeline/src/test_plan.rs`), and Nx is a pnpm dependency. So the install is the price of every shard, a Node-free shard included (measured 15 Nov).

| Layer | Path | Key | Restore keys | Saved when |
|---|---|---|---|---|
| sccache | `~/.cache/sccache` (`SCCACHE_DIR`; `RUSTC_WRAPPER=sccache`, `CARGO_INCREMENTAL=0`) | `sccache-<stage>[-s<shard>]-<os>-<arch>-<ISO week>-<hash of every Cargo.lock>` (no shard part for `wf-build`) | `sccache-<stage>[-s<shard>]-<os>-<arch>-` | `wf-build` and every shard of `flow-tests`, `integration-tests`, `cli-e2e-tests` and the browser and Android e2e jobs, each its own key; exact key missed, under 1.5 GB |
| metro | `frontend/mla-tamagui/node_modules/.cache/app-build` (Metro's transform cache and tsc build info) | `metro-<scope>-<suffix>-<os>-<arch>-<ISO week>-<hash of pnpm-lock.yaml, package.json, metro.config.js, babel.config.js, tsconfig.json>` | `metro-<scope>-<suffix>-<os>-<arch>-` | green job, exact key missed, one writer per key (`export` scope, suffix `all`: eas-update only on `ship`; suffix `web`: browser e2e shard 1) |
| nx | `~/.nx/*/cache` and `~/.nx/*/databases` (Nx's local cache and its index) | `nx-<stage>-<shard>of<count>-<os>-<arch>-<workflow>-<run_id>-<attempt>` | `nx-<stage>-<shard>of<count>-<os>-<arch>-<workflow>-`, then `nx-<stage>-<shard>of<count>-<os>-<arch>-` | not cancelled, `wf cache gate nx` says save (a task ran and passed, or the `cache_outputs` rows, their newest `created_at` or the entry listing changed since the restore), under 3 GB |
| references | `.git/modules/references` (the git objects of the two shallow reference clones; 489 MB, the bench measured 58 s to clone them) | `refs-<hash of the two pinned gitlink commits>` | none | any job that reads `references/` (`flow-tests`, `integration-tests`) after a miss; exact key only |
| pnpm (off) | `pnpm store path` | `pnpm-<os>-<arch>-<hash of pnpm-lock.yaml>` | `pnpm-<os>-<arch>-` | `CACHE_PNPM=on`, `flow-tests` shard 1, exact key missed |

Shard 1 is the one writer of the metro key only while it has work: if shard 1 picks no e2e test while shard 2 does, nobody saves that metro key for the run (a cache miss on the next run, nothing worse). The sccache key names its shard, so each shard is the one writer of its own key and a shard with no compiles saves nothing (`nothing compiled`).

- The sccache entry is per stage, week and lockfile set, not per run, so the quota holds a handful of entries. Since 21 Nov every shard saves its own entry (the weighted split puts the same crates on the same shard every run, so a shard hits its own entry); before that shard 1 alone saved, on the premise that the shards compile the same dependencies. Neither premise was checked against hit rates: the sccache stats line of each save (`sccache-<stage>` in the job summary) is the evidence to read. The workspace crates of a changed commit recompile (incremental profiles cannot be cached by sccache). A miss costs about 10 s over no cache (bench: 182 s against 172 s). The quota cost is unmeasured: 22 sccache entries (6 each for `flow-tests`, `integration-tests`, `cli-e2e-tests`, 2 each for the browser and Android e2e jobs) at the 268 MB the bench measured per stage would be about 6 GB of the 10 GB, and the 1.5 GB cap allows far more. When the quota is full the least recently used entries go first, whichever layer they belong to, so a burst of sccache saves can evict nx, metro or playwright entries; the effect is a cold restore (a miss line in the summary and the seconds back), never a failed job, and the only guard is the cap that skips an oversized save. If the summaries show those layers missing after a push, lower `max-mb` or return to one saving shard per stage.
- Metro's key is per input hash, not per commit: Metro and tsc key their own entries by file content, so one entry serves every commit until an input changes, and the ISO week in the key refreshes it weekly. A per-commit key would write a near-duplicate entry for each push into the shared quota. Only the `export` scope exists: nothing in the repo writes `tsc` build info into the cache directory, so the `typecheck` scope restored 0 MB in every shard and was dropped (14 Nov).
- Nx's key is unique per run so a later run restores the newest entry of its shard prefix. `wf cache gate nx` decides the save (23 Nov): it saves when a task of the job's ledger ran and passed, or the row count or newest `created_at` of `cache_outputs`, or the listing of `~/.nx/*/cache`, differs from the snapshot the restore took, and it skips only when every task replayed and nothing changed, which stops identical copies filling the quota. It first runs `PRAGMA wal_checkpoint(TRUNCATE)` on every `~/.nx/*/databases/*.db`, so the archive's database file holds the rows (Nx 23 serves a hit from that table, in WAL mode). The old gate counted entries, and a task that re-ran over an existing entry rewrote the same directory, so the count stayed equal, the save was skipped and the next run restored the same state and ran the task again (428 of the 736 `expired` misses of 20 to 22 Nov restored the entry the previous run had saved). Workflows only restore and save the directories; `wf` gives Nx its environment (`clis/pipeline` flow test `no_workflow_or_action_sets_the_nx_cache_environment_wf_gives_nx`). A changed shard count starts a new prefix. Each job prints the directory size before saving and refuses a save over 3 GB (`::warning::`). `.github/workflows/e2e-tests.yml` carries the Nx cache too (stage `<platform>-e2e-tests-<shard>of<shards>`, restore before the replay probe, save after the run, never for a cancelled job): the e2e Nx targets are `cache: true` with `.e2e-results` outputs (`tooling/nx/e2e-tests.js`), but until 22 Nov that workflow never restored or saved anything, so all 491 e2e task executions of 20 to 22 Nov ran and none hit (365 re-runs of an already passed `(task, hash)`, 22,114 runner-seconds). A failed e2e test exits non-zero and writes no result file, so Nx stores only passed ones (`clis/pipeline/tests/flow/e2e_nx_cache.rs`). The compile jobs of the bench run `--fresh`, so the cached Nx directory is about 1 MB: it holds verdicts, not binaries.
- Every restore writes one line to the job summary (layer, hit, partial with the matched restore key, or miss, and the restored size), through `.github/actions/cache-summary`; a save writes its size and the decision.
- Not cached, and why: the toolchain and the cargo registry (seconds, hundreds of MB), the rust target directory (sccache wins) and the bench's Playwright control (it skipped `--with-deps`, so its 20 s is an upper bound). The pipeline itself caches Playwright's browser and the system packages' .deb files (the `playwright-cache` action and its `install.sh`, used by `install-test-deps` and by the browser e2e job; key: Playwright version, runner `ImageVersion`, arch; saved only when .debs and the browser were fetched, and by one shard per run; no key without `ImageVersion`), and a hit installs by dpkg with no apt mirror. A hit that fell back to the mirror is not saved again: an exact key is immutable once written, so the refreshed .deb files wait for the next Playwright version or image. The reference trees' git objects are cached by their pinned commits (the shallow clone is 56 s per job); the bench's first save of that layer raced a git auto gc, so the layer is measured on the pipeline itself (the `references` line of the job summary and the step's seconds) until the next bench run confirms it.
- Limits: the repository shares 10 GB across all caches, evicted least recently used first, and an entry unused for 7 days expires. Caches saved on `dev` are readable by runs on `dev`; `dev` is not the default branch, so `main` and pull requests do not see them and a run on `main` cannot seed `dev`.

## The tenancy cap and the storage guard

The 20 GB Object Storage cap is the tenancy's, not the bucket's: build-cache, verification-artifacts, pnpm-cache, goldens and tfstate share it, and `always-free-quota.tf` stops writes at it. On 6 Nov it was full and every cache PUT was refused with HTTP 400 `StorageQuotaExceeded`, silently (a rejected PUT only skips the entry, so runs stayed green and cold). Two things now keep that loud and rare:

- The plan job of `pipeline.yml` starts `wf cache guard` in the background first thing and collects it last (`continue-on-error`, `timeout 60`; it is started with the runner's step tracking id cleared, or the runner kills it when the step ends, and the last step waits 5 seconds at most). The runner's wait for agent-shell is 45 s and cancels the remote job, the remote guard stops its own calls at 30 s. The runner holds no OCI key: the verb asks agent-shell, which has the `oci` CLI and `~/.oci` (written once from the `OCI_*` vault secrets, as `wf vm creds sync` does), to run `wf cache guard --local` through vm-ops-api's signed exec route, the access the deploy legs use. It prints one JSON line, `{"event":"storage-guard", action, usedBytes, usedBytesAfter, capBytes, deletedObjects, freedBytes, buckets, layers, evicted}`, always exits 0, and the job logs it as `wf: storage guard <json>`, adds it to the run summary and raises a warning annotation whenever the action is not `none`.
- Above 85 percent of the cap it deletes until usage is under 70, cheapest first and oldest first within a class: `sccache/`, `metro/`, `probe/`, `nx/`, old `pnpm/` generations (never the newest store and its sidecar), verification `test-runs/` bundles older than 3 days, then `eas-updates/` and `device-lab` older than 3 days. It never touches tfstate, goldens, `libs/`, `meta/`, the `latest-<branch>` pointers and the update group each names (the guard reads the pointers; one it cannot read spares every group), the indexes beside the folders, or any object younger than 1 day. A delete names the version the object was listed with (`--if-match`), so an object a writer re-PUT since the listing is left alone. Evicted `test-runs/` bundles stay in `verification/test-runs/index.json`: whatever follows an index entry (the reporter Routine, the nightly review) must tolerate a 404. `wf cache guard --local --dry-run` shows what a run would delete. The policy is `clis/blob-cache/src/storage_policy.rs`; the run is `storage_guard.rs`.
- The cap is `tenancyStoredBytes` in `clis/blob-cache/data/budget.json`, and a test (`clis/blob-cache/tests/build_cache_tf.rs`) fails when it differs from `always_free_object_storage_cap_gb` in `always-free-quota.tf`. Usage is what the listings of the build-cache and verification-artifacts buckets add up to, because a bucket's own size figure lags a delete by hours and would make the next run evict again; the other two buckets count their approximate size. What the line reports as deleted is what the store confirmed, also when a delete failed half way.
- A cache write refused with `StorageQuotaExceeded` is counted in the run's `wf: build cache {...}` line as `quotaExceeded`, adds one `wf: build cache storage quota exceeded` stderr line, and shows in the `cache` block of the test run bundle. It does not cool the cache (the store is fine, only full), so read the count, not `degraded`. The CI report flags it: a headline `Object Storage full: N cache write(s) refused` and a note on the job row.
- The guard runs the wf that agent-shell keeps (`/workspace/home/wf-bin/wf`): until that copy has `cache guard`, the runner's line is `action: skipped` with a `skipCode` and the reason (cleaned of key blocks and passphrases). `oci` is installed in the agent-shell image at a pinned version (`infra/oracle-cloud/agent-shell/Dockerfile`). `skipped` on several runs in a row means the guard does not work (no `oci`, no vault access to the `OCI_*` secrets, an old wf there): fix it, it is the silent failure the guard exists to end.

## Observability

Every cache operation is one logfmt event (source `ci-cache`) and a few gauges on the Better Stack source that `BETTERSTACK_METRICS_HOST`/`_TOKEN` name (`wf cache --help` lists both). The store's failure reaches the event as a class and an HTTP status only (`unreachable`, `credential`, `rejected`, `quota-exceeded`), never its words. A dirty tree and a dropped put are `warn` events with the paths and counts. Gauges are best effort and bounded to two seconds. A `Reading` has two labels, so `ci.cache.requests{kind,result}` is `scope=kind, name=result`, and a one-label metric carries `all` in `name`.

### Health: what fails a run and what is guarded

`wf ci cache-health` is the last step of the report job: it reads the `ci-cache` events and `wf: build cache {..}` lines of the run's job logs and exits 1 on a degraded layer, a refused or dropped required write (the tenancy's storage quota included), writes the store acknowledged but does not hold (`seeded 7 of 10`), a stage the pre-push gate runs that replayed nothing on a push to dev, a drift report, or a pnpm save over 60 s. The same verdict is the "Cache health" section of the live PR comment. A disabled shim is a note and a `wf: build cache disabled for this run` line, never silent. The comment's section groups the findings: one row per kind with the number of jobs (a job whose detail differs from the others' keeps its own row, named as the exception) and one note per shim reason with its job count. The push gate counts as seeded only when `WF_CI_PUSH_GATE` is not `off` (`ci_cache_health::seeded`, shared by the verb and the comment); `pipeline.yml` sets it `off` for the whole pipeline. Alert rules: `docs/runbooks/cache-health-alerts.md`.

Guards that keep a refusal from costing minutes: `wf cache save pnpm` checks the store's size against the entry cap (a tree over four times the cap cannot pack under it) and writes a one-word probe object before packing, so a full tenancy (`StorageQuotaExceeded`) is a `store not packed` reason in seconds, not a refused upload after the pack. Every shim layer asks the store for a sample of what it wrote when it stops (`seeded_checked`, `seeded_present`), and the pre-push gate refuses a stage whose entries are missing (`seeded N of M`), as it refuses one that only read the cache.

## Platform tiers: the platform is in no key by default

A task passed on x86_64 counts for arm64: no cargo task hashes the platform unless its crate is in the platform tier, and the tier is per crate.

- **Default**: the key is the crate's sources, its dependencies' sources, its lockfile slice and the Rust toolchain. A pass on any platform replays on every other.
- **Platform tier**: every cargo task of the crate (clippy, unit, flow, integration, e2e, contract) adds the named input `platform` (`node -p "process.platform+'-'+process.arch"`, `nx.json`), so each CPU keeps its own entries. A crate is in the tier when its `Cargo.toml` says `[package.metadata.flow] platform = true`, or, with no flag, when `tooling/nx/cargo-crates.js` finds `cfg!(..)`, `#[cfg(..)]`, `#![cfg(..)]` or `cfg_attr(..)` on `target_arch`, `target_pointer_width` or `target_endian` in its `src/`, `tests/`, `benches/` or `build.rs` (comments and string literals ignored; `target_os`, `unix` and `target_family` do not count: every machine that writes the cache is Linux).
- `platform = false` overrides a scan hit that is no CPU difference; give the reason in a comment beside it.
- **No inheritance**: a dependent of a platform crate stays in the default tier; its tier comes only from its own flag or its own code.
- `wf test drift` reports a table that differs by the platform as a cause of kind `platform`.

## The nx lineage is per calling workflow (21 Nov)

- Layout: the key and the first restore key carry `<workflow>`, the caller's `github.workflow` reduced to `[A-Za-z0-9_-]` (48 characters at most) by the `Name the lineage` step of `.github/actions/nx-cache`. The second restore key is the old unscoped prefix, so the first run of a workflow (and the first run after this change, whose predecessors have no workflow part) still restores the newest entry of any workflow for that stage and shard. Save rules, the 3 GB cap and the entry-count rule are unchanged. Proved by `given_the_nx_cache_action_when_its_keys_are_read_...` (`clis/pipeline/tests/flow/pipeline.rs`); what only a hosted run proves is the restore of the own lineage.
- Premise (measured on `NX_TASKS`, 18 to 21 Nov, 4,822 misses): `cli_core`, `mobile_core` and `backend_core` call `pipeline.yml` with the same stage and shard count, so all three wrote `nx-core-tests-<i>of3-Linux-X64-<run>-<attempt>` and a restore took whichever saved last: 136, 130 and 141 of 180 consecutive saves came from another workflow than the one before, and in a 72-job log sample 22 restores came from a sibling and 21 from the same workflow. The explainer called 98 of 332 core misses `expired` (an entry the lineage lost). Integration and cli-e2e have one caller each (1 switch in 51 saves), so they gain nothing.
- Predicted gain: the 1,000 same-shard re-runs (21% of misses) are the pool this can reach; counting only the share lost to sibling restores (about half of the sampled restores) it is about 10 to 20 points of replay ratio on `flow-tests` (now 26%) and `typecheck-lint-unit-tests` (now 32%), none on `integration-tests` and `cli-e2e-tests`. The ceiling for these two stages if every earlier-stored hash replayed is 59% and 62%.
- Measure: `ci.nx.replay_ratio` per stage (`flow-tests`, `typecheck-lint-unit-tests`; `integration-tests` and `cli-e2e-tests` must stay at 18% and 16%), for runs from the first hosted push after this change against the same series of 18 to 21 Nov, via `wf ci db query "<sql>"` over `CI_METRICS` (and `NX_TASKS` outcome per task). The first run per workflow restores unscoped (warm, but sibling-shadowed), so compare from the second push of each workflow on.
- Cost: none in download (one entry per shard, as now). Quota: each workflow keeps its own lineage, so up to three entries per stage and shard (12 to 39 MB for core, about 100 MB per integration shard if a second caller ever uses it) rather than one newest lineage; for core that is at most 3 x 3 shards x 39 MB, about 350 MB, of the 10 GB.
- Revert rule: if `ci.nx.replay_ratio` for `flow-tests` and `typecheck-lint-unit-tests` is not at least 5 points above the 18 to 21 Nov level over 20 hosted core runs, or the cache quota evicts nx entries (a `miss` line in the `nx` summary after a push), remove `<workflow>-` from the three lines of `.github/actions/nx-cache/action.yml` and the lineage step.
- Not done, by the numbers: a sticky task-to-shard assignment. Every machine of a stage computes the deal from the plan and the weights alone, so stickiness needs the previous push's assignment as shared state; tasks that moved shard are 31% of core appearances but only 89 + 28 of the 4,822 misses (about 3%) had a different shard as the earlier store, since most moved tasks have a new hash anyway. Restoring sibling shards' entries (+3 to +6 points) costs about 80 MB (2 s) per core shard and 400 MB (7 s) per integration shard and would overwrite the shared `databases` directory from another archive; it needs a separate key family and is the next step if the replay ratio stays under the ceiling. The larger gain (a durable per-task remote cache, +25 to +30 points) and the 60% of misses with a new hash (cargo-flow, clippy, unit inputs) are not touched here.

## Every restore and save is a row, every miss has a reason (22 Nov)

Why (measured 20 to 22 Nov, `NX_TASKS` and 656 job logs): the 10 GB quota was not the cause of the misses. 1,995 logged misses were 1,156 `input-changed`, 736 `expired` and 103 `never-stored`; 58% of the `expired` ones restored the very entry the previous run of the task had saved, and the task re-ran anyway, and 99 of 369 jobs with a real miss ended `not saving, no new task results`. None of it was visible without the job log, which expires. Now:

- **A restore or save is a row of `CI_CACHE_EVENTS`** (`wf cache event <layer> <restore|save>`, `wf cache event --help`): run, attempt, workflow, job, stage, shard, layer (`nx`, `sccache`, `pnpm`, `metro`, `playwright`, `references`, `other`), phase, key requested, key matched, match kind (`exact`, `restore-key`, `none`), size, duration, outcome (`ok`, `miss`, `timeout`, `error`, `skipped`), reason text, and for Nx the entries of `~/.nx/*/cache`, the rows of Nx's `cache_outputs` table and the size of its `-wal`. The actions (`nx-cache`, and `cache-summary` for every other layer) call it right after `actions/cache`; the job database is merged into the sealed one by the report job like every other table.
- **A failed restore is loud, never red.** The `actions/cache` step is `continue-on-error`, so the job goes on cold, but the event is `::error title=cache restore failed::layer=<layer> key=<key> reason=<text>` (a failed save: `title=cache save failed`), a red line in the step summary, a `warn` event in the log and the gauge `ci.cache.problems{layer,reason}`. A step cancelled by its time limit is outcome `timeout` (a composite step cannot carry a limit of its own, so the nx save step finds a restore whose start marker is still there and records it; the `Record the restore` step, which runs only when the restore finished or failed, removes the marker whether or not `wf` could write the result file, so a finished restore is never called killed). An Nx restore that matched a key and left 0 entries is an `error` too. A save skipped while tasks ran and passed (the gate only does it over the size limit) is `::error title=cache save skipped::` with the number of results left behind (`save-skipped-tasks-ran`); every skip and the reason of every save is recorded (`REASON` of the `skipped` row, `saved: <why>` of the `ok` row).
- **The check counts it.** `wf ci cache-health` reads the `cache.event` lines: a failed or timed-out restore is a `degraded` finding (the report job goes red), a failed save a `rejected-write`.
- **Every task that ran has a reason** (`NX_TASKS.MISS_REASON`, `MISS_DETAIL`, decided by `wf ci db merge` over the whole history, previewed by `wf ci cache-misses`, and as `reason` in `wf: nx why` from what the job alone knows): `never-stored` (no earlier run executed this hash: inputs changed), `stored-by-other-shard`, `stored-by-other-workflow`, `earlier-save-skipped` (the save gate), `earlier-save-failed` (the save failed or the job ended before it), `restore-failed`, `restore-timeout`, `uncacheable-by-design` (`cache: false`), `restored-but-reran` (the restored directory and Nx's table hold the hash and the task ran), `restored-without-db-row`, `restored-older-entry` (a race or lost update), `stored-entry-missing`, `unknown` (the lineage or the saves of the earlier run were not recorded; every run before 22 Nov is this or `never-stored`). Everything but the first and `uncacheable-by-design` is cache work that went to waste. The decision is one function (`clis/wf-bucket/src/miss_reason.rs`) over facts: the restore's outcome, `DIR_HAS_HASH` and `DB_HAS_HASH` (from the snapshot the restore took, so "the entry was there and Nx ran the task" is told from "it never was"), and the earlier executions of the hash with their workflow, cache stage and save outcome.
- **The comment says it.** `### Cache problems` is in every render (`_none: no cache restore failed_` when clean): each failed restore or save of the run with layer, job, key and reason, then why tasks ran with the seconds each reason cost. The cache section adds, per stage over the last 20 runs, the replay split into "inputs changed" (ran under a hash no run had executed) and "exact hash seen before" (ran or replayed under a hash a run had already executed and passed): the second column must be near 100%, red under 90%, amber under 98%. Gauges from the report job: `ci.nx.miss_tasks{stage,reason}`, `ci.nx.miss_s{stage,reason}`, `ci.nx.exact_replay_ratio{stage}`.
- **Fixed after it:** the save gate (`wf cache gate nx`, above), the e2e workflow's missing Nx restore and save, and the false restore timeout. Still open: the Actions cache's size and evictions cannot be read from the sandbox, so only a restore that finds nothing (`miss`) or fails shows them. Read the effect of the gate with `SELECT MISS_REASON, COUNT(*), SUM(MS)/1000 FROM NX_TASKS WHERE OUTCOME = 'ran' AND RUN_ID IN (<runs since the gate landed>) GROUP BY 1`: `restored-but-reran` and `earlier-save-skipped` should go to about 0.
