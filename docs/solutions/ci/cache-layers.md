# Cache layers: one job each, one bucket, one `wf cache` verb each

Every cache the build uses lives in the OCI bucket `mobile-learning-build-cache` and is reached through `wf cache`. Run `wf cache --help` for the live list and `wf cache status` for what each layer holds and how many requests the month has spent.

| Layer | Caches | `wf cache` verb | Prefix | Lifetime |
|---|---|---|---|---|
| Nx | whether a task runs, and its declared `outputs` (Rust verdicts, lint, typecheck, the web export) | `wf cache nx` (the loopback shim `wf test run --stage` starts) | `nx/` | 14 days |
| sccache | Rust compile output of cargo runs in the sandbox and in CI jobs (not inside the Docker builds) | `wf cache sccache` | `sccache/` | 7 days |
| pnpm store | downloaded npm packages | `wf cache pnpm` (`restore`, `save`) | `pnpm/` | 60 days |
| Metro and tsc state | the Metro transform cache and the `tsc` build info, one tarball | `wf cache metro` (`restore`, `save`) | `metro/` | 14 days |

Docker has its own: BuildKit layers on the VM and the registry cache `docker.io/<namespace>/<image>:buildcache` (`clis/deploy/src/build_image.rs`). Every Rust image but `clis/t3-serve` and `clis/orca-serve` compiles its dependencies in one cargo-chef layer (those two still build the whole closure in one `cargo build` layer, so any source change recompiles every dependency until they are moved to chef: open item, it needs a Docker build against the registry to verify) (`cargo chef prepare` writes a `recipe.json` of the service's dependency tree, `cook` compiles only that), so a source change rebuilds the service's own crates and a dependency change rebuilds that one layer. sccache is not used there: measured on 26 Oct, a warm chef layer builds in 14 s and sccache in 99 s, and an sccache entry is machine code for one architecture (the sandbox is x86_64, the images are arm64), so the sandbox cannot seed it for the VM; Nx shares across the two because it stores verdicts, not binaries.

A Rust service that has its own Cargo workspace (`backend/<service>/Cargo.toml` and `Cargo.lock`; reporting-service so far) has its own dependency versions and its own image hash: a change to its manifest or lockfile redeploys that service only. Its `.cargo/config.toml` points `target-dir` at `backend/target`, so compiled dependencies are reused across the services in the sandbox and on the runner; cargo keeps two versions of a crate side by side.

## Rules

- A cached Nx target that writes files lists them in `outputs`; one that only passes or fails lists none. `clis/pipeline/tests/flow/cache_contract.rs` fails on a cached target that is neither a known verdict nor a declared file writer.
- Nx outputs restore only on an exact input hash. State that must survive a changed input (Metro's transform cache, `tsc`'s build info, compiled crates) is not an Nx output: it is a restore-latest tarball (`metro`) or a per-compile cache (`sccache`).
- The EAS export is the cached Nx target `export:eas` (`expo export` for ios and android into `dist`, outputs `dist`; its inputs add the initial route, the app environment, the platform and bytecode flags). `publish:eas` runs it, then uploads with `eas update --skip-bundler`: the upload is a side effect and runs every time, only the export is replayed. Its Metro transform cache is restored and saved by `wf cache metro` around the publish; the web export is the `export:web` target.
- Invalidation is by key, never by hand: Nx by input hash, sccache by source, flags, compiler version and dependency hashes, the tarballs by lockfile and config hash; every prefix also expires by the bucket's lifecycle rule (`infra/oracle-cloud/build-cache.tf`).
- A run that cannot reach the bucket, or that is over a cap in `clis/blob-cache/data/budget.json`, goes cold, never red. Only a clean tree on `origin/dev` with pinned tools writes.
- Free-tier headroom is checked with `oci os bucket get --bucket-name mobile-learning-build-cache --namespace-name <ns> --fields approximateSize`; the Always Free Object Storage allowance is 20 GB across buckets, and 50,000 API requests a month.
- A slow live-model e2e suite is split into one Nx task per group, so a change reruns only the groups it can move. A crate lists `[package.metadata.e2e]` in its `Cargo.toml`: `groups` (a module of `tests/e2e.rs` each), `shared` (files every group reads), `src` (the crate sources the suite exercises) and `extra`, all relative to the crate dir. `tooling/nx/cargo-crates.js` then defines `cargo-e2e-<group>` instead of `cargo-e2e` (command filtered by `<group>::`), keyed by the toolchain, `^rustProduction`, the workspace files and lockfile slice (below), and those files only; `wf test plan` emits one `cli-e2e-tests` entry per group and `wf test run --stage cli-e2e-tests` runs the targets together, so `WF_PUSH_CLI_E2E=1` seeds each group on its own. `crate-offload` has four: `ask`, `parity`, `parity_features`, `parity_capabilities`. The batch, runbook, pricing and worker sources are outside `src` because no group drives them. A new module of `tests/e2e.rs` must be added to `groups`, or it runs in no task. `clis/pipeline/tests/flow/nx_cache.rs` holds the contract.
- A Rust task (`tooling/nx/cargo-crates.js`) is keyed by its crate (`rust`), its path dependencies (`^rustProduction`), its workspace's `Cargo.toml` and `.cargo/config.toml`, and its slice of `Cargo.lock`: `tooling/nx/cargo-lock-slice.js`, a runtime input, hashes only the lock entries the crate's dependency closure reaches (as `wf ship` keys images), so a lockfile edit for one crate reruns the crates that build it, and a comment reruns nothing. A lockfile that does not parse, or lacks the crate, is hashed whole.
- A crate inside a pnpm package is that package's files, unless the package sets `"nx": {"cargoCrates": true}` in its `package.json`: then each of its crates is a `crate-<name>` project with `cargo-clippy` and `cargo-unit`, and the package depends on them. Nx's `targetDefaults` beat a plugin's target inputs and a named input cannot take `{input, projects}`, so the package's own `nx.targets` key `test:flow` and `test:integration` on `["cargoFlow" | "cargoIntegration", "^rustProduction", {"externalDependencies": []}]`, named inputs the plugin defines from file sets: the dir of the crate the script runs (`-p <crate>`), its workspace files and lockfile slice, its `[package.metadata.flow]`, and the package.json. The remote chat agent opts in: its TypeScript e2e tests, Dockerfiles and compose files no longer rerun its flow suite.
- What a crate's tests read beyond the crate is in its `[package.metadata.flow]`, all from the crate dir: `inputs` (files, for the flow tests), and `uses` (crates whose binaries the flow and integration tests build and run, from any workspace: their sources, path dependencies, workspace files and lockfile slice, for those tasks only, not clippy or unit). A `uses` or group name that is no crate stops the graph with an error naming it on stderr; `wf test run` gives Nx `NX_ISOLATE_PLUGINS=false`, as a plugin worker's stderr can be lost when Nx exits. Never override a crate's `cargo-flow` inputs in a `project.json`: that replaces the plugin's list, lockfile slice and `externalDependencies: []` with the whole lockfile. `wf test plan` reads the same keys: a changed file an `inputs` glob (or a group's file glob, or `shared`) matches, or a reached crate a `uses` names, plans the crate's flow entries (and, for `uses`, its integration entry) and nothing else of it. A package that opts in is planned the same way, by its crates: one that depends (cargo) on a reached crate, runs one (`uses`) or reads a changed file (`inputs`) puts the package's own scripts in the plan, so Nx is asked to run a suite it would rerun (`packages_reached_through_crates` in `clis/pipeline/src/test_plan.rs`; the planted cases are in `clis/pipeline/tests/flow/pipeline.rs`).
- A declared glob (`inputs`, a `uses` crate's dir, e2e and flow group files) leaves out every crate nested under it, which is a project of its own; Nx applies a task's `!` file sets to all of them, so a nested crate the task itself names stays in.
- A slow flow suite can be split like the e2e one: `[package.metadata.flow] groups = { <group> = [...] }` (a module of `tests/flow.rs` each, `tests/flow/<group>.rs`) and `shared` (files every group reads). Each group is a `cargo-flow-<group>` task instead of `cargo-flow`, keyed by the crate's own sources, its module, `shared`, the files and crates the group lists (an entry without `/`, `.` or `*` names a crate), and every path dependency no other group names; `wf test plan` emits one `flow-tests` entry per group. A new module must be added to `groups`, or it runs in no task.
- A crate with a `tests/integration.rs` has a `cargo-integration` task next to `cargo-flow`, keyed like it plus `[package.metadata.integration]` (`inputs`, `uses`). It is in the weekly drift audit's target list (`TARGETS` in `clis/pipeline/src/nx_drift.rs`) with the other cached targets: a target missing there can move its hash with the checkout's path or the environment unseen, so add a new kind of cached target to that list when `tooling/nx/cargo-crates.js` starts to create it.
- `clis/pipeline/tests/flow/nx_crates.rs` holds these keys: a fixture of three cargo workspaces under the real `nx.json`, plugins and Nx, one planted change per case through `wf test run --stage`.

## CI today: the GitHub Actions cache, one switch for the backend

The Oracle bucket is gone, so hosted CI uses `actions/cache` (pinned by SHA) until another store exists. Which backend a layer uses is one repository variable, `CACHE_BACKENDS` (read as `env.CACHE_BACKENDS` by every cache action, set at the top of `pipeline.yml`):

| `CACHE_BACKENDS` | The Actions-cache steps | The blob store (`wf cache`, the build-cache shim of `wf test run`) |
|---|---|---|
| `gha` (default) | on | off (`WF_BLOB_CACHE=off`) |
| `blob` | skipped | on: the stores in `BUILD_CACHE_READ_STORES` and `BUILD_CACHE_WRITE_STORES` |
| `gha,blob` | on | on: reads take the first hit, writes go to every store |

Moving to R2 or Hetzner Object Storage is the variable plus the two store lists (`clis/blob-cache/src/stores.rs`), with no workflow edit. The sccache layer is the one exception to `gha,blob`: sccache has a single backend, so while the blob shim owns `RUSTC_WRAPPER` the directory cache stays out (`sccache-cache` does nothing when `WF_BLOB_CACHE` is not `off`). `CACHE_PNPM=on` brings the pnpm store back; it is off because it does not pay.

What each layer is worth, measured on 14 Nov (run 43558013495, `docs/audits/2026-11-14-ci-cache-bench.md`): sccache 96 s per use for 268 MB, metro 70 s for 17 MB, nx 38 s (identical rerun) for 1 MB, the pnpm store 13 to 17 s for 705 MB (and none in the real jobs), the rust target directory 86 s for 348 MB (sccache beats it), toolchain 4 s, cargo registry 0.5 s. Together the layers kept hold about 0.6 GB: the 10 GB quota is not the constraint, key churn is.

| Layer | Path | Key | Restore keys | Saved when |
|---|---|---|---|---|
| sccache | `~/.cache/sccache` (`SCCACHE_DIR`; `RUSTC_WRAPPER=sccache`, `CARGO_INCREMENTAL=0`) | `sccache-<stage>-<os>-<arch>-<ISO week>-<hash of every Cargo.lock>` | `sccache-<stage>-<os>-<arch>-` | `wf-build` and shard 1 of `flow-tests`, `integration-tests`, `cli-e2e-tests`; exact key missed, under 1.5 GB |
| metro | `frontend/mla-tamagui/node_modules/.cache/app-build` (Metro's transform cache and tsc build info) | `metro-<scope>-<suffix>-<os>-<arch>-<ISO week>-<hash of pnpm-lock.yaml, package.json, metro.config.js, babel.config.js, tsconfig.json>` | `metro-<scope>-<suffix>-<os>-<arch>-` | green job, exact key missed (`export` scope in eas-update only on `ship`) |
| nx | `~/.nx/*/cache` and `~/.nx/*/databases` (Nx's local cache and its index) | `nx-<stage>-<shard>of<count>-<os>-<arch>-<run_id>-<attempt>` | `nx-<stage>-<shard>of<count>-<os>-<arch>-` | not cancelled, more entries than restored, under 3 GB |
| pnpm (off) | `pnpm store path` | `pnpm-<os>-<arch>-<hash of pnpm-lock.yaml>` | `pnpm-<os>-<arch>-` | `CACHE_PNPM=on`, `flow-tests` shard 1, exact key missed |

- The sccache entry is per stage, week and lockfile set, not per run, so the quota holds a handful of entries. A stage compiles the same third-party dependencies in every shard, so the one shard that saves covers most of what the others need; the workspace crates of a changed commit recompile (incremental profiles cannot be cached by sccache). A miss costs about 10 s over no cache (bench: 182 s against 172 s).
- Metro's key is per input hash, not per commit: Metro and tsc key their own entries by file content, so one entry serves every commit until an input changes, and the ISO week in the key refreshes it weekly. A per-commit key would write a near-duplicate entry for each push into the shared quota. The `typecheck` and `export` scopes keep tsc's state and Metro's apart.
- Nx's key is unique per run so a later run restores the newest entry of its shard prefix. A save is skipped when no task result was added (every task replayed), which stops identical copies filling the quota. Workflows only restore and save the directories; `wf` gives Nx its environment (`clis/pipeline` flow test `no_workflow_or_action_sets_the_nx_cache_environment_wf_gives_nx`). A changed shard count starts a new prefix. Each job prints the directory size before saving and refuses a save over 3 GB (`::warning::`). The compile jobs of the bench run `--fresh`, so the cached Nx directory is about 1 MB: it holds verdicts, not binaries.
- Every restore writes one line to the job summary (layer, hit, partial with the matched restore key, or miss, and the restored size), through `.github/actions/cache-summary`; a save writes its size and the decision.
- Not cached, and why: the toolchain and the cargo registry (seconds, hundreds of MB), the rust target directory (sccache wins), Playwright's browsers (the bench control skipped `--with-deps`, so its 20 s is an upper bound; measure with a fresh runner and `playwright install-deps` before adding it) and the reference submodules (58 s in each of 12 jobs; the bench save raced a git auto gc, fixed, and the layer is measured again in the next bench run).
- Limits: the repository shares 10 GB across all caches, evicted least recently used first, and an entry unused for 7 days expires. Caches saved on `dev` are readable by runs on `dev`; `dev` is not the default branch, so `main` and pull requests do not see them and a run on `main` cannot seed `dev`.

## The tenancy cap and the storage guard

The 20 GB Object Storage cap is the tenancy's, not the bucket's: build-cache, verification-artifacts, pnpm-cache, goldens and tfstate share it, and `always-free-quota.tf` stops writes at it. On 6 Nov it was full and every cache PUT was refused with HTTP 400 `StorageQuotaExceeded`, silently (a rejected PUT only skips the entry, so runs stayed green and cold). Two things now keep that loud and rare:

- The plan job of `pipeline.yml` starts `wf cache guard` in the background first thing and collects it last (`continue-on-error`, `timeout 60`; it is started with the runner's step tracking id cleared, or the runner kills it when the step ends, and the last step waits 5 seconds at most). The runner's wait for agent-shell is 45 s and cancels the remote job, the remote guard stops its own calls at 30 s. The runner holds no OCI key: the verb asks agent-shell, which has the `oci` CLI and `~/.oci` (written once from the `OCI_*` vault secrets, as `wf vm creds sync` does), to run `wf cache guard --local` through vm-ops-api's signed exec route, the access the deploy legs use. It prints one JSON line, `{"event":"storage-guard", action, usedBytes, usedBytesAfter, capBytes, deletedObjects, freedBytes, buckets, layers, evicted}`, always exits 0, and the job logs it as `wf: storage guard <json>`, adds it to the run summary and raises a warning annotation whenever the action is not `none`.
- Above 85 percent of the cap it deletes until usage is under 70, cheapest first and oldest first within a class: `sccache/`, `metro/`, `probe/`, `nx/`, old `pnpm/` generations (never the newest store and its sidecar), verification `test-runs/` bundles older than 3 days, then `eas-updates/` and `device-lab` older than 3 days. It never touches tfstate, goldens, `libs/`, `meta/`, the `latest-<branch>` pointers and the update group each names (the guard reads the pointers; one it cannot read spares every group), the indexes beside the folders, or any object younger than 1 day. A delete names the version the object was listed with (`--if-match`), so an object a writer re-PUT since the listing is left alone. Evicted `test-runs/` bundles stay in `verification/test-runs/index.json`: whatever follows an index entry (the reporter Routine, the nightly review) must tolerate a 404. `wf cache guard --local --dry-run` shows what a run would delete. The policy is `clis/blob-cache/src/storage_policy.rs`; the run is `storage_guard.rs`.
- The cap is `tenancyStoredBytes` in `clis/blob-cache/data/budget.json`, and a test (`clis/blob-cache/tests/build_cache_tf.rs`) fails when it differs from `always_free_object_storage_cap_gb` in `always-free-quota.tf`. Usage is what the listings of the build-cache and verification-artifacts buckets add up to, because a bucket's own size figure lags a delete by hours and would make the next run evict again; the other two buckets count their approximate size. What the line reports as deleted is what the store confirmed, also when a delete failed half way.
- A cache write refused with `StorageQuotaExceeded` is counted in the run's `wf: build cache {...}` line as `quotaExceeded`, adds one `wf: build cache storage quota exceeded` stderr line, and shows in the `cache` block of the test run bundle. It does not cool the cache (the store is fine, only full), so read the count, not `degraded`. The CI report flags it: a headline `Object Storage full: N cache write(s) refused` and a note on the job row.
- The guard runs the wf that agent-shell keeps (`/workspace/home/wf-bin/wf`): until that copy has `cache guard`, the runner's line is `action: skipped` with a `skipCode` and the reason (cleaned of key blocks and passphrases). `oci` is installed in the agent-shell image at a pinned version (`infra/oracle-cloud/agent-shell/Dockerfile`). `skipped` on several runs in a row means the guard does not work (no `oci`, no vault access to the `OCI_*` secrets, an old wf there): fix it, it is the silent failure the guard exists to end.

## Observability

Every cache operation is one logfmt event (source `ci-cache`) and a few gauges on the Better Stack source that `BETTERSTACK_METRICS_HOST`/`_TOKEN` name (`wf cache --help` lists both). The store's failure reaches the event as a class and an HTTP status only (`unreachable`, `credential`, `rejected`, `quota-exceeded`), never its words. A dirty tree and a dropped put are `warn` events with the paths and counts. Gauges are best effort and bounded to two seconds. A `Reading` has two labels, so `ci.cache.requests{kind,result}` is `scope=kind, name=result`, and a one-label metric carries `all` in `name`.

### Health: what fails a run and what is guarded

`wf ci cache-health` is the last step of the report job: it reads the `ci-cache` events and `wf: build cache {..}` lines of the run's job logs and exits 1 on a degraded layer, a refused or dropped required write (the tenancy's storage quota included), writes the store acknowledged but does not hold (`seeded 7 of 10`), a stage the pre-push gate runs that replayed nothing on a push to dev, a drift report, or a pnpm save over 60 s. The same verdict is the "Cache health" section of the live PR comment. A disabled shim is a note and a `wf: build cache disabled for this run` line, never silent. Alert rules: `docs/runbooks/cache-health-alerts.md`.

Guards that keep a refusal from costing minutes: `wf cache save pnpm` checks the store's size against the entry cap (a tree over four times the cap cannot pack under it) and writes a one-word probe object before packing, so a full tenancy (`StorageQuotaExceeded`) is a `store not packed` reason in seconds, not a refused upload after the pack. Every shim layer asks the store for a sample of what it wrote when it stops (`seeded_checked`, `seeded_present`), and the pre-push gate refuses a stage whose entries are missing (`seeded N of M`), as it refuses one that only read the cache.

## Platform tiers: the platform is in no key by default

A task passed on x86_64 counts for arm64: no cargo task hashes the platform unless its crate is in the platform tier, and the tier is per crate.

- **Default**: the key is the crate's sources, its dependencies' sources, its lockfile slice and the Rust toolchain. A pass on any platform replays on every other.
- **Platform tier**: every cargo task of the crate (clippy, unit, flow, integration, e2e, contract) adds the named input `platform` (`node -p "process.platform+'-'+process.arch"`, `nx.json`), so each CPU keeps its own entries. A crate is in the tier when its `Cargo.toml` says `[package.metadata.flow] platform = true`, or, with no flag, when `tooling/nx/cargo-crates.js` finds `cfg!(..)`, `#[cfg(..)]`, `#![cfg(..)]` or `cfg_attr(..)` on `target_arch`, `target_pointer_width` or `target_endian` in its `src/`, `tests/`, `benches/` or `build.rs` (comments and string literals ignored; `target_os`, `unix` and `target_family` do not count: every machine that writes the cache is Linux).
- `platform = false` overrides a scan hit that is no CPU difference; give the reason in a comment beside it.
- **No inheritance**: a dependent of a platform crate stays in the default tier; its tier comes only from its own flag or its own code.
- `wf test drift` reports a table that differs by the platform as a cause of kind `platform`.
