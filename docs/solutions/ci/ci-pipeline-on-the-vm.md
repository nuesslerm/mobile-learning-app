# The CI pipeline

Moved verbatim from the always-on `CLAUDE.md` section "CI runs on the VM" (8 Nov 2026), where a short rule now points here.

Pushing to `dev` runs one pipeline: `ci-hosted.yml` ("CI (GitHub-hosted)"), a thin caller of the reusable `pipeline.yml` (see `one-pipeline-two-flavors.md`; the self-hosted runner on the VM was removed on 2026-11-13, so every job runs hosted), on GitHub-hosted runners that join the tailnet as `tag:ci-gh-hosted`, each job doing one thing: `plan` (`wf ci plan tests`: every test the push needs, by stage; `wf ci plan legs`, run only when the stages include deploy or e2e (a core or cli run skips it and the relay pair; with `deploy` false it passes `--no-lookup` and asks no service for its running commit): a service ships only when its image input hash (Dockerfile, the context files it copies, the Cargo.lock entries of its crates; tag `nx-<hash>`) differs from the running image's `wf.input-hash` label; it and the two test jobs run this commit's wf, as the hosted flavor does; the wf the previous push published only stands in when this commit's did not build, so a long run of red pushes cannot leave the test jobs on a stale wf) -> `core-tests` (the flow stage and the typecheck stage side by side on each shard's 4 cores, stages keep their names; the flow stage is every package's `test:flow`: frontend and Rust services and CLIs, through their main entry point with every external dependency doubled, a real Chromium included; each `clis/wf-*` crate is its own `cargo-flow` task over its thin binary, so a change reruns that crate and the crates built on it; the typecheck-lint-unit-tests stage is also `cargo clippy -D warnings` on every CLI crate the push reaches, an Nx `cargo-clippy` task) -> `clis` (the one wf build) -> `deploy (<service>)` (an app with images is built by the `build-image` action, then `wf ship --redeploy-only --smoke <app> --ref <sha> --tag sha-<8> --wait-serving`; each phase printing its seconds: the pulled image run as a throwaway container on a spare port in the live one's netns, which `wf` asks for `/health` over the tailnet (signed for vm-ops-api) before stopping it, a failure failing the leg with the container's log or the probe's error and swapping nothing; the swap, which answers with its own result (vm-ops-api swaps itself through a detached script, restores the old stack on a failure and records `redeploy.failed` and `restored` in `/redeploy/status`); then one bounded /health check, done when the service serves the commit; the app is no leg, its EAS Update is the `eas-update` job below) -> `integration-tests` (every `test:integration`: the built binary run as a black box, every dependency a fake, mocked contract tests, never a real dependency) -> `cli-e2e-tests` (each crate's `tests/e2e.rs`, `cargo-e2e`: a real Chromium or ffmpeg driven through the CLI binary; the rca crate starts its own rca-service and opencode on the runner and needs only the `OPENCODE_GO_API_KEY` model key, no deployed service) -> `deployment-verification-tests` (`test:verify:deployed` of every changed package: real calls against the deployed service) -> `browser-e2e-tests` and `android-e2e-tests` (both `e2e-tests.yml`, each in two shards dealt over `shard-weights.json`: the focused e2e tests the push reaches, one harness each; the browser job joins no tailnet: it builds the leetcode backend and rca-service on the runner and starts them with `opencode serve` and the faster-whisper speech sidecar (`wf test backends up --only stt,opencode-server,rca-service,leetcode-backend`, sccache stage `browser-e2e-tests`; the vault's `OPENCODE_GO_API_KEY` is the live model key voice-edit and tamil-writing need), then a web export of the commit (`wf test prepare --web`, the two backends' loopback urls and the leetcode token of the run baked in, the vm-ops url a closed port) and serves it on loopback; the Android job joins no tailnet either: it starts the same backends on ports 8787 and 8789 (the leetcode token is the fixed `E2E_LEETCODE_BEARER`), boots the device once, cold, and its tests load the e2e variant of the EAS Update (`WF_EAS_UPDATE_BRANCH=e2e`), which the `eas-update` job publishes beside the production one (`wf ship eas --platform android --branch e2e --pointer`, whenever the app's package graph changed since the commit `latest-e2e.json` names) with the backends baked as `10.0.2.2:8787` and `:8789`, the emulator's alias of the runner; the stub server forwards `10.0.2.2` to the runner's loopback: the `eas-update` job writes the branch pointers and group summaries into `$RUNNER_TEMP/eas-pointer` (`WF_EAS_POINTER_DIR`) and uploads them as the run's `eas-pointer` artifact (2 days), which `e2e-tests.yml` downloads before the harness and points `WF_EAS_POINTER_DIR` at; with no artifact (a dispatch, a skipped eas-update) the reader falls back to its own source; a failed or stale update errors the units; `wf test backends down` first prints the last 80 lines of each backend's log in a `::group::` block named after it, the run's secrets masked, so a failed test leaves the backends' logs in the job log even when no bundle can be published). Every test stage runs through the Nx cache (`nx.json`, `tooling/nx`): a task whose inputs are unchanged replays its last pass, and an e2e test reruns only when its features (with what they import), test case or the app shell changed; services have their own deployment verification tests (the Nx cache's contract suite, real Nx on a copy of the repo and minutes long, is `clis/pipeline/tests/nx_contract.rs`, the crate's own `cargo-contract` task that `wf ci plan tests` selects only when a file that can move the contract changed, not for the CI report). A push tagged `[services:all] [cache:no]` that changes a file (an empty commit starts no CI run) redeploys every service and republishes the EAS Update with nothing replayed. The local gate is still lefthook pre-commit: `wf check --staged` (lint, affected typecheck and unit/flow tests, the simplicity budget; `wf check --budget` alone) plus secrets; a red hook is the failure to fix, never to bypass. Production ships only by a push to `dev`: no verb builds an image outside CI (`wf ship --build-only` is refused as an unknown option, `vm-ops-api` has no build route; a hand build is docker buildx in agent-shell's own docker, never into a production tag), and a pushed tag is redeployed with `wf ship <app> --ref <sha> --redeploy-only --tag <tag>`. agent-shell is deployed by hand; vm-ops-api ships first, proving and swapping in the image its leg pushed (`POST /redeploy?ref=&tag=`), so the other legs deploy through it. The other workflows (lint, architecture, tailscale, hosted-minutes) run only by hand; `hosted-minutes.yml` measures a hosted runner's minutes for the CI-scoped vault plan (`docs/solutions/ci/hosted-minutes.md`). Long reference captures run on a hosted runner for an empty `dev` commit whose message is `[record <set>...]` or `[replay <set>...]` (`mimic-record.yml`; `wf ci plan mimic --help`).

A red test never hides the e2e jobs' errors (#83 E4). The test stages run in parallel with `fail-fast: false`, and `deploy` and `clis` keep skipping on any red `core-tests`, `integration-tests` or `cli-e2e-tests`, so a red test never ships a service. Because a red test leaves `clis` and `deploy` skipped, never successful, the other jobs read them as "not failed": `eas-update`, `browser-e2e-tests` and `android-e2e-tests` run when `clis` and `deploy` are not `failure` and no longer look at the four test stages (they dial no deployed service: the browser job builds its backends on the runner, the Android job loads the `e2e` EAS branch with the backends at 10.0.2.2). `deployment-verification-tests` is the one job that dials the deployed service, so it needs `deploy == 'success'` unless no leg was planned. The production EAS Update (branch `dev`, what phones open) ships whatever the tests say: `Publish the EAS Update` is gated only on being the head of `dev`, because this is development and every push is fine to build; a red test still never ships a service.

## The build verb (what runs where)

Written for issue #367 (`docs/plans/ci-scoped-vault-access/plan.md`, U1.7); the only build path since the old one was retired.

- **Daemon.** Image builds run on the GitHub-hosted runner's own docker daemon.
- **`wf ship build <app> --tag <tag>`** runs in the CI job, never on the VM's agent-shell. It hashes each image of the app (its own and the sidecars its compose pulls) at `--ref` (default `HEAD`), logs in with `DOCKERHUB_TOKEN` on stdin, uses a `docker-container` buildx builder named `ci-builder` on the daemon `DOCKER_HOST` names (the runner's own by default), and pushes `<image>:<tag>` and `<image>:nx-<hash>`. An image whose `nx-<hash>` is in the registry is re-tagged with the commit, not rebuilt. It prints one JSON line. The old remote build (`wf ship --build-only`, a script run in agent-shell through vm-ops-api) is retired: the first green push on this path was run 42523195784 (commit fda082ad6).
- **`wf ship promote <app> --tag <tag>`** points `latest` of each image of the app at the tag with `docker buildx imagetools create`, registry to registry, on the runner's docker (no vm-ops-api route; it logs in with `DOCKERHUB_TOKEN` on stdin like `ship build`). The `Promote the verified images to latest` step of the `vm-ops-api` leg runs it with `--tag sha-<8>` after the leg is smoke-tested and serving, on a push to dev, so a recreated VM pulls a build that served.
- **Deploy legs** of an app with images build through the action below, then `wf ship --redeploy-only --smoke <app> --ref <sha> --tag sha-<8> --wait-serving`; the legs of apps with no image run `wf ship <app> --ref <sha> --wait-serving` (a redeploy at `latest`). `wf ship build <app> --images` lists an app's images; `--cache-push` (a push to `dev` only) also writes the registry layer cache `<image>:buildcache`, which every build reads.
- **`.github/actions/build-image`** (inputs `app`, `tag`, optional `dockerhub-token`, `cache-push`) builds on the runner's local docker daemon. The token is in the env of the push step alone (read there with `wf secret get` when the input is empty). A step writes the daemon's name and version to the job summary.
- **Buildkit is stopped after each build.** `wf ship build` makes a `docker-container` buildx builder (`ci-builder`), which keeps a buildkitd running after the build. The `build-image` action ends with `docker buildx stop ci-builder` (state volume and layer cache kept; the next build starts it again) and logs the buildkit memory before and after in the job summary.
