## Context

`wf secret` (`clis/secrets/src/secrets/`) reads the single source of truth at `clis/secrets/src/data/registry.json`, which enumerates each secret as a `{ service, envVar, description }` record mapping an env-var name to a backend lookup key (e.g. `TELEGRAM_BOT_TOKEN → telegram-bot-token`, `OPENCODE_GO_API_KEY → opencode-api-key`, `LEETCODE_BACKEND_ADMIN_SECRET → leetcode-backend-admin-secret`). Two app entrypoints — `backend/leetcode-auth-cookie-capture/rs/src/main.rs` and `backend/remote-chat-agent/rs/src/main.rs` (through the `rca_service::infrastructure::secrets` re-export) — call `service_kit::secrets::load().await` (`backend/service-kit/src/secrets.rs`) before reading `std::env::*`. `load()` runs `wf secret env --keys <the registered vars still unset>` (or `$WF_BIN` in place of `wf`) and, best effort, fills only those vars from the active backend: when nothing is missing it starts no process, and when the vault is unusable or the call takes over 60 s it warns once on stderr and startup continues with the existing environment. Two env-var names carrying the same secret value can share it: on the keychain, point both at the same `service` string in the registry and one `wf secret set` populates both; Bitwarden never reads `service` (it matches by `bitwardenKey`, else `envVar`), so there both entries need the same `bitwardenKey`, whose one vault item is created first and then rotated with `wf secret update`, which only rotates an item that already exists (see Guidance). `.env.defaults` files are the committed non-secret config (ports, URLs, modes, file paths, public identifiers); `.env` is generated and gitignored, written by `wf secret sync-env --for <app> --base .env.defaults --out .env`, and holds real values — on a host it (with the `.env.synced` copy vm-ops-api's redeploy keeps) is where the resolved secrets land.

Backends are pluggable behind the `Backend` trait (`clis/secrets/src/secrets/backend.rs`, implemented by `Macos` and `Bitwarden`). Pick the production backend with `--backend <name>` or the `SECRETS_BACKEND` env var; the `resolve` port takes the whole registry entry, so each backend reads whichever addressing field it needs (see the override fields below):

- **`macos`** (the default on darwin) — wraps the `security` CLI, exactly as before. This is the local-dev path and no-ops entirely off darwin. Off darwin the default is `bitwarden` (`default_backend_name()` in `backend.rs`), so a bare `wf secret get`/`list`/`env` on Linux or in a sandbox reads the vault; any backend name other than `bitwarden` there — `--backend macos`, `SECRETS_BACKEND=macos`, a typo, or a removed name such as `lastpass` — silently resolves nothing rather than erroring (`build()` in `backend.rs` falls back to `Macos`), which reads exactly like "the secret doesn't exist." Off darwin, leave the default or pass `--backend bitwarden`; `set` and `delete` take no `--backend` option, so for them only `SECRETS_BACKEND` or the default selects the backend; see `docs/solutions/security/wf-secrets-default-backend-and-redaction-pitfalls.md` for the failure modes this causes and how to verify a secret's existence without ever printing its value. With this backend `wf secret set` stores into the keychain and `wf secret delete` removes from it; `delete` only ever touches the keychain.
- **`bitwarden`** — wraps the `bws` CLI (Bitwarden Secrets Manager), authenticated by a **machine account** token in `BWS_ADMIN_ACCESS_TOKEN` (read-only; a second write-capable `BWS_ADMIN_ACCESS_TOKEN` exists for the vault writers and never ships to a VM or a CI deploy: it is in no `clis/secrets/src/secrets/groups.json` group and cloud-init never writes it, and the one workflow wired to read it, the manual `.github/workflows/tailscale-rotate-auth-key.yml`, documents that CI holds no such secret by design; it lives on a laptop or in an agent session's environment). The backend's own store/remove are read-only, so `wf secret delete` fails on it, but `wf secret set` with this backend writes the vault item through the edit token (updating it, or creating it in the default project), as `create`, `update` and `rename` do (`clis/secrets/src/secrets/writers.rs`; those three are dry runs until `--apply`). `set` keys the vault item by `envVar` and ignores `bitwardenKey`, so for an entry whose `bitwardenKey` differs (`EXPO_PUBLIC_BETTERSTACK_TOKEN`, `BETTERSTACK_INGEST_HOST`) it creates an item that resolve never reads; use `wf secret update <KEY> --value-stdin --apply` for those, which writes the key `bitwardenKey` names once that item exists (it refuses a vault key that is not there yet; see Guidance for creating one). `push-notes` copies registry descriptions into the vault notes the same way, also dry until `--apply`. The token's own project grant is the scoping mechanism — no separate project-id config. Lists secrets once (memoized) and matches by key — defaulting to the entry's `envVar`, overridable with `bitwardenKey`. **Genuinely free** at our scale (free tier: unlimited secrets, 3 projects, 3 machine accounts).

**`bitwarden` is the production default and the only production backend** — production deploys go through vm-ops-api's redeploy (`backend/vm-ops-api/core/src/application/scripts/redeploy.rs`), which runs `sync-env` with `--backend bitwarden`, and the legacy SSH `backend/*/scripts/deploy.sh` scripts default to it. It gives a **read-only, non-interactive credential from an env var** plus a real scoped machine token (per-project).

**There is deliberately no `lastpass` backend.** It existed until 2026-07-25 and was removed: `lpass` has no service-account concept, so it required a durable, already-unlocked `lpass login` session (MFA satisfied by a human) on every production host, and its scoping is folder/account-only — no per-item ACL, no machine token. Nothing selected it: the docs claimed it backed `backend/leetcode-backend`'s Oracle VM while that VM's `deploy.sh` had always defaulted to `bitwarden`.

**There are also deliberately no `onepassword`/`infisical` backends.** They existed until 2026-07-27 and were removed: both were alternative production backends, fully implemented and tested, but never selected by any deploy — `SECRETS_BACKEND` always defaulted to `bitwarden`. Removed the adapters, tests, the `BackendName` union members, the `onepasswordRef`/`infisicalSecret` registry schema fields, the `setup.sh` installers, and the `OP_*`/`INFISICAL_*` registry entries.

**No soft failures.** A backend distinguishes a genuine "the secret isn't there" (legitimately resolves to `null`) from an **operational error** — CLI not installed, auth failed, network down, unparseable output — which it turns into a thrown error carrying the real stderr, never a silent `null`. A broken backend must scream, not masquerade as "every secret is missing" (that's how empty secrets silently ship). Likewise `wf secret sync-env` **exits non-zero and refuses to write a partial `.env`** if any required key can't be resolved (a `--for` group's optional keys missing from the vault are skipped). The `resolve` port catching a failure into `null` (the old behavior) is exactly the trap this avoids. The service-side `load()` above is one deliberate exception: a deployed container gets its environment before it runs, so an unusable vault only warns. wf's own in-process loaders (`load_values` and `load_all_into_process_env` in `clis/secrets/src/secrets/mod.rs`, used by `wf offload ask`, `wf secret login`, `wf ship eas` and report runs, among others) are also best effort: an unusable backend warns once or yields nothing, and the caller reports the missing value itself. The other exception is the sealed local copy the Bitwarden backend keeps of the vault listing (`clis/secrets/src/secrets/cache.rs`): a fresh one (TTL 1 h, `WF_SECRETS_CACHE_TTL_SEC`) is used without calling `bws`, and on any list failure a copy up to 7 days old stands in with a stderr warning. `sync-env` always refreshes but falls back the same way, so it can write a `.env` from a stale copy instead of exiting non-zero. The write-capable list is always fetched live, and `WF_SECRETS_CACHE=off` disables the copy.

Each token-based backend (today only `bitwarden`) also resolves its **own bootstrap config** (`BWS_ADMIN_ACCESS_TOKEN`, falling back to `BWS_ACCESS_TOKEN`, the optional edit and gh-ci tokens, and `BWS_SERVER_URL`) **env-first, then from the macOS keychain** (`clis/secrets/src/secrets/backend.rs`, `resolve_backend_config`). So on a dev machine you can `wf secret set BWS_ADMIN_ACCESS_TOKEN` once and keep it out of your global shell env; on prod/CI you just export the env var. The resolved token is passed to the CLI via the child process env (never argv). Bootstrapping never routes through the active production backend (that would be circular).

### Telemetry (secrets CLI)

The per-command `secrets.*` BetterStack events (`secrets.get`, `secrets.set`, `secrets.delete`, `secrets.list`, `secrets.env`, `secrets.sync_env`) went with the TypeScript secrets package; `wf secret` does not emit them. What it records today, like every `wf` command:

- One anonymised row per invocation in `HEALTH_RPT.WF_USAGE` (Autonomous DB, `infra/oracle-cloud/sql/wf_usage.sql`, ORDS alias `wf_usage`): the command path (`secret get`), exit code, duration, the last error line noted through `wf_err!` (only on a non-zero exit; the secrets subcommands print theirs directly, so a failed `wf secret get` row has an exit code and no error text), wf's version, and the OS. **Never** the host, the arguments, or a key name — and the error is scrubbed like every log sink, with the home directory written as `~`. The writer is `clis/wf/src/usage_row.rs`; a detached copy of wf posts the row so the command never waits. `WF_USAGE=off` turns rows off (the flow-test harness sets it).
- Where `wf` does log to BetterStack — `wf log emit` (`clis/wf/src/log_emit.rs`, the shell scripts' logger) and the VNC auth-capture log (`clis/wf-login/src/vnc/log.rs`) — it goes through the `clis/telemetry` crate the Rust services also use; the secrets subcommands never call it. `SECRETS_LOG_BETTERSTACK=false` lives on as that crate's kill switch and turns off every BetterStack destination, not only secrets (`clis/telemetry/src/destination.rs`).

Scrubbing is **automatic across all logging**, not just this telemetry, on both sides. Rust sinks (the usage row, `wf log emit`, the VNC log, the services) scrub with `telemetry::redact::Redactor` (`clis/telemetry/src/redact.rs`). In TypeScript, `configureLogger` attaches a `scrubberPlugin` to the root LogLayer by default (opt out with `configureLogger({ scrub: false })`), so every log through every transport is scrubbed by the same rules before it leaves. `createScrubber`/`scrubberPlugin` live in `@lib/logging` — distinct from the older `redactSensitiveFields` Stage, which is a no-op under the pipeline's read-only batch contract. See `docs/solutions/conventions/logging.md`.

### Backend CLI setup

The Bitwarden backend's only external dependency is `bws`, pinned in `mise.toml` (`"ubi:bitwarden/sdk-sm[exe=bws]" = "bws-v2.1.0"`). The session bootstrap `.agents/setup.sh` runs `mise install` whenever `bws` (or another pinned tool) is missing, and `.github/actions/install-bws/action.yml` installs the same pin in CI. The backends themselves do **not** fail soft — selecting a backend whose CLI is missing or misconfigured throws loudly unless a sealed vault copy stands in (see **No soft failures** above; `WF_SECRETS_CACHE=off` forces a live list), so make sure `bws` is on `PATH` first.

## Guidance

- **Add a registry entry first.** Before introducing a new secret, edit `clis/secrets/src/data/registry.json` (add the env var → backend `service` → description, plus a `bitwardenKey` override only if that backend's item name doesn't match the default), add the key to the app's group in `clis/secrets/src/secrets/groups.json` so `wf secret sync-env --for <app>` writes it, and rebuild `wf` (`wf secret registry sync`). The registry is compiled into `wf` and `service_kit` with `include_str!`, so `load()` needs no wiring per secret and picks the entry up on the service's next build; a new app entrypoint calls `service_kit::secrets::load().await` once. Then ask the user to run `wf secret set <KEY>` with the real value (the macOS keychain on darwin; off darwin it writes the Bitwarden vault through the edit token, keyed by `envVar`). For an entry with a different `bitwardenKey`, `wf secret update` does not help at first: it only rotates an item that already exists and refuses a vault key that is not there yet. Create the item first, with `bws secret create <bitwardenKey> <value> <projectId>` under the edit token (`BWS_ACCESS_TOKEN="$BWS_ADMIN_ACCESS_TOKEN"`), or with `wf secret create <KEY> <projectId> --value-stdin --apply` when the vault name equals the registry key (`create` names the item after the registry key and refuses a name that is not one). After that, `wf secret update <KEY> --value-stdin --apply` rotates it.
- **Use `wf secret list|get|env|sync-env|set|delete|create|update|rename|push-notes|doctor|cache clear|registry sync`.** Those are the only commands for managing entries (`clis/secrets/src/secrets/mod.rs`'s `run()`, reached through the `secret` route in `clis/wf/src/routes.rs`, which sends `wf secret login` to the auth flow instead). Never write secrets to `process.env` from a script, never paste them into a `.env` file, never commit them to a config file under version control.
- **Two env vars that share a secret → one `service`.** If two apps must read the same secret under different env-var names (e.g. a shared trigger/notify secret), point both `envVar` entries at the same `service` string in the registry. On the keychain one `wf secret set` populates both. In Bitwarden, which matches by `bitwardenKey` or `envVar` and never reads `service`, give both entries the same `bitwardenKey`, create that one vault item as in the first point (`bws secret create` under the edit token, or `wf secret create` when the item is named after one of the two registry keys), and rotate it later with `wf secret update <KEY> --value-stdin --apply`, which only rotates an item that already exists; one vault item then populates both, with no duplication and no drift.
- **In tests, stub the backend's CLI or override the env, not committed fixtures.** `clis/secrets/tests/flow/secrets.rs` runs the real `wf secret` against a stub `bws` that serves a per-token vault listing. The `e2eSkip` guard the Telegram bot's tests used for unavailable credentials was deleted with the bot; there is no shared replacement.
- **Audit on every PR touching `registry.json`** — every new entry is a service id that now exists, every description change is a doc update, every rename is a one-time migration.

## Why this matters

A `.env` file with a real secret is a leaked credential the moment it lands in git history, even if later deleted. The backend-based model keeps secrets out of version control: the value never lives in a committed file and never crosses the wire in a config dump. On disk it exists in the generated, gitignored `.env` on the host (and the `.env.synced` copy vm-ops-api's redeploy keeps beside it), the sealed vault copy under `~/.cache/wf`, the owner-only rotation history (`~/.local/state/wf-secrets/rotation-history.jsonl`, the previous value of each `set`/`update`), each VM's `~/<app>/.env.local` (chmod 600; it holds the read-only `BWS_*` bootstrap token cloud-init seeds, which vm-ops-api's redeploy sources before `sync-env`), and wf's own `~/.config/wf/.env` (for example the usage-row ORDS credentials `clis/wf/src/usage_row.rs` asks for). Only the `bws` access token is kept out of argv (it goes through the child env); a value passed as an argument to `wf secret set KEY <value>`, and the value wf hands to `security add-generic-password -w` or `bws secret create`/`edit --value`, appears in a process listing while that command runs. The registry makes the *shape* of the secret surface auditable in code (reviewable, diffable, lintable) while the *values* stay in the OS-protected store (dev) or the vault (prod).

## When to apply

- Onboarding a new external service that needs an API key, token, or shared secret.
- Sharing a secret between two apps or two env-var names.
- Reviewing a PR that introduces a `process.env.SOMETHING_SECRET` read.
- Debugging "secret not found at runtime" — usually means the registry entry was added without a corresponding `wf secret set` (macOS) or vault item (production).
- Preparing a production deploy: the CI jobs on the VM's runner install `bws` (`.github/actions/install-bws/action.yml`) and read the vault with the read-only `BWS_ADMIN_ACCESS_TOKEN` the `gh-runner` container is given (`infra/oracle-cloud/agent-shell/docker-compose.prod.yml`); the `tailscale-*.yml` workflows on hosted runners (dispatched by hand; `tailscale-auth-key-expiry.yml` also runs weekly) read it through `bitwarden/sm-action` with their own read-only `BWS_CI_DEPLOY_ACCESS_TOKEN`, and the expiry watch also hands that token to wf as `BWS_ACCESS_TOKEN`. The target host holds its own read-only machine token, which is what `sync-env` uses.

## Examples

- Source of truth: `clis/secrets/src/data/registry.json` — every secret the repo knows about, with `service` + `envVar` + `description`.
- CLI surface: `wf secret list|get|env|sync-env|set|delete|create|update|rename|push-notes|doctor|cache clear|registry sync` (`clis/secrets/src/secrets/mod.rs`, routed by `clis/wf/src/routes.rs`).
- Real entrypoints that call `service_kit::secrets::load()`: `backend/leetcode-auth-cookie-capture/rs/src/main.rs`, `backend/remote-chat-agent/rs/src/main.rs`.
- Production deploy path: vm-ops-api's redeploy (`backend/vm-ops-api/core/src/application/scripts/redeploy.rs`, `sync_env_lines`) runs `wf secret sync-env --for <app> --backend bitwarden --base .env.defaults --out .env` before the compose restart (snapshot: `backend/vm-ops-api/core/tests/snapshots/app-redeploy.sh`). The legacy SSH script `backend/leetcode-backend/scripts/deploy.sh` runs the same command with `--backend "$SECRETS_BACKEND"` (default `bitwarden`), but nothing in CI or `wf` calls it.
- Provisioning helper: `wf secret login <tool>` (`clis/wf-login/src/help/wf__secret__login.txt`) — starts the login in the shared VNC desktop and waits until it finished (`--copy` also writes the credential here); formerly it ran the tool's native login locally and confirms the credential landed; `--remote` runs the one-time interactive login on the shared VNC desktop for a machine with no display.
- Test double: `clis/secrets/tests/flow/secrets.rs` (a stub `bws` per test and env overrides, no committed secret values).
