# The typed editor API (`@lib/code-editor-api`)

Text is canonical. Every client edits it through seven typed requests on one engine port, each answered with the document revision it applied to and the one it produced. Issue 86 (B1) is where it was decided; the later items (toolbar, syntax tree, semantic ops, block view, voice edit) add requests, step ops and events, never new engines.

## Shape

- `ports/`: the wire types (`Requests`, `Reply`, `EditorEvent`, `EditorError`), `EditorEngine` (`request`, `listen`: what a client calls) and `DocumentHost` (what an engine core needs from an editor).
- `core/`: pure. Changes and mapping (`mapPos` is CodeMirror's rule over the individual change list), the revision log, `planBatch`, the validators, `createEditorEngine(host)` with its FIFO queue, `createEditorClient` (sugar that never rejects), `createDocumentMirror`.
- `adapters/`: `serveEditor` (page side) and `toRemoteEngine` (host side) over `@lib/webview-rpc`, the only imports of it (the preset's `libraries` option).
- `testing/`: `createFakeEditor` (a string host under the same core), `editorContract` (the suite), `withFaults`.
- The CodeMirror host is `features/leetcode/data/editor/cm6/cm6Host.ts`, served beside the old messages from `cm6Bundle.src.ts` in the same folder; the view reaches the page through the leetcode feature's `EditorBridgePort`.

## Rules a client can rely on

- A call is one transaction, one revision (when the text changed) and one undo step. Steps are simultaneous and positions are in the document at `at`. Overlapping steps are refused: CodeMirror would merge them silently.
- `at` older than the head is `stale` unless the call says `stale: 'map'`, which maps ranges through the revision log and answers `range-lost` or `text-mismatch` (with `expect`) rather than editing the wrong text. A lost reply is retried with the same `at`: the retry is `stale`, so nothing applies twice.
- The app reaches the page through this API for everything that acts on the document or the focus: `focus`, selection, `insertAt`, `typeText` (the `type` step), `undo`, `redo` and the config it can express; a refused call is logged (`editor.port.forward_failed`) and does nothing. What still travels as a script: `init` and `blur` on iOS only (the page's own script, until a person has watched the typed one on an iPhone; `ForwardingOptions.blurThroughApi`). An `updateConfig` the API cannot express (`initialText`, an unknown key or language) is refused and logged (`editor.port.forward_failed`, code `unmapped-config`); the page no longer has `updateConfig`, `highlightRange`, `clearHighlights`, `showDiff` or `hideDiff` handlers. The flow tests drive the same API (`session.editor()` makes calls and reads a document mirror); the page keeps one test hook, `window.__editorDebug__`, which exists only when the page html is built with the debug flag and which the contract suite uses to simulate a person's typing and pointer selection.
- `configure({language})` is one request that changes the language and nothing else: the text, revision, selection and undo stack do not move and nothing is emitted. The languages an engine offers are in `hello.capabilities.languages` (the vocabulary is `LANGUAGE_NAMES`); a language outside what it offers is `unsupported` with `what: 'language'`, and a language set once stays through `load`.
- What the host can do is what `hello` announces, derived from the host's optional methods: the `type` step and the `complete` step (and the `completion` event) when it has them, the `tree` request when it has `tree()`, `view.marks` and `view.reveal` when it has `marks()` and `reveal()`. An engine whose host lacks one answers `unsupported` (`step:complete`, `request:tree`, `config:completion`) and does not list it. The core requests (`CORE_REQUEST_NAMES`) every engine answers.
- The `complete` step accepts the completion the editor has open, at the live selection, like `type` it is the only step of its call and acts on the head (an older `at` is `stale`); nothing open is `ok` with no change. The `completion` event says a list opened or closed, once per change. `configure({completion: {enabled, entries}})` turns completion on and gives it the names it may offer (at most 200, word characters only).
- The `tree` request returns the syntax tree as plain nodes (`type`, `from`, `to`, `error?`, `children?`) stamped with the instance and revision it describes, with `parsedTo` and `complete` when the budget ran out first.
- `tree` parses in slices of at most `treeSliceMs` and gives the event loop a turn between slices, so an apply asked while a tree waits is answered first; the job stops at `budgetMs` or when the head moves, and says so with `complete: false` (the tree then describes the revision it began at, `base`). Nothing in the tree is read past `parsedTo`: `isUnread` says so and callers treat that text as plain text.
- Syntax questions are pure functions over a tree reply (`core/syntax`): `nodeAt`, `nodesInRange`, `statementAt`, `enclosingBlock`, with node names classified by explicit per-language tables (`SYNTAX_TABLES`), never by pattern. The client has them as sugar (`client.enclosingBlock(pos)` reads the text and a point-range tree, retries once when a keystroke lands between the two reads, then answers `stale`). The fake editor answers `tree: true` through two tiny parsers (`testing/treeParsers.ts`); what they leave out is listed there, and `syntaxTreeContract` is the suite every engine that announces `tree` runs.
- The `type` step is one keystroke (1 to 64 characters) at the live selection, through the editor's input handlers, so the editor's own rules (auto-closed brackets, re-indent) apply; it is the only step of its call, it acts on the head (`at` older than it is `stale`, `map` or not) and its `landed` is `[null]`. A host that has no `type` method does not announce it and answers `unsupported`.
- Node steps (`moveNode`, `wrapNode`, `unwrapNode`, `deleteNode`, `duplicateNode`, `insertSnippet`, `reindentBlock`; `SEMANTIC_STEP_OPS`) edit whole lines of syntax nodes. A node is one statement or a run of sibling statements (a range, or `'selection'`, an empty one standing for the statement at the caret) that begins its line after its indentation and ends its line (a trailing comment is allowed); the comment-only lines right above it at its indent travel with it. A call may hold several node steps and one `select` step but no raw `replace` or `move`, and it is planned against the head: an `at` older than it is `stale`, `map` or not. The engine parses the document (in the `tree` job's slices, `budgetMs` 250 by default, 1000 at most), plans every step into one simultaneous change list (`planBatch`: one revision, one undo step), parses the result through the host's `treeOf(text)`, refuses it when it has a syntax error the document did not have or does not have the structure the steps promised (`core/semantic/verify.ts`), and only then commits, with no wait between the last head check and the commit: a keystroke that landed meanwhile ends the call as `structure-changed`, and its reply can come after the reply of an apply asked later. `hello` announces a node step only when the host has `tree()` and `treeOf()` and the engine has a planner for it; otherwise it is `unsupported` (`step:<op>`).
- A destination is `{before: Range}` or `{after: Range}` (relative to the whole-line run that range names, comments included), or `{into: Range, at: 'start' | 'end', block?}` (one statement block of a compound statement, numbered through its clauses; an else-if is reached by naming the nested compound; an empty `{}` is opened up at the owner's indent plus the host's `indentUnit`). Lines take the indent of the statement they land next to; indents are swapped as strings, so tabs stay tabs, a continuation line keeps its offset to its statement, and a line that begins inside a multi-line string is never touched. A move to where the lines already are, and a block already at its depth (`reindentBlock` with no `by`), change nothing: `ok`, no revision, no event. The caret or selection inside moved, wrapped, unwrapped or re-indented lines goes with them unless the call has a `select` step.
- Refusals are the existing codes with optional detail: `not-a-node` carries a `reason` (`no-statement`, `shares-line`, `not-in-block` for a braceless body, an else-if or a block of something else, `damaged`, `not-unwrappable`) and the `step`; `would-not-parse` carries a `reason` (`syntax`, `structure`) and `errors` that are ranges in the would-be text, because nothing applied (an emptied Python block is refused this way, there is no hidden `pass`); `parse-timeout{budgetMs}`; `structure-changed{head}`; a destination inside the moved node is `invalid` at `steps[i].to`, a `try` wrap header `invalid` at `steps[i].header` (it needs a clause one line cannot give). `wrapNode`'s header is the line without its colon or brace and must make one compound whose block holds exactly the run (so `if (x) foo();` and `else` are `structure`); `unwrapNode` takes a compound with exactly one block, nothing after it and no body on its header's line, and deletes the comment lines above it with the header; `insertSnippet` is not parsed on its own and is re-indented like any other text, multi-line strings included, so an `else:` that would extend the `if` before it is refused; `reindentBlock` with `by` shifts the run by that many units and the parse refuses what is not code (the run may leave its block), without `by` it gives every line the indent of its depth (a closing brace and an `else` line that of their owner; a `switch`'s case bodies are flattened to the depth of the `case`). Out of scope: C++ class and struct bodies, `try` wraps.
- `preview: true` on any `apply` (node steps or raw) plans and checks the call and answers `preview: {text, diff, landed}` with `changes: []`: the revision does not move, nothing is emitted and no undo step exists.
- `view` takes `focus` and, when `hello.capabilities.view` lists them, `marks: {clear, set}` and `reveal`, with `at` and `instance` as fields of the call and not of each mark. A mark is `{id, kind: 'edit' | 'error', range, hidden?}`: at most 8, one per id, `clear` runs before `set`, and a `hidden` one is listed and kept but not drawn. Ranges are rebased through the revision log like `apply`: an `at` ahead of the head is `invalid`, one below the floor `stale`, a range past the document at `at` is `out-of-range` (`step` is the index in `set`, -1 for the reveal), and a non-empty range whose text is gone is `range-lost`; the whole call is checked before anything is applied, so a refusal leaves no mark, no reveal and no focus change. `ViewValue` carries `marks` (head coordinates) and `revealed` (the last reveal: what was asked, not pixels; the next change or `load` clears it).
- The engine owns the marks (`core/marks.ts`, pure) and maps them through every change it ingests; the host maps its own copy with the same `mapMarks`, so they agree without a message: text typed at either edge of a mark stays outside it, a mark that lost all its text goes, an empty one (a blank line) stays. The engine tells the host (`marks(list)`, `reveal(range)`) only when a `view` or a `load` changes the list and never while ingesting a change, because a dispatch inside CodeMirror's update listener throws. A host without `marks()` or `reveal()` does not announce it and the call is `unsupported` (`view:marks`, `view:reveal`). The CodeMirror host draws both (`data/editor/cm6/cm6Marks.ts`: an `error` mark is a `cm-run-error-line` class on every line it touches and a `cm-run-error` underline over its text, an `edit` mark is the `cm-diff-change` highlight, a `hidden` one is skipped; `reveal` scrolls the range to the middle of the editor and moves neither the selection nor the focus), so the real page announces `marks` and `reveal`; the fake editor does too (`peek().marks`, `peek().revealed`; the option `marks: false` makes a host without them). The screen uses them for a failing run: `domain/editor/errorJump.ts` `showErrorLine` is one atomic `view` call placed at the revision the run took its checkpoint at, `clearErrorLine` takes the mark away, and `e2e/run-error-line.lua` proves it in the browser (a line below the first screen is marked, revealed inside the editor zone, and goes with the card on the next keystroke).
- A voice or plan edit marks what it changed with one mark (id `edit`, kind `edit`): `EditorInput.applyEdit` sets it in the same queued job as the apply, `at` the revision and `instance` the edit produced (`markEdit` in `domain/editor/editMark.ts`), so a keystroke that arrives first moves it with the text. The diff toggle flips its `hidden` flag (`setEditMarkHidden`: read the marks, set the same range at that revision), Reset clears it (`clearEditMark`) and a later edit replaces it.
- Events of a call arrive before its reply. A `changed` event's `from` that does not follow the mirror's revision means a lost message: resync.
- The engine owns the selection mapping: an empty caret stays before text inserted at it, a range stays inward, and a range wholly inside replaced text collapses to a caret after the replacement (CodeMirror's own mapping leaves a range turned inside out).
- Contract failures resolve as `{ok: false, error}`; transport failures reject at the engine and resolve as `transport` through the client.

## Adding to it

A new operation is a request name, a step op, an optional field, an event type or an optional host method, announced in `hello.capabilities`; an unknown one answers `unsupported`. Give it a case in `testing/contract.ts` and it runs on the fake, over both transports and on the real CodeMirror bundle.

## The page's syntax and suggestions

The page offers python, javascript and cpp (`hello.capabilities.languages`) and switches between them with `configure({language})`, in one compartment, without touching the text, selection, revision or undo history. It answers `tree` from the live state (`ensureSyntaxTree` in slices the engine paces) and, once `configure({completion: {enabled, entries}})` has turned it on, offers the `complete` step and the `completion` event; a load and a language switch keep the config. Completion is off until configured, and the app configures it from the problem list's Suggestions row (off by default).

## What proves it

`pnpm --filter @lib/code-editor-api test` (the suite on the fake, over a loopback and the emulated WebView, a 16,000-operation differential test against real CodeMirror state and history, a ChangeSet conformance test, the fake's tree parsers and the class tables against the real grammars) and the real-bundle flow tests: `cm6Engine.contract.flow.test.tsx` runs the editor contract and the tree contract for each language, `cm6Language`, `cm6Completion` and the host's `cm6Host.flow.test.ts` the rest. The browser runs `e2e/editor-language.lua` and `e2e/editor-completion.lua` show the switch and the list on a phone frame. Not provable there: typing through the DOM and IME, soft-keyboard focus, layout, Android bridge timing: the Chromium and Android editor-typing e2e cover those. The node steps are proved by `semanticContract` (per language, run on the fake with its own parsers and over real Lezer trees, over the loopback and emulated WebView, and on the real bundle in `cm6Engine.contract.flow.test.tsx`), the per-operation planner tests in `tests/core/semantic`, the fake-versus-Lezer differential in `tests/semantic.lezer.test.ts`, and, at the screen, `ProblemEditor.semanticOps.flow.test.tsx` through `session.editor().apply(steps, {preview})` and `undo()`.
