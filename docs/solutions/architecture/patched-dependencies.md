## Context

This repo uses pnpm's `patchedDependencies` block (`pnpm-workspace.yaml:62-65`) for three narrow, justified cases where an upstream package ships a bug or missing feature that we cannot wait for an upstream release to fix:

```yaml
patchedDependencies:
  '@storybook/react-native-ui@10.4.4': patches/@storybook__react-native-ui@10.4.4.patch
  react-native-css-interop@0.2.5:    patches/react-native-css-interop@0.2.5.patch
  skills@1.5.13:                     patches/skills@1.5.13.patch
```

Each entry is a `<name>@<exact-version>` → `patches/<file>.patch` mapping. The patch files live at the repo root in `patches/` (alongside an additional `react-native-reanimated+4.1.7.patch` already committed to the repo but not currently in the manifest — it gets activated if and when the underlying reanimated issue re-emerges). The patch content is a unified diff generated by `pnpm patch <pkg>@<ver>`; pnpm applies it during `pnpm install` to that exact version only.

The patch is pinned to the version: bump `@storybook/react-native-ui` to `10.5.0` and the patch no longer applies cleanly (line-number drift, hunks that no longer match), so `pnpm install` fails. This is intentional — it forces re-evaluation of the patch against the new upstream. The patch file is committed to git; every PR that changes a patch is a deliberate, reviewable event.

## Guidance

- **A patch is a temporary measure with an exit plan.** Every patched dependency in the manifest should have an associated upstream issue/PR or a TODO with a target version range where the patch can be removed. A patch that lives forever is a silent fork.
- **Always regenerate the patch via `pnpm patch <pkg>@<ver>`** (then `pnpm patch-commit <pkg>` after editing the extracted sources in `.pnpm-store/`). Never hand-write a `.patch` file — pnpm's format includes specific sha hashes for the extracted sources, and a hand-rolled patch that *seems* to apply may produce a broken install.
- **Bump the version in the manifest key, not the patch content.** If upstream ships `10.4.5` and the patch still applies, update the manifest key (`'@storybook/react-native-ui@10.4.4'` → `'@storybook/react-native-ui@10.4.5'`) and re-run `pnpm install` to verify. If it doesn't apply, you have two choices: (1) ship a new patch for `10.4.5` (same procedure), or (2) keep the older version pinned and document why.
- **One patch per fix.** Don't bundle unrelated changes into a single `.patch` file — when you re-apply after a version bump, you want a clean conflict signal per logical change. Split a monolithic patch into multiple files (`<pkg>-fix-x.patch`, `<pkg>-fix-y.patch`) and add them all to `patchedDependencies` if upstream ships them separately.
- **Document the patch in the PR description.** The patch diff itself doesn't explain *why* — reviewers need a one-paragraph summary: which upstream issue/PR it works around, what the symptoms were before, how to verify the patch is doing what it says. This belongs in the PR body, not the patch file (patches are pure diffs).
- **Watch the lockfile.** `pnpm-lock.yaml`'s `patchedDependencies` block (line 65) is the runtime truth — every installed copy has the patch hash recorded there, and a `pnpm install --frozen-lockfile` (CI default) will fail if `patches/<file>.patch` doesn't match the lockfile entry. A stale patch + a stale lockfile is the most common install failure mode.
- **Patch files are large diffs; commit them as-is.** Don't try to be clever with `gitattributes` (`*.patch diff=…`) — the patch is meant to be readable in `git log -p`.
- **Add the patch check to the dependency-vetting flow.** When `pnpm audit` reports a CVE in a patched package, the patch may (or may not) be in the affected code path; verify manually that the patched function isn't the vulnerable one, and bump the upstream version if it is.

## Why this matters

Patches are the supply-chain's escape hatch: when an upstream bug blocks progress and the maintainer is unresponsive or the next release is weeks away, a `pnpm patch` is the only way to ship today. The cost is that you're now maintaining a private fork of one function in N packages, pinned to an exact version, where every upstream bump requires re-validation. The repo's convention is "patches are committed, scoped to an exact version, and visible in CI" — so:

1. The patch can't silently disappear (committed, lint-checked, lockfile-recorded).
2. The exact version pin means a stale patch can't be silently reapplied to a new upstream (it fails install).
3. The PR review is the place where the "should we patch this, or wait for upstream?" decision lives.

A patch that grows over years without an upstream issue is technical debt; a patch that lives for one release cycle and gets removed is healthy.

## When to apply

- An upstream package has a bug that blocks shipping, no fix in the next release window, and no clean workaround in user code (e.g. wrapping the export, monkey-patching at runtime) — patch it. Document the upstream issue link in the PR.
- Bumping a patched dependency to a new version — verify the patch still applies; if not, regenerate or remove.
- Reviewing a PR that adds a new `patchedDependencies` entry — check that the patch is the minimum diff to fix the issue, that there's an upstream issue/PR linked, and that the version pin matches the lockfile.
- Running `pnpm audit` and seeing a CVE in a patched package — verify the patch isn't in the affected code path, or bump the version.

## Examples

- Current patches in the repo (`pnpm-workspace.yaml:62-65`): `@storybook/react-native-ui@10.4.4`, `react-native-css-interop@0.2.5`, `skills@1.5.13`. Each has a committed patch file under `patches/` and a pinned version in the manifest.
- Patch file location: `patches/<escaped-pkg>@<ver>.patch` (e.g. `patches/@storybook__react-native-ui@10.4.4.patch`, with `__` replacing `/` and `@`).
- Lockfile mirror: `pnpm-lock.yaml:65` — `patchedDependencies:` block, with the patch hash recorded per package. CI runs `pnpm install --frozen-lockfile` and fails if the patch sha drifts from the committed file.
- Procedure reference: `pnpm patch <pkg>@<ver>` to extract, edit the extracted sources in the pnpm store, then `pnpm patch-commit <pkg>` to write the diff into `patches/<file>.patch`. Both commands are documented in pnpm's official docs; the `commit` form is the one that updates `patchedDependencies` for you.
