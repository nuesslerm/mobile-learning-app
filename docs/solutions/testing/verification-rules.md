# Verification rules

Moved verbatim from the always-on `CLAUDE.md` section "Tests: what counts as verification" (8 Nov 2026), where a short rule now points here.

The test types (unit, flow, integration, deployment verification, browser/Android e2e, runbook), what each covers and doubles, one example each: `docs/solutions/testing/verification-ladder.md`. Order of importance and of reporting: runbook, browser/Android e2e, deployment verification, integration, flow, unit. Say which type ran; if only unit, say so plainly. A wf crate's flow tests (`clis/wf-*/tests/flow.rs`) enter through its thin binary `wf-<name>`; `WF_BIN=<full wf> cargo test -p wf-<name> --test flow` runs them through the real router (the parity oracle, every crate in post-land `rust-clis`). A change to a deployed service is tested against the service's own interface with the real payload, then through the real entry point. A negative probe must prove the request arrived. Visually verify anything visual and show the screenshot via `SendUserFile`. **Every run of a recordable test (e2e, runbook, device-lab, flow-in-browser) publishes a recording**, one per run (per step when a single file would be cut off), read back after upload; its report artifact links every recording beside the screenshots and tables, and a run with no recording is not done. **Every run of every test harness (flow, browser, Android) ends with a report**, pass or fail: one page with the verdict, steps, screenshots, recordings, goldens, timings, warnings and debugger hits, written by the harness itself. **Every CI test run publishes a run bundle**: `wf test publish <dir>` (the flow report dir, a harness run's test output dir, a queue job's results; `--publish` on `wf browser test`, `wf android test` and `wf flow run`, `WF_TEST_PUBLISH=1` on the VM worker) uploads `bundle.json` (schema 1: report, screenshots, recordings, debugger hits, timing, the metrics row, every file's public URL) under `verification/test-runs/<runId>/` in the verification-artifacts bucket and lists it in `verification/test-runs/index.json`; the reporter Routine turns new bundles into report artifacts, so a run that is not in the index did not happen for the dashboards. **The flow and browser harnesses have source maps and a debugger** (the Android harness has none until a later stage: its debugger went through the dev Metro, which is retired): breakpoints and logpoints by original `file:line`, stacks at original lines, locals at the stop. **Drive the keyboard like a user**: focus an input to raise it, tap Done (or a button that blurs) to lower it; no verb, hook or key press (`back`) may show or hide it directly. **Design agent-first**: every `wf` verb, test runner and debugging aid answers an agent in one call with stable JSON (a documented schema in `--help`/`--api`), never prompts, and on failure carries its own evidence (final state, screenshot path, warnings, a slow-or-broken verdict) and the next step; humans read the same output. Given/When/Then in every test. **Test behavior, never the implementation**: assert what happens when a name, key, string or value is used, not that it is set; a test that would still pass if the feature were broken, or fail when the code is restructured but behaves the same, is deleted or rewritten. Derive a test's inputs from the data under test (read the groups file, the lockfile, the registry) instead of copying names into the test, and when no behavior can be asserted (a constant, a wiring line, the text of a query) leave it untested and cover it one tier up (a live run, a flow test through the entry point). Mobile app definition of done: an EAS Update published with `wf ship eas --initial-route <route>`; web UI changes validated with Playwright against a local export first (`frontend/mla-tamagui/AGENTS.md`). Mobile UI verification is flow tests (`test:flow`, harness doubles) plus a local `expo export --platform web`; the EAS Update link from the CI run summary (or the one `wf ship eas` prints) opens the pushed commit in Expo Go.

## Flow tests of a screen that subscribes to a store

A store write that a mounted screen subscribes to is an update outside act. Reset such a store in `beforeEach`, before the screen mounts, never in `afterEach`: Vitest runs a test file's `afterEach` before the harness setup's `afterEach` that calls `cleanup()`, so the write lands on a still-mounted screen and the warning gate fails the test (seen in `ToolbarKeysTabs.flow.test.tsx`). Every flow test of an editor route awaits `session.editor()` before it acts or ends: the frame's ready, hydration and the keyboard target's updates land during the test, and a test that ends first fails on "update to X not wrapped in act" (`ProblemEditorHeader.flow.test.tsx`).

- A persisted zustand store's `setState` returns a promise: `act(() => store.setState(x))` returns it, React warns about `act(async)` without await and the render that follows draws nothing; write `act(() => { store.setState(x); })`.
- Hooks run last in, first out, so a state change in your `afterEach` re-renders the screen before the harness takes the test's final golden: reset stores in `beforeEach`, and put a resize or platform reset first.
- jsdom has no viewport: react-native-web's window width is 0, so anything sized from `useWindowDimensions` sits at its floor; give `documentElement` a `clientWidth` and dispatch a `resize`.
- `wf flow run <file> --update-goldens` rewrites every sidecar json (`render_ms`) even when the PNG is byte-identical: restore the sidecar of unchanged images to keep diffs small. The goldens of the settings index and row-press tests were made with a different font than this sandbox paints, so regenerating them moves pixels for nothing.
- Every flow test of an editor route awaits `session.editor()` before it acts or ends: the frame's ready, hydration and the keyboard target's updates land during the test, and a test that ends first fails on 'update to X not wrapped in act'.
- React Native Web maps `accessibilityRole` adjustable to role slider and `aria-valuetext` through, and drops `accessibilityActions` and `onAccessibilityAction`: a flow test or a browser e2e can read the role, name and value of an accessible node but cannot fire an accessibility action. Wire an action through a pure name-to-behaviour table (unit-tested, e.g. `domain/editor/cursorActions`) and prove the actions only with TalkBack and VoiceOver on a phone.

## No flaky tests (owner rule, 21 Nov 2026)

A test that fails and then passes with no change to the code is a bug, in the test or in the product, and it is fixed at its cause the first time it is seen. It is never rerun past, never marked "known", never given a retry or a longer sleep, and a red run caused by one is not a reason to push on. The usual causes and their fixes:

- A wall-clock budget under load (a syntax parse that has not caught up, a tree budget of 50 ms, a timeout that a busy two-core box misses): force the parse to complete in the test (`ensureSyntaxTree` or `forceParsing` with room to finish), or inject the clock and the budget so the test controls time. A product code path that decides on a partial parse is the bug.
- A deadline is fired by the test, not waited for: `testing/manualTimers.ts` is the double of the `@lib/webview-rpc` Timers seam, and a test fires a worker's case deadline after the worker's own begin message (a spawn wrapper in `data/javascript/__tests__/support/judgeRun.ts` lets it watch workers start, speak and end). Prove a timing-sensitive file by isolated copies in one vitest run under busy loops: write N stub files that only `import` the test file into a scratch folder under the tests, run them with `--maxWorkers=2` beside two `yes > /dev/null` loops, delete the stubs (F1.8: 30 copies of four files, 1920 tests, green).
- A fixed wait: wait on the condition itself (`extended_wait_until` over a read, a `findBy`, an awaited promise), with the timeout only as the failure bound.
- A wait that a different event can satisfy: waiting for a buffer to grow, or a counter to move, is satisfied by earlier input still arriving. Wait for the thing itself (the buffer ends with the key you tapped): `e2e/editor-typing.lua` `sym()`.
- A race the test papers over: a retry around a key press, a re-read until the text matches, a second tap "in case the first is lost" hide a product defect (the editor dropping a keystroke, a write that lands before the page is ready). Reproduce it under load, find the cause, fix the product, and delete the workaround.
- Shared state: a global, a store, a persisted setting or a browser profile that one test leaves for the next; reset it in the test that sets it, never in another.
- The one HOME of a flow-test process: wf-testkit gives every wf a test process spawns the same home, so a tool that leaves files under HOME (Nx writes `~/.nx/<id>/cache/run.json`, which a stage run reads back and sums into `CI_UNITS`) hands one parallel test another test's file. A fixture that runs such a tool passes its own HOME (`Workspace::wf` in `clis/pipeline/tests/flow/pipeline.rs`, the Nx crates fixture); prove it by running the test beside the others at `--test-threads=8`, not alone.
- A name made from the process id: a path like `ci-log-cache-<pid>-<n>` under `/tmp` is reused by a later test process, which then reads what an earlier run left there (a log cached under the same run and job ids). A scratch directory comes from `tempfile` with a random name, or is removed first.
- A file written and then executed in a multi-threaded test process: another thread's `fork` copies the open write handle into its child until that child's own `exec`, and executing the file in that window fails with `ETXTBSY` ("Text file busy", `real_clis.rs`, hosted run 44964345155). Run a script a test wrote through its interpreter (`/bin/sh path`), which opens it read-only; a stub that `wf` runs later has the same exposure only if the test spawns it itself.

To land a fix, show it holds: run the test many times in a row under CPU load (two parallel runs on the sandbox's two cores is enough) with no failure, and say how many times in the commit. A hosted job that goes red for a reason outside the code (a rate limit, a runner outage) is infrastructure: fix the workflow so it cannot recur (an exact pin, a bounded and retried fetch with a clear error) rather than waiting for the next run.
