# Verification rules

Moved verbatim from the always-on `CLAUDE.md` section "Tests: what counts as verification" (8 Nov 2026), where a short rule now points here.

The test types (unit, flow, integration, deployment verification, browser/Android e2e, runbook), what each covers and doubles, one example each: `docs/solutions/testing/verification-ladder.md`. Order of importance and of reporting: runbook, browser/Android e2e, deployment verification, integration, flow, unit. Say which type ran; if only unit, say so plainly. A wf crate's flow tests (`clis/wf-*/tests/flow.rs`) enter through its thin binary `wf-<name>`; `WF_BIN=<full wf> cargo test -p wf-<name> --test flow` runs them through the real router (the parity oracle, every crate in post-land `rust-clis`). A change to a deployed service is tested against the service's own interface with the real payload, then through the real entry point. A negative probe must prove the request arrived. Visually verify anything visual and show the screenshot via `SendUserFile`. **Every run of a recordable test (e2e, runbook, device-lab, flow-in-browser) publishes a recording**, one per run (per step when a single file would be cut off), read back after upload; its report artifact links every recording beside the screenshots and tables, and a run with no recording is not done. **Every run of every test harness (flow, browser, Android) ends with a report**, pass or fail: one page with the verdict, steps, screenshots, recordings, goldens, timings, warnings and debugger hits, written by the harness itself. **Every CI test run publishes a run bundle**: `wf test publish <dir>` (the flow report dir, a harness run's test output dir, a queue job's results; `--publish` on `wf browser test`, `wf android test` and `wf flow run`, `WF_TEST_PUBLISH=1` on the VM worker) uploads `bundle.json` (schema 1: report, screenshots, recordings, debugger hits, timing, the metrics row, every file's public URL) under `verification/test-runs/<runId>/` in the verification-artifacts bucket and lists it in `verification/test-runs/index.json`; the reporter Routine turns new bundles into report artifacts, so a run that is not in the index did not happen for the dashboards. **The flow and browser harnesses have source maps and a debugger** (the Android harness has none until a later stage: its debugger went through the dev Metro, which is retired): breakpoints and logpoints by original `file:line`, stacks at original lines, locals at the stop. **Drive the keyboard like a user**: focus an input to raise it, tap Done (or a button that blurs) to lower it; no verb, hook or key press (`back`) may show or hide it directly. **Design agent-first**: every `wf` verb, test runner and debugging aid answers an agent in one call with stable JSON (a documented schema in `--help`/`--api`), never prompts, and on failure carries its own evidence (final state, screenshot path, warnings, a slow-or-broken verdict) and the next step; humans read the same output. Given/When/Then in every test. **Test behavior, never the implementation**: assert what happens when a name, key, string or value is used, not that it is set; a test that would still pass if the feature were broken, or fail when the code is restructured but behaves the same, is deleted or rewritten. Derive a test's inputs from the data under test (read the groups file, the lockfile, the registry) instead of copying names into the test, and when no behavior can be asserted (a constant, a wiring line, the text of a query) leave it untested and cover it one tier up (a live run, a flow test through the entry point). Mobile app definition of done: an EAS Update published with `wf ship eas --initial-route <route>`; web UI changes validated with Playwright against a local export first (`frontend/mla-tamagui/AGENTS.md`). Mobile UI verification is flow tests (`test:flow`, harness doubles) plus a local `expo export --platform web`; the EAS Update link from the CI run summary (or the one `wf ship eas` prints) opens the pushed commit in Expo Go.
